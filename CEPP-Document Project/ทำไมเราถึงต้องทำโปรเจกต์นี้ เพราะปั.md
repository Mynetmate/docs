"Gartner คือบริษัทวิจัยและที่ปรึกษาด้านเทคโนโลยีอันดับหนึ่งของโลกครับ ข้อมูลสถิติเรื่อง Network Outage และความเสี่ยงจากการทำงานแบบ Manual ที่เรานำมาอ้างอิง 
จึงเป็นข้อมูลมาตรฐานอุตสาหกรรมที่วิศวกรและองค์กรระดับสากลใช้เป็นฐานในการตัดสินใจเปลี่ยนผ่านสู่ระบบ Automation ครับ"


คำแนะนำของอาจารย์ที่ปรึกษาถือเป็น "Engineering Reality Check" ที่ดีมากครับ เพราะท่านมองเห็นจุดที่อาจจะทำให้โปรเจกต์ดีเลย์ได้จริง ในฐานะทีมพัฒนา หากต้องไปคุยกับอาจารย์เพื่อให้ท่านมั่นใจว่าเรา "รับทราบและมีแผนรับมือ" (โดยที่ยังไม่ต้องแก้เล่มตามที่ท่านบอก) ผมขอแนะนำแนวทางการพูดแบ่งตามประเด็น ดังนี้ครับ:
1. เรื่องระบบกรอง PII (ไม่พึ่ง AI)
แนวทางการพูด:
"ในส่วนของ PII Protection ทีมตั้งใจจะใช้แนวทาง Deterministic Regex ร่วมกับ Local NLP Library (เช่น Microsoft Presidio หรือ spaCy) ครับ โดยเราจะทำหน้าที่เป็นเลเยอร์ตรวจสอบ 100% บนเครื่องเซิร์ฟเวอร์ของเราเองก่อนจะส่งข้อมูลไปหา LLM API ครับ 
เราเห็นด้วยกับอาจารย์ครับว่าไม่ใช่เรื่องง่าย เราจึงเลือกโฟกัสที่ข้อมูล 4 ชุดหลักที่มีแพทเทิร์นชัดเจนก่อน คือ Passwords, IP Addresses, SNMP Communities และ Encryption Keys เพื่อคุมความซับซ้อนของโค้ดให้ยังอยู่ในวิสัยที่จัดการได้ครับ"

2. เรื่องความเยอะของ Parser (Cisco & MikroTik)
แนวทางการพูด:
"สำหรับเรื่อง Parser ทีมขอรับคำแนะนำอาจารย์มาบีบ Scope ให้ชัดเจนขึ้นครับ ในช่วงแรกเราจะจำลองอุปกรณ์ใน ContainerLab โดยอ้างอิงรุ่นยอดนิยมคือ Cisco Catalyst (IOS 15/17) และ MikroTik RouterOS v7 เท่านั้นครับ เราจะใช้ออกแบบเป็น Modular Parser คือแยก Logic ของแต่ละยี่ห้อออกจากกันเพื่อให้ง่ายต่อการ Unit Test และถ้าหากเวลาไม่พอ เราจะยึด Cisco ให้สมบูรณ์ 100% เป็นลำดับแรกก่อนครับ"

3. เรื่อง Temporal Database
แนวทางการพูด:
"เรื่อง Temporal Database ทีมเลือกใช้ PostgreSQL เป็นฐานข้อมูลหลักครับ เนื่องจากมีฟีเจอร์รองรับมาตรฐาน SQL:2011 และมี Extension ที่ช่วยจัดการเรื่อง System-versioned tables ได้ค่อนข้างนิ่งแล้วครับ
 ตอนนี้ทีมกำลังเร่งศึกษาเรื่องการทำ Point-in-time Query เพื่อให้การดึงประวัติ Configuration ออกมาเทียบ Diff ทำได้รวดเร็วและถูกต้องตามหลักฐานข้อมูลครับ"

4. เรื่อง Documentation (Onboarding vs Audit)
แนวทางการพูด:
"ประเด็นความแตกต่างของเอกสาร Onboarding และ Audit ทีมเห็นด้วยอย่างยิ่งครับว่ารายละเอียดไม่ตรงกัน ในช่วงแรกเราจะยึดตามแผนเดิมไปก่อนตามที่อาจารย์แนะนำครับ
 แต่เราจะเตรียม 'Data Source' ชุดเดียวไว้ในฐานข้อมูล แล้วใช้วิธีเปลี่ยน Output Template แทนครับ หากถึงช่วงที่ทำจริงแล้วพบว่าซับซ้อนเกินไป ทีมจะขออนุญาตอาจารย์ปรับลด Scope
ลงโดยเน้นที่ Audit Log สำหรับการตรวจสอบ (Compliance) เป็นสำคัญ เพราะเป็นจุดที่สร้างมูลค่าให้ Stakeholder ได้ชัดเจนที่สุดครับ"

Q1. ความถูกต้องของ Ai + rag วัดยังไง ?
ans : แบ่งเป็น 2 ส่วนคือ ส่วนแรก Rag จะวัดด้วย F2 score เน้นความครอบคลุมของเนื้อหาที่ดึงมาให้หมด

Q1.1 ถ้าความแม่นยำต่ำเป็นอะไรมั้นถ้าอย่างนั้น?
ans : เป็นแต่พอเข้า model Ai อย่างเช่น gemini ด้วยความที่โมเดลค่อนข้างเก่งพอเราได้รับ context แล้วมีบางส่วนที่ไม่เกี่ยวข้องโดยมากจะถูกกรองออกเอง

Q2. ความถูกต้องของ Ai?
ans : f1 score เน้นทั้งความแม่นยำและ recall(ภาพรวม) เพื่อ balance ให้ไม่มั่วและตอบให้ครอบคลุมพอดี ๆ

Q3. ถ้าเน้นความแม่นยำแบบโคตร ๆ Ai ควรใช้อะไรวัด
ans : f0.5 score ที่เน้นความแม่นยำ

Q4. RAG ช่วยอะไรในโปรเจกต์นี้?
ans : เนื่องจากการพัฒนามีการใช้ vendor มากกว่า 1 เจ้า ทำให้การมี Rag ช่วยให้การ config แต่ละเจ้าแม่นยำขึ้นจากเอกสารที่นำมาอ้างอิง

Q5. คุณจะมั่นใจได้อย่างไรว่า Sensitive Data Detection (เช่น Password ใน Config) จะไม่หลุดไปถึง Google Gemini API?
ans : เราใช้ microsoft presidio ในการพัฒนาส่วนนี้ที่เป็น enterprise standard จึงค่อนข้างมีความปลอดภัยที่สูงเพราะถูกใช้งานในระดับ enterprise
