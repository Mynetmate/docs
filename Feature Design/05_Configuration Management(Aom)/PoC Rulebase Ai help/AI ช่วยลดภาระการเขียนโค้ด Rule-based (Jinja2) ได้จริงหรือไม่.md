# **สิ่งที่อาจารย์ต้องการคืออะไร?** 

จากคำแนะนำของอาจารย์ที่ว่า _"ให้ทดลองใช้ AI ช่วยเขียน code เพื่อสร้างตัว generate config ดูว่าพอใช้งานได้มากน้อยแค่ไหน... จะได้ลดภาระในการเขียน code"_ สิ่งที่อาจารย์กำลังสื่อสาร ไม่ใช่การทำระบบ AI แชทบอทให้ User ใช้งาน (End-User Feature) แต่เป็นการ **"ประเมินขีดความสามารถของ AI ในฐานะเครื่องมือช่วยพัฒนาระบบ (Developer Tool)"** โดยมีเป้าหมายแฝง 3 ประการ ดังนี้:

1. **การพิสูจน์สมมติฐานเรื่องความคุ้มค่าของเวลา (Time-to-Value):** การสร้างระบบ Network Automation ต้องอาศัยการเขียน Template (เช่น Jinja2) จำนวนมหาศาลเพื่อรองรับฟีเจอร์ต่างๆ (VLAN, Routing, ACL) ซึ่งเป็นงานที่ใช้แรงงานคน (Manual effort) สูงมาก อาจารย์ต้องการให้ทีมงานสร้าง **Proof of Concept (PoC)** เพื่อทดสอบว่า หากผู้พัฒนา (Developer) โยนโครงสร้างข้อมูล (JSON Schema) และชุดคำสั่งอ้างอิง (CLI Blueprint) ให้กับ AI (เช่น ChatGPT หรือ Gemini) แล้วสั่งให้ AI เขียนลอจิก Jinja2 ออกมา ผลลัพธ์ที่ได้มีความถูกต้องเพียงพอที่จะนำไปใช้งานต่อได้ทันทีหรือไม่ หรือสุดท้ายแล้วผู้พัฒนาต้องเสียเวลามานั่งแก้บั๊ก (Debug) โค้ดที่ AI เขียนผิดจนไม่คุ้มค่า
    
2. **การหาจุดสมดุลระหว่าง Automation กับ AI (Finding the Sweet Spot):** อาจารย์ต้องการให้ทีมงานวิเคราะห์ว่า AI เก่งแค่ไหนในบริบทของ Network Configuration โดยคาดหวังให้ทีมงานจัดกลุ่มได้ว่า:
    
    - _Config ระดับใดที่ AI สามารถ Generate โค้ด Jinja2 ได้สมบูรณ์ 100%_ (เช่น สคริปต์วนลูปสร้าง Interface พื้นฐาน) ซึ่งจะช่วยลดภาระโปรแกรมเมอร์ได้อย่างมหาศาล
    - _Config ระดับใดที่ซับซ้อนเกินไปจน AI เริ่มเกิดอาการ Hallucination (เขียนมั่ว)_ (เช่น การทำ Policy Routing หรือ QoS) ซึ่งในส่วนนี้ทีมงานจะต้องยอมรับภาระในการเขียนโค้ด Rule-based ด้วยตัวเอง

3. **การสร้างเครื่องมือช่วยสร้างโค้ด (Code Generator Pipeline):** หาก PoC นี้ประสบความสำเร็จ สิ่งที่อาจารย์มองเห็นคือ ทีมงานอาจจะสามารถสร้าง "สคริปต์ตัวช่วย (Internal Tool)" ที่ใช้ AI เป็นหลังบ้าน เพื่อผลิตไฟล์ `.j2` (Jinja2) จำนวนมากออกมาได้อย่างรวดเร็ว ทำให้โปรเจกต์สามารถรองรับอุปกรณ์เครือข่ายได้หลากหลายยี่ห้อ (Multi-Vendor) ในระยะเวลาที่จำกัด

**สรุป:** สิ่งที่อาจารย์ต้องการเห็น คือ **"ผลการทดลองแบบ A/B Testing"** ที่มีตัวเลขชี้วัดชัดเจน (เช่น เวลาที่ใช้เขียนเองเทียบกับใช้ AI, อัตราความถูกต้องของโค้ด) เพื่อฟันธงว่าในขั้นตอนการพัฒนา (Sprint) เราควรพึ่งพา AI ในการเขียน Rule-based มากน้อยเพียงใดครับ

**คำถาม: ทำไมอยู่ดีๆ ถึงเป็น Jinja2?** เพราะในสถาปัตยกรรมระบบที่เราตกลงกันไว้ (ไฟล์ `MyNetMate Weight Feature List.md` หมวด 5.1) เราระบุชัดเจนว่าแกนหลักของการแปลงข้อมูลจากหน้าเว็บไปเป็นคำสั่ง คือ **Jinja2 Template Engine** (ซึ่งเป็นมาตรฐานอุตสาหกรรมที่ Python, Ansible, Nornir ใช้) ดังนั้นคำว่า "Rule-based" ของโปรเจกต์นี้ จึงหมายถึง "การเขียนเงื่อนไข (If-Else/Loop) ด้วยภาษา Jinja2" ครับ

# ก่อนจะเริ่มทำ PoC ให้ AI เขียนโค้ด คุณต้องเตรียม **"3 สิ่งที่จำเป็น (Prerequisites)"**:

### 📄 สิ่งที่ 1: กำหนด Target Vendor (จะเอา Cisco, Huawei หรือ MikroTik?)

AI จะไม่สามารถเขียนโค้ดได้เลยถ้าไม่รู้เป้าหมายครับ

- **วิธีเลือก:** อิงจาก "อุปกรณ์จริง" ที่คณะ/มหาวิทยาลัยมีให้ยืมทำโปรเจกต์ครับ สมมติว่าห้องแล็บมีแต่ Cisco Router/Switch เราก็จะเลือก **Cisco IOS** เป็นเป้าหมายหลักในการทำ PoC
- **ทำไมต้องเลือกก่อน:** เพราะคำสั่งสร้าง VLAN ของ Cisco (`vlan 10`) กับ MikroTik (`/interface vlan add`) หน้าตาคนละเรื่องกันเลยครับ ถ้าไม่ระบุ AI จะเดามั่ว

### 📄 สิ่งที่ 2: Command Blueprint (คู่มือคำสั่ง CLI ที่ถูกต้อง 100%)

คุณ (ในฐานะ Engineer) ต้องไปเปิดคู่มือหรือตำราเรียน เพื่อหา **"คำสั่งที่ถูกต้องที่สุด (Best Practice)"** มาเตรียมไว้ก่อน เพราะถ้าคุณไม่รู้ว่าคำสั่งที่ถูกคืออะไร คุณจะไม่มีทางรู้เลยว่า AI มันเขียน Jinja2 เจนคำสั่งออกมามั่วหรือเปล่า

- **สิ่งต้องเตรียม:** พิมพ์ชุดคำสั่งเปล่าๆ ใส่ Notepad ไว้ เช่น
```text
! Blueprint สำหรับสร้าง VLAN (Cisco)
vlan [ID]
 name [NAME]
interface [PORT]
 switchport mode access
 switchport access vlan [ID]
```
### 📄 สิ่งที่ 3: Data Schema (โครงสร้างข้อมูลฝั่ง Frontend)

AI จำเป็นต้องรู้ว่า "ข้อมูลตั้งต้น" ที่กรอกมาจากหน้าเว็บ (6-Tab) หน้าตามันเป็นยังไง? มันถึงจะเอาตัวแปรไปเขียนเงื่อนไขใน Jinja2 ถูก

- **สิ่งต้องเตรียม:** ร่างไฟล์ JSON สมมติขึ้นมา 1 ก้อน (Mock Data) ว่าถ้า User กรอกฟอร์ม ข้อมูลที่ส่งมาหลังบ้านจะเป็นแบบนี้:
```json
{
  "interfaces": [
    {"port": "Gig0/1", "vlan": 10},
    {"port": "Gig0/2", "vlan": 20}
  ]
}
```

### 🚀 สรุปขั้นตอน (Flow) เมื่อเตรียมของครบ:

พอคุณมีของ 3 อย่างนี้ครบ คุณถึงจะเดินไปหา AI (Gemini/Claude) แล้วบอกมันว่า:

> _"นี่คือข้อมูล JSON ที่ฉันมี (สิ่งที่ 3) และนี่คือรูปแบบคำสั่ง Cisco IOS ที่ฉันอยากได้ (สิ่งที่ 1 และ 2) จงใช้ AI ของนาย เปลี่ยนมันเป็นโค้ด Jinja2 ให้ฉันหน่อย!"_

เมื่อทำตามลำดับนี้ คุณจะมี **"เกณฑ์มาตรฐาน (Baseline)"** ในการจับผิด AI ทันทีครับ ว่ามันฉลาดพอที่จะช่วยลดภาระเรา หรือมันโง่จนเราต้องมานั่งแก้โค้ดให้มันครับ! 


# Proof of Concept
### ขั้นตอนที่ 1: กำหนดขอบเขตการทดสอบ (Test Scenarios)
เลือกหัวข้อ Config มา 2 ระดับ เพื่อดูขีดจำกัดของ AI:

1. **ระดับพื้นฐาน (Basic):** เช่น การสร้าง VLAN และ Assign IP เข้า Interface (Logic ไม่ซับซ้อน มีแค่ Loop ธรรมดา)
2. **ระดับซับซ้อน (Advanced):** เช่น การทำ OSPF หรือ ACL (Logic ซับซ้อน ต้องมี If-Else หลายชั้น เช่น ถ้าเป็น Switch ทำแบบนึง ถ้าเป็น Router ทำอีกแบบนึง)

### ขั้นตอนที่ 2: กำหนดเกณฑ์ชี้วัด (Metrics) เพื่อวัดคำว่า "ลดภาระ"

คุณจะพิสูจน์ได้ว่า "ลดภาระได้จริงไหม" ต้องมีตัวเลขชี้วัดให้จดบันทึก 4 ค่านี้:

1. **Time-to-Code (เวลาที่ใช้):** จับเวลาเปรียบเทียบระหว่าง "คุณนั่งพิมพ์ Jinja2 เองตั้งแต่ศูนย์" VS "คุณนั่งคิด Prompt สั่ง AI + เวลาแก้บั๊กที่ AI เขียนผิด"
2. **Syntax Accuracy (ความแม่นยำของโค้ด):** โค้ด Jinja2 ที่ AI เจนมาให้ ก๊อปปี้ไปรันปุ๊บ พังปั๊บเลยไหม? (มี Error Syntax ของภาษาโปรแกรมไหม)
3. **Domain Correctness (ความถูกต้องทาง Network):** โค้ดผ่านการ Render ออกมาเป็น Cisco CLI แล้ว เอาไปรันใน Simulation อุปกรณ์พังไหม? (AI ใช้คำสั่งผิดเวอร์ชัน หรือผิด Grammar ของ Cisco หรือเปล่า)
4. **Prompt Iteration (ภาระการสั่งงาน):** ต้องพิมพ์แก้คำสั่งสั่ง AI กี่รอบ (กี่ Prompt) กว่า AI จะเขียน Jinja2 ออกมาได้สมบูรณ์ 100%

###  ขั้นตอนที่ 3: ลงมือพิสูจน์จริง (Execution)

นี่คือสิ่งที่คุณต้องไป **"ค้นคว้าและทำจริง"** เพื่อเอาผลลัพธ์ไปโชว์อาจารย์:

1. **เตรียม Data Source:** เขียนไฟล์ JSON หรือ YAML สมมติขึ้นมา 1 ก้อน (เช่น ข้อมูล VLAN 3 วง และ OSPF)
2. **สั่งงาน AI (ทดสอบ Prompt):**
    - โยน JSON นั้นเข้าไปใน AI (เช่น ChatGPT, Claude)
    - สั่ง Prompt ว่า: _"จงเขียนโค้ด Jinja2 Template สำหรับ Cisco IOS เพื่อรับข้อมูล JSON นี้ไปสร้างเป็น CLI Config"_
3. **ทดสอบรัน (Render):**
    - เอาโค้ด Jinja2 ที่ AI ให้มา ไปรันผ่าน Python (เขียนโค้ดเทสแค่ 5 บรรทัดก็พอ)
    - ตรวจดูว่า Text CLI ที่คลอดออกมา หน้าตาตรงตามความคาดหวังไหม
4. **ทดสอบจริง (Validate):** เอา CLI ที่ได้ไปก๊อปปี้แปะลงใน Cisco Router บน **GNS3 หรือ Cisco Packet Tracer** ดูว่าอุปกรณ์รับคำสั่งนั้นได้โดยไม่ขึ้น Error `^ Invalid input detected`

###  ขั้นตอนที่ 4: สรุปผลลัพธ์เทียบกับสมมติฐานอาจารย์

หลังจากทำ Step 1-3 เสร็จ คุณจะได้ **ตารางตัวเลข** ไปกางให้อาจารย์ดู ซึ่งผลลัพธ์จะออกมาทางใดทางหนึ่งเพื่อตอบสมมติฐานครับ:

- **เคสที่ 1 (สมมติฐานอาจารย์เป็นจริง):** AI สามารถเขียน Jinja2 ให้คุณได้ถูก 90% ตั้งแต่ Prompt แรก คุณแค่แก้บั๊กนิดหน่อย ใช้เวลา 5 นาที (เทียบกับเขียนเอง 30 นาที) -> **สรุปให้อาจารย์ฟัง:** _"AI ช่วยลดภาระการเขียน Rule-base ได้จริง เราจะใช้ AI ในฐานะ Co-pilot (เครื่องมือช่วย Dev) ในการปั๊ม Template ทั้งหมดของระบบครับ"_
- **เคสที่ 2 (สมมติฐานอาจารย์เป็นเท็จ/มีข้อจำกัด):** AI เขียน Jinja2 ออกมามีแต่บั๊ก If-Else ผิดลอจิก หรือใช้คำสั่ง Cisco ผิดเวอร์ชัน คุณเสียเวลาทะเลาะกับ AI ไป 40 นาที (เขียนเอง 30 นาทีเสร็จ) -> **สรุปให้อาจารย์ฟัง:** _"จากการพิสูจน์ AI ช่วยลดภาระได้เฉพาะ Config พื้นฐาน แต่พอเป็น Config ที่มี Logic ซับซ้อน AI มี Hallucination (มั่ว) สูง และเพิ่มภาระในการ Debug สรุปคือความซับซ้อนบางส่วน เรายังต้องใช้แรงวิศวกรเขียน Rule เองครับ"_
