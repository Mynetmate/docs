# Authentication & RBAC — สรุปการอัปเดต 04-09-2569

> **สำหรับทีม:** รอบนี้ปิดรายละเอียด Design และ Contract เพื่อเตรียม Implement แต่ยังไม่ใช่หลักฐานว่า Feature พัฒนาเสร็จแล้ว

หลังจากรายงานความคืบหน้าครั้งที่ 2 ฝั่ง Authentication เดิมมี**แนวคิดเรื่อง Session, RBAC และโครงสร้างฐานข้อมูลเบื้องต้นแล้ว** ไม่ได้เพิ่มขอบเขต Feature แต่ลงรายละเอียดให้สามารถนำไป Implement ได้โดยไม่ต้องตัดสินใจเรื่องสำคัญระหว่างเขียนโค้ดครับ

1. ใช้ Server-side Session แบบ ไม่รู้ความหมาย (Opaque) โดย Browser เก็บเพียง Session Token แบบสุ่มใน HttpOnly Cookie ส่วนฐานข้อมูลเก็บเฉพาะค่า Hash ของ Token 
	1. วิธีนี้ทำให้ Server ตรวจสอบและยกเลิก Session ได้ทันที เช่น เมื่อ Logout, เปลี่ยนรหัสผ่าน, เปลี่ยน Role หรือ Deactivate ผู้ใช้
    
2. ผมกำหนดมาตรการความปลอดภัยของ Login ให้ชัดเจน ได้แก่ 
	1. ใช้ Argon2id สำหรับ Hash รหัสผ่าน, 
	2. ใช้ Dummy Hash เมื่อไม่พบ Username เพื่อลดการเดาบัญชีจากระยะเวลาตอบกลับ, 
	3. จำกัดการ Login ผิด 5 ครั้งภายใน 15 นาที และใช้ข้อความผิดพลาดแบบเดียวกันเพื่อไม่เปิดเผยว่าบัญชีมีอยู่หรือไม่
    
3. ผมออกแบบการป้องกันฝั่ง Web เพิ่มเติม 
	1. โดย Session Cookie เป็น HttpOnly, Secure ใน Production  
	2. SameSite=Strict 
	3. รวมถึงตรวจ Origin และ CSRF Header สำหรับคำสั่งที่เปลี่ยนข้อมูล 
	4. ส่วน Frontend ใช้การแสดงผลข้อความตามปกติของ React และไม่อนุญาตให้ Render HTML หรือ Markdown ดิบ เพื่อลดความเสี่ยง XSS
    
4. ผมล็อก RBAC เป็น 3 บทบาท คือ Admin, Operator และ Viewer 
	1. โดย Backend เป็นผู้ตรวจสิทธิ์ทุก Request แบบ Default Deny ไม่พึ่งการซ่อนปุ่มที่ Frontend เพียงอย่างเดียว และมีข้อกำหนดป้องกันการ Deactivate หรือลดสิทธิ์ Admin คนสุดท้ายของระบบ
    
5. ทำ Contract เชื่อมกับ
	1. Central Database, Dashboard และ Audit Trail แล้ว
	2. โดยกำหนดชื่อเหตุการณ์มาตรฐาน กฎการบันทึก Login สำเร็จหรือล้มเหลว Permission Denied และการเปลี่ยนข้อมูลผู้ใช้ รวมถึงห้ามส่ง Password, Token, Cookie, IP หรือ Username ที่ Login ผิดลง Audit Log
    

นอกจากนี้ ผมกำหนด API Contract, รูปแบบ Error กลาง, พฤติกรรมหน้าจอเมื่อได้ 401 หรือ 403, Component และ Sequence Diagram, Test User Policy และ Acceptance Tests ไว้แล้ว

**Demo ของ P1** ที่ตั้งเป้าไว้คือ Viewer Login แล้วเรียก Admin API จะได้รับ 403 จาก Backend จากนั้น Admin สามารถ Deactivate Operator ที่กำลังใช้งานอยู่ได้ และ Request ถัดไปของ Operator จะถูกปฏิเสธทันทีพร้อมมี Audit Event บันทึกไว้

**สถานะปัจจุบันคือ** การออกแบบและ Contract ของ Authentication พร้อมเข้าสู่ Implementation แต่ยังไม่ถือว่า Feature เสร็จ เพราะยังต้องสร้าง Database Migration, Backend Auth Service และ API, หน้า Login และ Session State ฝั่ง Frontend รวมถึงรัน Acceptance Tests ให้ผ่านจริงครับ

**ขอบเขตที่ตัดออกจาก P1 ได้แก่** OAuth/SSO, MFA, การ Reset Password ผ่านอีเมล, LDAP/Active Directory และสิทธิ์ละเอียดระดับรายอุปกรณ์ เพื่อควบคุมขนาดงานให้เหมาะกับโปรเจกต์จบครับ

ถ้าอาจารย์ถามว่า “ครั้งที่ 2 กับตอนนี้ต่างกันอย่างไร” ให้ตอบสั้น ๆ ว่า:

> ครั้งที่ 2 เป็นการเลือกแนวทางและวางโครงสร้างเบื้องต้นครับ ส่วนรอบนี้เป็นการปิดรายละเอียดด้าน Security, API, Database, RBAC, Audit Integration และ Acceptance Tests ให้โปรแกรมเมอร์สามารถเริ่ม Implement ได้โดยไม่ต้องเดา Contract เพิ่ม
