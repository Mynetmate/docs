# คำศัพท์และแนวคิดสำคัญ (Glossary) สำหรับ Authentication & RBAC

เอกสารนี้รวบรวมคำศัพท์และแนวคิดที่เกี่ยวข้องกับระบบ Authentication และ Role-Based Access Control (RBAC) ในโปรเจกต์ MyNetMate (อ้างอิงจากบทวิเคราะห์ MVP)

| คำศัพท์ / แนวคิด               | คำอธิบาย                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| :----------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Argon2id**                   | อัลกอริทึม Memory-hard สำหรับ Hash รหัสผ่าน MyNetMate P1 ล็อก Baseline ที่ `m=19456 KiB`, `t=2`, `p=1` โดยให้ Library สร้าง Salt ใหม่อัตโนมัติทุกครั้งและเก็บผลในรูป PHC String ต้องใช้ Password Hasher ชุดเดียวกันกับ Login, Create User, Change Password และ Seed User พร้อม Benchmark บนเครื่อง Demo ให้การ Verify หนึ่งครั้งต่ำกว่าประมาณ 1 วินาที ห้ามเก็บรหัสผ่านเป็น Plaintext หรือใช้ Fast Hash เช่น SHA-256 กับ Password                                             |
| **Dummy Password Hash**        | Argon2id PHC String ที่สร้างหนึ่งครั้งตอนเริ่ม Application ด้วย Password Hasher ชุดเดียวกับผู้ใช้จริง ใช้ Verify รหัสผ่านที่ส่งมาแล้วทิ้งผลเมื่อไม่พบบัญชี เพื่อลดความต่างด้านเวลาระหว่าง “ไม่พบบัญชี” กับ “รหัสผ่านผิด” Dummy Hash ไม่ใช่ Credential ของบัญชีใดและไม่ใช้สร้าง Session                                                                                                                                                                                        |
| **Login Rate Limiter**         | P1 ใช้ Bounded In-memory Sliding-window TTL Store ใน FastAPI Process เดียว นับ Login ที่ล้มเหลวต่อ Client IP ภายใน 15 นาที โดยอนุญาต 5 ครั้งและปฏิเสธครั้งที่ 6 ก่อน Query User/Argon2id; Counter หายเมื่อ Process Restart เป็นข้อจำกัดที่ยอมรับใน P1 และต้องเปลี่ยนเป็น Shared Store หากภายหลังใช้หลาย Worker/Instance                                                                                                                                                       |
| **Trusted Proxy**              | Reverse Proxy ที่ Backend ตั้งค่าไว้อย่างชัดเจนว่าเชื่อถือได้ Backend เชื่อ Forwarded Header เฉพาะเมื่อ Connection มาจาก Proxy ใน Allowlist เท่านั้น หากไม่ผ่านเงื่อนไขต้องใช้ Peer IP จาก Connection และห้ามเชื่อ `X-Forwarded-For` ที่ Client ส่งมาโดยตรง                                                                                                                                                                                                                   |
| **Error Response Envelope**    | รูปแบบ Error กลางของ Auth คือ `{ "error": { "code": "...", "message": "..." } }` โดย `code` เป็น Machine-readable Contract ที่ Frontend ใช้ตัดสินพฤติกรรม ส่วน `message` เป็นข้อความปลอดภัยสำหรับผู้ใช้ P1 ไม่ส่ง Stack Trace, SQL Error, Raw Input, Token หรือข้อมูลลับ และยังไม่เพิ่ม Field-level Error Schema                                                                                                                                                              |
| **Reversible Encryption**      | การเข้ารหัสที่สามารถถอดกลับมาเป็นข้อความเดิมได้ (เช่น AES, RSA) **ข้อควรระวัง:** [OWASP กำหนดว่าห้ามใช้ Reversible Encryption ในการเก็บรหัสผ่าน](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) ต้องใช้ One-way Hashing (เช่น Argon2id) เท่านั้น                                                                                                                                                                                           |
| **Server-side Session**        | รูปแบบการยืนยันตัวตนที่ Browser ถือเพียง Session Token แบบสุ่มและไม่มีความหมาย ส่วนข้อมูลผู้ใช้ สถานะ Session วันหมดอายุ และ Role ถูกเก็บและตรวจสอบที่ Backend ผ่านตาราง `auth_sessions` และ `users` ทุกครั้ง                                                                                                                                                                                                                                                                 |
| **Opaque Session Token**       | ค่าสุ่มลับที่ไม่บรรจุ `user_id`, Role หรือข้อมูลธุรกิจใด ๆ MyNetMate สร้างด้วย CSPRNG ขนาด 32 bytes (256 bits) และส่งผ่าน Cookie เท่านั้น ห้ามส่งผ่าน URL, Response JSON, `localStorage` หรือ `sessionStorage`                                                                                                                                                                                                                                                                |
| **Session Token Hash**         | ค่า SHA-256 ของ Opaque Session Token ที่เก็บในคอลัมน์ `auth_sessions.session_token_hash` ระบบเก็บเฉพาะ Hash และไม่เก็บ Token ดิบ เพื่อลดความเสี่ยงที่ฐานข้อมูลหรือ Log รั่วแล้ว Token ถูกนำไปใช้สวมรอยทันที                                                                                                                                                                                                                                                                   |
| **Cookie Security Attributes** | การตั้งค่า Session Cookie เพื่อความปลอดภัย: <br> - **`HttpOnly`**: ป้องกัน JavaScript อ่านค่า Cookie โดยตรง <br> - **`Secure`**: บังคับส่งผ่าน HTTPS เท่านั้นใน Production <br> - **`SameSite=Strict`**: ลดการส่ง Cookie จากบริบท Cross-site <br> - **ไม่กำหนด `Domain`**: จำกัด Cookie อยู่ที่ Host เจ้าของ <br> *หมายเหตุ: SameSite เป็นเพียง Defense in Depth และไม่แทนการตรวจ CSRF อื่น*                                                                                  |
| **CSRF Protection**            | การป้องกันไม่ให้เว็บไซต์อื่นสั่ง Browser ที่ Login อยู่ส่งคำขอแทนผู้ใช้ MyNetMate กำหนดให้ State-changing Request ตรวจ Exact `Origin`/`Referer`, ต้องมี `X-CSRF-Protection: 1`, ใช้ Exact CORS Allowlist และสำหรับ Endpoint ที่มี Request Body ต้องรับเฉพาะ `application/json` ร่วมกับ `SameSite=Strict`                                                                                                                                                                      |
| **CSRF Custom Header**         | Header `X-CSRF-Protection: 1` **ไม่ใช่ Token ลับ** แต่ใช้ทำให้ Cross-origin JavaScript ต้องผ่าน CORS Preflight ก่อน Browser จะส่ง Request จริง Backend ต้องตรวจ Header นี้ร่วมกับ Exact `Origin`/`Referer`; ห้ามใช้ Header นี้เพียงอย่างเดียวเป็นหลักฐานว่า Request ปลอดภัย                                                                                                                                                                                                   |
| **Cross-Site Scripting (XSS)** | การโจมตีที่ทำให้ข้อมูลจากผู้ใช้หรือ API ถูก Browser ตีความและรันเป็น JavaScript บนหน้า MyNetMate ผลกระทบอาจรวมถึงการสวมสิทธิ์ผู้ใช้และสั่ง API จาก Browser ของเหยื่อ แม้ Session Cookie จะเป็น `HttpOnly`                                                                                                                                                                                                                                                                     |
| **Safe Rendering**             | P1 ต้องแสดงข้อมูลจากผู้ใช้หรือ API เป็นข้อความผ่าน React JSX ตามปกติ ห้ามนำข้อมูลที่ไม่น่าเชื่อถือไปใช้กับ `dangerouslySetInnerHTML`, `innerHTML`, `outerHTML`, `insertAdjacentHTML` หรือ `document.write` และ P1 ไม่รองรับการ Render HTML, Rich Text หรือ Markdown ดิบ หากอนาคตต้องรองรับ ต้องผ่าน Security Review และใช้ HTML Sanitization ที่เหมาะสม                                                                                                                       |
| **HttpOnly Limitation**        | `HttpOnly` ช่วยป้องกัน JavaScript อ่านและขโมย Session Token โดยตรง แต่ไม่ป้องกัน XSS ไม่ให้รัน และไม่ป้องกัน Script ที่รันอยู่ใน Origin ของ MyNetMate จากการเรียก API โดย Browser แนบ Cookie ให้อัตโนมัติ                                                                                                                                                                                                                                                                     |
| **Content Security Policy**    | HTTP Header ที่จำกัดแหล่ง Script และ Resource เพื่อลดผลกระทบจาก XSS สำหรับ MyNetMate ถือเป็น Future Hardening และไม่ใช่ข้อบังคับของ P1; หากเพิ่มภายหลังต้องทดสอบกับ React Build และ Resource ที่ระบบใช้จริง                                                                                                                                                                                                                                                                   |
| **Revoke Session**             | การบังคับยกเลิกเซสชันจากฝั่งเซิร์ฟเวอร์โดยตั้ง `auth_sessions.is_revoked=true` ทำให้ Session Token เดิมใช้ต่อไม่ได้ใน Request ถัดไป                                                                                                                                                                                                                                                                                                                                           |
| **Session Fixation**           | การโจมตีที่พยายามบังคับให้ผู้ใช้ใช้ Session Token ที่ผู้โจมตีรู้ค่า ระบบป้องกันด้วยการสร้าง Token ใหม่จาก CSPRNG หลัง Login สำเร็จทุกครั้ง และไม่รับ Session Token จาก URL หรือ Request Body                                                                                                                                                                                                                                                                                  |
| **Route / API Protection**     | การป้องกันการเข้าถึง API และหน้าเว็บตามสิทธิ์ (Role) ของผู้ใช้งาน                                                                                                                                                                                                                                                                                                                                                                                                             |
| **Backend Enforcement**        | หลักการป้องกันความปลอดภัยที่ต้อง **"บังคับใช้ที่ฝั่ง Backend เป็นหลัก"** การซ่อนปุ่ม หรือปิดการใช้งาน (Disable) บนหน้าจอ UI (Frontend) เป็นเพียงการปรับปรุง UX เท่านั้น ไม่ใช่มาตรการรักษาความปลอดภัยที่แท้จริง                                                                                                                                                                                                                                                               |
| **Audit Events (Auth)**        | เหตุการณ์สำคัญด้านความปลอดภัยที่ต้องบันทึกลง Audit Log ได้แก่: <br> - `user.login_success` <br> - `user.login_failed` <br> - `user.logout` <br> - `user.password_changed` <br> - `user.deactivated` <br> - `auth.permission_denied` <br> *(หมายเหตุ: ชื่อ action นี้เป็น canonical name ที่ใช้ทั้งระบบ ถ้า D&M ต้องการฟิลด์ `result` ให้ Backend function อนุมาน result จากชื่อ action เช่น `user.login_success` → result=`success`, `user.login_failed` → result=`failure`)* |
| **Resource Type**              | ประเภทของข้อมูลที่ถูกกระทำ เช่น `user`, `auth`, `device` เพื่อให้ง่ายต่อการ Filter                                                                                                                                                                                                                                                                                                                                                                                            |
| **actor_user_id**              | (DTO) ชื่อฟิลด์ในฝั่ง API ที่ Map มาจากคอลัมน์ `user_id` ใน Database เพื่อส่งให้ D&M นำไปแสดงผลว่าใครเป็นคนทำ                                                                                                                                                                                                                                                                                                                                                                 |
| **occurred_at**                | (DTO) ชื่อฟิลด์ในฝั่ง API ที่ Map มาจากคอลัมน์ `created_at` ใน Database เพื่อใช้บอกเวลาที่เกิดเหตุการณ์                                                                                                                                                                                                                                                                                                                                                                       |
| **result**                     | สถานะของเหตุการณ์ มีแค่ 2 ค่าคือ `success` (สำเร็จ) และ `failure` (ล้มเหลว)                                                                                                                                                                                                                                                                                                                                                                                                   |
| **safe_error_category**        | หมวดหมู่ Error ที่ถูกคัดกรองแล้วว่าปลอดภัย ห้ามมีข้อมูลลับหรือ PII สำหรับ Auth P1 ใช้จริงเฉพาะ `authentication_error`, `authorization_error` และ `null`; ค่า `validation_error` กับ `server_error` เป็น Reserved จนกว่าจะมี Canonical Registry Entry รองรับ                                                                                                                                                                                                                   |
| **Out of Scope (P1)**          | ฟีเจอร์ที่ถูก **ตัดออก** หรือไม่อยู่ในระยะ MVP P1 ได้แก่: <br> - OAuth / SSO <br> - MFA (Multi-Factor Authentication) <br> - การยืนยันอีเมล (Email Verification) <br> - การรีเซ็ตรหัสผ่านผ่านอีเมล (Email Reset Password) <br> - ระบบ LDAP / Active Directory <br> - สิทธิ์ระดับฟิลด์หรือทรัพยากร (Resource/Field-level Permission)                                                                                                                                           |
