
หลักแบ่งงานที่ถูกต้องคือ:

- **คุณในฐานะ Audit Owner:** กำหนดหลักว่าเหตุการณ์แบบไหนจำเป็นต้องเก็บ และกำหนดรูปแบบ Event กลาง
- **เจ้าของแต่ละ Feature:** ระบุว่า Feature ของเขามี Business Action อะไร เกิดตรงไหน และมี ID อะไรส่งมาให้ได้
- จากนั้นทั้งสองฝ่ายตกลง Event Catalog ร่วมกัน

เอกสารปัจจุบันมี Event Catalog ตั้งต้นแล้ว แต่ตอนนี้ Reconcile จริงเพียง Central Schema, Auth และ D&M ส่วน Device, Config, CIS และ Settings ยังควรขอการยืนยันจากเจ้าของ Feature

## ต้องคุยกับใครบ้าง

| ผู้ประสานงานตามโฟลเดอร์ | Feature                   | Event ที่เสนอใน P1                                                                                                                                              | สถานะ                   |
| ----------------------- | ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------- |
| นภัทร                   | Authentication & RBAC     | `user.login_success`, `user.login_failed`, `user.logout`, `user.password_changed`, `user.created`, `user.updated`, `user.deactivated`, `auth.permission_denied` | Reconciled แล้ว         |
| นภัทร                   | Dashboard & Monitoring    | ไม่ต้องส่ง Event; เป็นผู้ขออ่าน Recent Activity                                                                                                                 | Reconciled แล้ว         |
| Tee                     | Device Inventory          | `device.create`, `device.update`, `device.delete`                                                                                                               | ต้องขอยืนยัน            |
| Aom                     | Configuration Management  | `config.generate`                                                                                                                                               | ต้องขอยืนยัน            |
| King                    | Security & Validation/CIS | `scan.run`, `scan.override`                                                                                                                                     | ต้องขอยืนยัน            |
| ยังไม่พบ Owner ชัดเจน   | Settings & Administration | `settings.update`                                                                                                                                               | ต้องกำหนดเจ้าของก่อน    |
| Aom                     | Configuration Deployment  | `config.deploy`                                                                                                                                                 | P2 ยังไม่ต้อง Integrate |

ควรยืนยันกับ King ด้วยว่า `scan.run` ใน Catalog หมายถึง **CIS Benchmark Scan** ไม่ใช่ Network Discovery Scan เพราะชื่อปัจจุบันตีความได้สองแบบ

## คุณต้องขออะไรจากเจ้าของ Feature

อย่าขอแค่ว่า “ส่ง Log มาให้หน่อย” แต่ให้แต่ละคนตอบข้อมูลต่อไปนี้สำหรับทุก Action:

1. **ชื่อการกระทำสำคัญ**
    - เช่น Create Device, Generate Config หรือ Override CIS
2. **จังหวะที่ถือว่า Action สำเร็จ**
    - หลัง Insert DB สำเร็จ?
    - หลัง Jinja2 สร้าง Config และบันทึก `config_history` สำเร็จ?
    - หลัง Scan บันทึกผลครบทุก Rule?
3. **ใครเป็นผู้กระทำ**
    - ส่ง `actor_user_id` ได้หรือไม่
    - เป็น User, Admin หรือ System Action
4. **กระทำกับข้อมูลใด**
    - ส่ง `resource_id` ตัวไหน
    - Device ID, Config History ID หรือ Scan Result ID
5. **ต้องการเก็บ Failure หรือไม่**
    - Failure แบบใดมีความสำคัญด้าน Security หรือ Compliance
    - Failure ทั่วไปไม่ควรเก็บทั้งหมด เพราะจะเกิด Log Noise
6. **ใช้ Database Transaction ตัวใด**
    - ต้องสามารถส่ง DB Session เดียวกับ Business Action มาให้ Audit Writer ได้
7. **มีข้อมูลลับอะไรเกี่ยวข้อง**
    - Password, IP, Config Secret, Credential หรือข้อความจากผู้ใช้
    - ข้อมูลใดห้ามส่งเข้า `description`
8. **ต้องการให้ Dashboard แสดง Event นี้หรือไม่**
    - ถ้าต้องการ ต้องเพิ่มใน Positive Allowlist ของ Recent Activity

## คุณต้องส่งอะไรให้เพื่อน

เมื่อเพื่อนตอบข้อมูลข้างต้นแล้ว คุณต้องส่ง Contract กลับให้แต่ละคนว่า:

- ชื่อ Event ที่อนุมัติ เช่น `device.update`
- `resource_type` ที่ต้องใช้
- `resource_id` ต้องอ้างถึงอะไร
- `actor_user_id` ต้องเป็นใคร
- `result` และ `safe_error_category` ที่อนุญาต
- เรียก `record_audit_event()` ตรงจุดใด
- ต้องใช้ Transaction เดียวกับ Business Action หรือ Transaction แยก
- ข้อมูลใดห้ามส่ง
- ถ้า Audit Write ล้มเหลว Feature ต้องทำอย่างไร
- Acceptance Test ที่ Feature ต้องผ่าน

ตัวอย่าง Contract ที่ส่งให้ Tee:

```
เมื่อสร้าง Device สำเร็จ ให้ส่ง:

action: device.create
resource_type: device
resource_id: ID ของ Device ที่เพิ่งสร้าง
actor_user_id: Current User
result: success
safe_error_category: null

ต้องเรียก Audit Writer ใน Transaction เดียวกับการสร้าง Device
หาก Audit เขียนไม่สำเร็จ ต้อง Rollback การสร้าง Device
ห้ามส่ง Credential, Password หรือ Management IP ใน description
```

## คุณต้องตัดสินใจว่าอะไรสำคัญพอจะ Audit

ใช้หลักง่าย ๆ นี้:
ควรเก็บเมื่อ Action นั้น:
- เปลี่ยนแปลงข้อมูลสำคัญ
- เปลี่ยนสิทธิ์หรือสถานะผู้ใช้
- สร้างหรือลบ Resource
- เกี่ยวกับ Security หรือ Compliance
- เป็นการ Override คำเตือนหรือกฎความปลอดภัย
- เป็นการส่งคำสั่งไปยังระบบภายนอก
- เป็นการปฏิเสธการเข้าถึงที่มีนัยสำคัญ

ไม่ควรเก็บใน P1:
- การเปิดหน้า
- การค้นหาและ Filter
- การพิมพ์ทุกครั้ง
- Validation Error 400/422 ทั่วไป
- Health Check
- Dashboard Refresh
- การอ่านข้อมูลทั่วไป เว้นแต่ข้อมูลนั้นมีความอ่อนไหวสูง

ดังนั้นขั้นตอนถัดไปของคุณคือ **นำ Event Catalog ปัจจุบันไปให้ Tee, Aom, King และเจ้าของ Settings ตรวจสอบ** ไม่ใช่ถามกว้าง ๆ ว่า “ส่ง Log อะไรมาบ้าง” แต่ให้พวกเขายืนยัน Trigger, Actor, Resource, Transaction และข้อมูลลับของแต่ละ Event ครับ
