แนวทางที่เหมาะสมคือแบ่งเป็น 2 ส่วน:
## ส่วนที่ทำต่อได้ทันที

ทำโครงสร้างกลางของ Audit ให้เสร็จก่อน ได้แก่:

- ตาราง `audit_logs`
- `record_audit_event()`
- การตรวจ Event Registry
- Redaction ข้อมูลลับ
- Transaction rules
- `GET /api/audit-logs`
- Acceptance Tests ของ Audit Writer
- เชื่อม Auth และ D&M ซึ่ง Contract พร้อมแล้ว

## ส่วนที่พักไว้ก่อน

สำหรับ Device, Config, CIS หรือ Settings ที่ Feature ยังออกแบบไม่เสร็จ ให้กำหนดสถานะว่า:

> `Pending Feature Contract — ยังไม่อนุมัติ Event สำหรับ Implementation`

ไม่ควรเดาชื่อ Event หรือสร้าง Contract ล่วงหน้า เพราะอาจเกิดปัญหา เช่น:

- Audit ผิดจังหวะ
- อ้าง `resource_id` ผิดตาราง
- บันทึกเหตุการณ์ที่ Feature ไม่มีจริง
- ต้องแก้ Migration หรือ Test ใหม่ภายหลัง
- เก็บ Failure มากเกินความจำเป็น

## ข้อมูลขั้นต่ำที่ขอไว้ก่อนได้

แม้ Feature ยังไม่เสร็จ คุณอาจขอเพียง:

- Feature นี้ยังอยู่ใน P1 หรือไม่
- ใครเป็น Owner
- มีการเปลี่ยนแปลงข้อมูลสำคัญประเภทใดบ้าง
- คาดว่าจะใช้ตารางหรือ Resource ใด
- ประมาณเมื่อไร Contract จะนิ่ง

ยังไม่ต้องขอชื่อ Event, Trigger และ Transaction แบบ Final

## เมื่อไรต้องกลับมาคุยเรื่อง Audit

กำหนด Audit Integration Gate ว่า:

> ก่อนเจ้าของ Feature เริ่ม Implement หรือ Merge API ที่สร้าง แก้ไข หรือลบข้อมูล ต้องยืนยัน Audit Contract ก่อน

ตอนนั้นจึงให้เขาตอบ:

- Action อะไรต้องเก็บ
- เก็บเมื่อสำเร็จหรือเมื่อล้มเหลว
- Actor คือใคร
- Resource ID คืออะไร
- เรียก Audit Writer ตรงไหน
- ใช้ Transaction ใด
- มีข้อมูลอะไรห้ามส่ง
- ต้องแสดงใน Dashboard หรือไม่

## สถานะที่ควรใช้ตอนนี้

|Feature|สถานะ Audit|
|---|---|
|Auth|Ready / Reconciled|
|Dashboard & Monitoring|Ready / Reconciled ในฐานะ Consumer|
|Device Inventory|Pending Feature Contract|
|Configuration Generation|Pending Feature Contract|
|CIS Validation|Pending Feature Contract|
|Settings|Pending Owner และ Feature Contract|
|Configuration Deployment|Deferred to P2|

สรุปคือ **พัก Dependency ที่ยังไม่นิ่ง แต่เดินหน้า Audit Foundation ต่อ** และห้ามประกาศว่า Audit Trail P1 “Integrated ครบทุก Producer” จนกว่า Device, Config, CIS และ Settings จะยืนยัน Contract จริงครับ
