# Audit Trail — สรุปการอัปเดต 04-09-2569

> **สำหรับทีม:** Contract กลางของ P1 พร้อมเชื่อม Authentication และ Dashboard แล้ว แต่ Backend, API และ Automated Tests ยังไม่ได้ Implement ครบ

หลังจากรายงานความคืบหน้าครั้งที่ 2 ในส่วน Audit Trail ได้ปรับงานจากการกำหนดขอบเขตเบื้องต้น ให้กลายเป็นข้อตกลงกลางที่ชัดเจนก่อนเริ่มพัฒนาจริงครับ

**แนวคิด**คือ 
	แต่ละฟีเจอร์จะเป็นผู้แจ้งว่าเกิดเหตุการณ์สำคัญอะไรขึ้น 
		เช่น มีการเพิ่มอุปกรณ์ สร้าง Configuration หรือมีผู้ใช้เข้าสู่ระบบไม่สำเร็จ 
	ส่วน **Audit Trail จะรับผิดชอบตรวจสอบรูปแบบ กรองข้อมูลลับ และเก็บเหตุการณ์เหล่านี้ลงฐานข้อมูลกลาง** เพื่อให้ตรวจสอบย้อนหลังได้ว่าใครทำอะไร กับข้อมูลใด เมื่อไร และผลเป็นอย่างไร

งานที่ดำเนินการเพิ่มเติมมี 4 ส่วนหลักครับ

1. ได้ปรับโครงสร้างตาราง `audit_logs` ให้เป็นมาตรฐานเดียวกับฐานข้อมูลกลาง เหลือข้อมูลที่จำเป็น 9 ฟิลด์ และตัด Client IP ออกจาก Audit Log ใน P1 เพื่อลดการเก็บข้อมูลส่วนบุคคลที่ไม่จำเป็น
2.  ได้สรุปหน้าที่ระหว่างแต่ละระบบให้ชัดเจน โดย Authentication และฟีเจอร์อื่นเป็นผู้ส่ง Event, Audit Trail เป็นผู้เขียนข้อมูลผ่านฟังก์ชันกลาง และ Dashboard เป็นเพียงผู้อ่านข้อมูลบางส่วนไปแสดงใน Recent Activity ซึ่งจะไม่เห็นรายละเอียดหรือข้อมูลลับทั้งหมด
3. ได้แก้กฎเรื่อง Transaction ให้ครอบคลุมกรณีพิเศษ
	1. เช่น ถ้าแก้ไขข้อมูลอุปกรณ์สำเร็จ การแก้ไขกับ Audit Log ต้องบันทึกพร้อมกัน แต่ถ้าเป็นเหตุการณ์ Login ไม่สำเร็จหรือถูกปฏิเสธสิทธิ์ แม้คำขอหลักจะไม่สำเร็จ ระบบยังต้องเก็บหลักฐานเหตุการณ์นั้นไว้ได้ 
	2. หาก Audit ที่จำเป็นบันทึกไม่ได้ ระบบจะไม่ปล่อยให้การเปลี่ยนแปลงหลักสำเร็จโดยไม่มีหลักฐาน

4. ได้เพิ่มข้อกำหนดด้าน Privacy และการทดสอบ เช่น ห้าม Password, Token และ Credential หลุดลงฐานข้อมูล จำกัดการดูประวัติฉบับเต็มไว้เฉพาะ Admin และกำหนดการทดสอบเรื่อง Rollback, สิทธิ์การเข้าถึง, การปกปิดข้อมูล และการแบ่งหน้าที่ไม่ทำให้ข้อมูลซ้ำหรือข้าม

**สถานะปัจจุบันคือ** Contract ระหว่าง Audit Trail, Central Schema, Authentication และ Dashboard ได้ตรวจให้สอดคล้องกันแล้วสำหรับ P1 แต่ยังไม่ถือว่า Implement เสร็จ เพราะ Backend ปัจจุบันยังไม่มีตารางจริง ฟังก์ชัน Audit Writer, API และ Automated Test

สำหรับ Device Inventory, Configuration Generation, CIS Validation และ Settings จะยังพักการกำหนด Event ขั้นสุดท้ายไว้ก่อน จนกว่าเจ้าของแต่ละฟีเจอร์จะสรุปกระบวนการทำงานของตนเอง แล้วจึงยืนยันร่วมกันว่าเหตุการณ์ใดสำคัญพอที่จะต้องเก็บ Audit

**ขั้นตอนถัดไปคือเริ่มสร้างโครงสร้าง** Audit Trail กลางและเชื่อมกับ Authentication ก่อน จากนั้นจึงทยอยเชื่อมฟีเจอร์อื่นเมื่อ Contract ของแต่ละส่วนพร้อมครับ

หากอาจารย์ถามสั้น ๆ ว่า “รอบนี้ได้ผลลัพธ์อะไร” ตอบได้ว่า:

> ได้ข้อตกลงกลางที่ทำให้ทุกฟีเจอร์ส่งประวัติในรูปแบบเดียวกัน เก็บอย่างถูกต้องตาม Transaction และไม่มีข้อมูลลับหลุดลง Audit Log โดยตอนนี้ Auth กับ Dashboard พร้อมเชื่อมต่อแล้ว เหลือการ Implement และรอ Event Contract จากฟีเจอร์อื่น

หากถามว่า “ทำไมไม่ให้แต่ละ Feature เขียน Log เอง”:

> แต่ละ Feature เป็นผู้ตัดสินว่าเหตุการณ์เกิดเมื่อไร แต่ให้ Audit Trail เป็นผู้ตรวจและเก็บผ่านจุดเดียว เพื่อป้องกันชื่อ Event ไม่ตรงกัน ข้อมูลลับรั่ว และประวัติไม่ตรงกับการเปลี่ยนแปลงจริง

หากถามว่า “ทำไมยังไม่กำหนด Event ของทุก Feature”:

> เพราะบาง Feature ยังออกแบบไม่จบ หากกำหนด Event ล่วงหน้าอาจอ้างอิงขั้นตอนหรือตารางผิด จึงทำโครงสร้างกลางก่อน และกำหนดให้ทุก Feature ต้องยืนยัน Audit Contract ก่อนเริ่มรวมระบบหรือ Merge API ที่เปลี่ยนแปลงข้อมูลครับ
