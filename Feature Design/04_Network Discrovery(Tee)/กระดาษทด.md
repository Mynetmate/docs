## เดิม" หากพบอุปกรณ์แต่ยังระบุตัวตนหรือ Management Address ไม่ครบ ระบบต้องเก็บไว้เป็น Unresolved Neighbor แทนการละทิ้งข้อมูล" และเพื่อนบอกว่า "ข้อจำกัดของ network discovery กรณีที่มี devices ที่ไม่สามารถระบุได้ (unmanagement) แต่มีวิธีให้สามารถ discovery ต่อจากนั้นได้หาก network admin เพิ่ม manunal เองหลังจากนั้นก็ค้นหาต่อได้"****


แนวคิดของเพื่อนถูกต้อง แต่ควรแยกคำว่า **Unresolved Neighbor** กับ **Unmanaged Device**:

- **Unresolved Neighbor:** พบหลักฐานจาก LLDP/CDP แต่ยังจับคู่กับอุปกรณ์ใน Inventory ไม่ได้
- **Unmanaged Device:** ระบุตัวอุปกรณ์ได้บางส่วน แต่ระบบยังเชื่อมต่อเพื่อเก็บข้อมูลไม่ได้ เช่น ไม่มี Management IP หรือ Credential

สามารถปรับข้อความเป็น:

หากระบบตรวจพบอุปกรณ์เพื่อนบ้านจาก LLDP/CDP แต่ยังไม่มี Management Address หรือไม่สามารถจับคู่กับอุปกรณ์ใน Device Inventory ได้ ระบบจะเก็บข้อมูลที่ตรวจพบไว้เป็น **Unresolved Neighbor** พร้อมหลักฐาน เช่น Chassis ID, Hostname, Interface และอุปกรณ์ต้นทาง โดยไม่ละทิ้งข้อมูลหรือสร้างอุปกรณ์ที่ยืนยันแล้วโดยอัตโนมัติ

ผู้ดูแลเครือข่ายสามารถเพิ่ม Management IP Address, Vendor/Platform และ Credential Reference ของอุปกรณ์ดังกล่าวผ่าน Manual Device Enrollment จากนั้นระบบจะเชื่อมต่อผ่าน SSH เพื่อตรวจสอบตัวตนและจับคู่กับข้อมูล Unresolved Neighbor เดิม หากตรวจสอบสำเร็จ อุปกรณ์จะเปลี่ยนเป็นอุปกรณ์ที่ระบบบริหารจัดการได้ และสามารถใช้เป็น Seed Device เพื่อค้นหาอุปกรณ์ในลำดับถัดไปได้


ลำดับสถานะจะเป็น:

```
พบจาก LLDP/CDP
→ Unresolved Neighbor
→ ผู้ดูแลเพิ่ม IP และ Credential Reference
→ ตรวจสอบผ่าน SSH
→ จับคู่กับข้อมูลเดิม
→ Verified/Managed Device
→ เริ่ม Discovery ต่อจากอุปกรณ์นี้
```

แต่หากอุปกรณ์ไม่มี Management IP หรือไม่รองรับ SSH/SNMP จริง ระบบจะค้นหาต่อผ่านอุปกรณ์นั้นไม่ได้ และต้องแสดงว่า Topology อาจไม่ครบถ้วนครับ


## CDP เพื่อนบอกไม่ใช้ ใช้ SNMP แทน โดยเพื่อนบอกว่า "CDP เป็น protocol เฉพาะของ cisco vendor อื่นไม่สามารถใช้ร่วมกันได้ ของผมทำเป็นรองรับ protocol พื้นฐาน SNMP, LLDP"

เพื่อนอธิบายถูกต้องครับ ควรตัด CDP ออกจากขอบเขต เพราะเป็น Protocol เฉพาะของ Cisco

แต่ในเชิงเทคนิค **SNMP ไม่ได้ทำหน้าที่แทน CDP โดยตรง**:

- **SNMP** ใช้อ่านข้อมูล Device, Interface และตารางข้อมูลต่าง ๆ
- **LLDP** ใช้ประกาศและค้นหาข้อมูลอุปกรณ์เพื่อนบ้าน
- ระบบใช้ SNMP อ่านข้อมูลจาก **LLDP MIB**

ข้อความที่แก้แล้วควรเป็น:

ระบบ Network Discovery ใช้ SNMP แบบอ่านอย่างเดียวเพื่อเก็บข้อมูลพื้นฐานของอุปกรณ์และ Interface และใช้ข้อมูลจาก LLDP MIB เพื่อค้นหาอุปกรณ์เพื่อนบ้าน โดยเลือกใช้ LLDP เนื่องจากเป็น Protocol มาตรฐานที่สามารถใช้งานร่วมกับอุปกรณ์จากหลาย Vendor ส่วน CDP ไม่อยู่ในขอบเขต เนื่องจากเป็น Protocol เฉพาะของ Cisco

หากระบบตรวจพบอุปกรณ์เพื่อนบ้านจาก LLDP แต่ข้อมูลยังไม่เพียงพอสำหรับจับคู่กับอุปกรณ์ใน Device Inventory เช่น ไม่มี Management Address, Hostname หรือ Chassis ID ที่สมบูรณ์ ระบบจะเก็บข้อมูลพร้อมหลักฐานที่ตรวจพบไว้เป็น **Unresolved Neighbor** โดยไม่ละทิ้งข้อมูลหรือสร้างอุปกรณ์ที่ยืนยันแล้วโดยอัตโนมัติ

ผู้ดูแลเครือข่ายสามารถเพิ่ม Management IP Address, Vendor/Platform และ Credential Reference ของอุปกรณ์ดังกล่าวผ่าน Manual Device Enrollment จากนั้นระบบจะตรวจสอบตัวตนของอุปกรณ์และจับคู่กับข้อมูล Unresolved Neighbor เดิม หากอุปกรณ์เปิดใช้ SNMP และมีข้อมูล LLDP ระบบจะสามารถใช้อุปกรณ์นั้นเป็น Seed Device เพื่อดำเนินการ Network Discovery ต่อไปได้

ลำดับการทำงานคือ:

```
SNMP อ่านข้อมูล LLDP MIB
→ พบข้อมูลเพื่อนบ้าน
→ ข้อมูลไม่ครบ: Unresolved Neighbor
→ ผู้ดูแลเพิ่ม Management IP และ Credential
→ ระบบตรวจสอบและจับคู่ข้อมูลเดิม
→ อุปกรณ์เปิด SNMP/LLDP
→ ใช้เป็น Seed Device เพื่อ Discovery ต่อ
```

ข้อควรระวัง: หากเพิ่มอุปกรณ์ผ่าน SSH ได้ แต่ไม่ได้เปิด SNMP หรือ LLDP อุปกรณ์นั้นสามารถอยู่ใน Device Inventory ได้ แต่ยังใช้เป็นจุดเริ่มต้นเพื่อค้นหาเพื่อนบ้านต่อด้วยกระบวนการ Discovery ปัจจุบันไม่ได้ครับ




Unresolved Neighbor: พบหลักฐานจาก LLDP/CDP แต่ยังจับคู่กับอุปกรณ์ใน Inventory ไม่ได้ อ้าวจะเกิดขึ้นได้อย่างไร

เกิดขึ้นได้ครับ เพราะ LLDP บอกว่า “มีเพื่อนบ้านเชื่อมอยู่” แต่ไม่ได้รับประกันว่าจะมีข้อมูลเพียงพอสำหรับจับคู่กับ Device Inventory

ตัวอย่าง:

```
Device Inventory
└─ มี Core-SW-01 เท่านั้น

Core-SW-01 อ่าน LLDP แล้วพบ:
├─ System Name: Floor-SW-01
├─ Chassis ID: 00:11:22:33:44:55
├─ Remote Port: ether1
└─ Management IP: ไม่ได้ประกาศ
```

ระบบรู้ว่ามี `Floor-SW-01` เชื่อมอยู่ แต่ยังสร้างความสัมพันธ์กับ `device_id` ไม่ได้ เพราะอุปกรณ์นั้นยังไม่อยู่ใน Inventory และไม่มี Management IP สำหรับเชื่อมต่อ จึงเก็บเป็น Unresolved Neighbor

กรณีที่เกิดได้ ได้แก่:

- อุปกรณ์เพื่อนบ้านยังไม่ได้ลงทะเบียนใน Device Inventory
- LLDP ไม่ได้ส่ง Management Address เพราะข้อมูลส่วนนี้เป็น Optional
- LLDP ส่งเพียง Chassis ID หรือ MAC Address
- System Name ว่างหรือซ้ำกับอุปกรณ์อื่น
- Management IP อยู่ในเครือข่ายที่ระบบเข้าถึงไม่ได้
- พบโทรศัพท์ IP, Access Point หรืออุปกรณ์อื่นที่ประกาศ LLDP แต่ระบบยังไม่รองรับ
- ข้อมูลใน Inventory ใช้ IP เป็นตัวอ้างอิง แต่ LLDP ส่งมาเพียง Chassis ID

ดังนั้นความหมายที่ถูกต้องคือ:

> **Unresolved Neighbor:** ข้อมูลเพื่อนบ้านที่ตรวจพบจาก LLDP แต่ยังไม่สามารถจับคู่กับ Device ID และ Interface ID ใน Device Inventory ได้

เมื่อผู้ดูแลเพิ่มอุปกรณ์นั้นผ่าน SSH:

```
เพิ่ม Management IP
→ ระบบเชื่อมต่อผ่าน SSH
→ เก็บ Hostname, MAC/Chassis ID และ Interface
→ จับคู่กับ LLDP Observation เดิม
→ เปลี่ยนจาก Unresolved Neighbor เป็น Managed Device
```

อย่างไรก็ตาม ไม่ควรจับคู่ด้วย Hostname เพียงอย่างเดียว เพราะอาจซ้ำกัน ควรใช้ Management Address หรือ Chassis ID/Base MAC เป็นหลัก และให้ผู้ใช้ยืนยันหากหลักฐานยังไม่แน่นอนครับ
