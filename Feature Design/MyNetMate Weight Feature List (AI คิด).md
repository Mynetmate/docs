## 1. บริบทและข้อจำกัด (ทำไมเราถึงทำทุกอย่างไม่ได้?)

ก่อนที่จะจัดลำดับฟีเจอร์ เราต้องยอมรับข้อจำกัดของโปรเจกต์นี้ก่อน:
1. **เวลาจำกัด:** มีเวลาเขียนโค้ดจริงๆ แค่ประมาณ 1 เทอม (CE Project 2)
2. **ขีดจำกัดของอุปกรณ์จริง:** Router/Switch ที่มหาลัยให้ยืมมา อาจจะไม่รองรับคำสั่งสมัยใหม่ หรือ IOS Version เก่า (ถ้า AI เจนคำสั่งแปลกๆ มา อุปกรณ์อาจจะพังได้)
3. **ข้อจำกัดเรื่อง Network มหาลัย:** เราไม่สามารถทำ Network Discovery (Ping Sweep) สุ่มสี่สุ่มห้าในมหาลัยได้ เพราะจะโดนบล็อก
4. **ข้อจำกัดของ AI:** Gemini Free Tier มี Rate Limit ถ้าอาจารย์กดรัวๆ ตอน Demo ระบบอาจจะค้างได้

## 2. เกณฑ์การแบ่งความสำคัญ

เพื่อแก้ปัญหาข้อจำกัดด้านบน เราจะแบ่งฟีเจอร์ออกเป็น 3 กลุ่ม:
* 🏆 **P1-CORE (ต้องโชว์อาจารย์):** ฟีเจอร์หลักที่ "ต้องทำงานได้จริง" และเห็นภาพรวมตั้งแต่ต้นจนจบ (Demo-able)
* 🏗️ **P1-INFRA (ต้องทำ แต่ไม่ต้องโชว์):** ระบบหลังบ้านที่ต้องเขียนไว้แต่แรก (เช่น Security, Database, จัดการ Error) อาจารย์ไม่ต้องเห็นหน้าตาก็ได้
* 🚀 **P2 (ทำเทอมหน้า):** ฟีเจอร์เสริมความหล่อ ถ้า P1 ยังไม่เสร็จ ห้ามแตะพวกนี้เด็ดขาด
* ✂️ **CUT (ตัดทิ้ง):** ฟีเจอร์ที่อันตรายเกินไป หรือเกินเบอร์ระดับ ป.ตรี (จะเขียนอธิบายในเล่มเฉยๆ ว่าทำไมถึงไม่ทำ)
## 3. การแบ่ง Scope P1: Core vs Infrastructure (The "Real" MVP)

ปัญหาหลักของเอกสารก่อนหน้าคือ P1 มีถึง 11 Feature Groups ซึ่งเข้าข่าย "Scope Overload" (กว้างเกินไปจนไม่จบ) ในทางวิศวกรรมซอฟต์แวร์ Prototype ที่ดีต้องโชว์ End-to-End Flow ได้สมบูรณ์ 100% จึงต้องแบ่ง P1 ออกเป็น 2 ระดับ:
### 🏆 3.1 P1-CORE (End-to-End Demo Flow)
นี่คือ Critical Path ที่ต้องทำงานประสานกัน (Frontend -> Backend -> Template Engine) ให้จบใน Flow เดียว เพื่อโชว์ความสมบูรณ์ของระบบ:

`[Login] → [Add Device] → [6-Tab Config Builder] → [Jinja2 Preview] → [CIS Scan] → [Plan → Apply Modal]`

**Engineering Challenges & Trade-offs ใน P1-CORE:**
1. **Cross-Tab State Dependencies (ฟอร์ม 6 หน้า):** 
   - *ปัญหา:* การกรอกข้อมูลใน Tab 3 (VLAN) มีผลกระทบต่อ Tab 2 (Interface SVI) และ Tab 4 (Routing)
   - *Solution:* ต้องใช้ Global State Management (เช่น Zustand หรือ Redux) และ **ต้องออกแบบ Schema ของ State ให้เสร็จก่อนเริ่มเขียนโค้ด** (State Architecture Design) เพื่อป้องกันการ Refactor ภายหลัง
2. **Form-to-CLI Rendering Performance:**
   - *ปัญหา:* ถ้ายิง API ไปให้ Backend (FastAPI + Jinja2) ทำการ Render CLI ทุกครั้งที่ User พิมพ์ (Keystroke) จะเกิด HTTP Request Flooding จน Backend ค้าง
   - *Solution:* ต้องใช้เทคนิค **Debouncing** ที่ฝั่ง Frontend (หน่วงเวลา ~400ms หลังพิมพ์เสร็จค่อยยิง API) หรือพิจารณาทำ Client-side Rendering เบื้องต้น

### 🏗️ 3.2 P1-INFRA (Foundation & DevOps)
ส่วนนี้คือ "โครงสร้างพื้นฐาน" ที่ไม่มี UI ให้ Demo แต่ถ้าไม่ทำตั้งแต่ Sprint 0 โปรเจกต์จะพังในระยะยาว (Technical Debt):

1. **Database Migration (Alembic):** 
   - ข้อมูล Device Schema จะเปลี่ยนแน่นอนเมื่อขึ้น P2 (เช่น เพิ่ม Column สำหรับ Discovery) การไม่มี Migration Tool แปลว่าต้อง `DROP TABLE` และสร้างใหม่ทุกครั้ง ข้อมูลทดสอบจะหายหมด
2. **PII Masking Pipeline:**
   - ฟังก์ชันที่ใช้ซ่อนข้อมูล (เช่น `yacryptopan` สำหรับ IP และ Regex สำหรับ Password) ต้องถูกเขียนเป็น Middleware หรือ Pipeline ไว้ก่อน เพื่อเตรียมพร้อมรองรับ AI ใน P2
3. **CORS Middleware & Environment (Secrets):**
   - React (Port 3000) และ FastAPI (Port 8000) จะติดปัญหา Cross-Origin ทันที ต้อง Config CORS ให้ถูกตั้งแต่ต้น (ระวังเรื่อง `allow_credentials=True`)
   - ควบคุม Secrets (`CRYPTOPAN_KEY`, DB URL และค่าลับอื่น) ผ่าน `.env` และ Pydantic Settings; Session Token สร้างแบบสุ่มต่อการ Login จึงไม่มี JWT Signing Key
4. **Testing Strategy (Pytest / Jest):**
   - การเขียน Template จำนวนมาก (Jinja2) มีความเสี่ยงเรื่อง **Command Order** (ลำดับคำสั่ง เช่น ต้องสร้าง VLAN ก่อนค่อย Assign Interface) 
   - ต้องทำ Template Integration Test เพื่อเช็คว่า CLI Output ออกมาเรียงลำดับคำสั่งถูกต้องตามหลักของ Cisco IOS หรือไม่

## 4. Feature Evaluation & Engineering Justifications
การประเมินนี้ใช้หลักการ Risk-Reward Ratio และขีดจำกัดทางเทคนิค (API Limits, Hardware Variance, Complexity) เป็นตัวตัดสิน

### 4.1 Configuration Generation (อ้างอิงหมวด 5)

หัวใจของโปรเจกต์นี้คือการสร้าง Config ที่นำไปใช้ได้จริง ไม่ใช่แค่แชทบอทตอบคำถาม
#### **Template-Based (Jinja2) [🏆 P1-CORE]:** 
เป็น Foundation หลักที่ต้องเสถียร 100% ต้องใช้แนวทาง **Conservative Command Set** (เขียน Template โดยใช้คำสั่งพื้นฐานที่รองรับ IOS 12.x ขึ้นไป) เพื่อป้องกันปัญหา Version Incompatibility กับ Hardware ที่ยืมมา

เมื่อผ่านการประเมิน Weight แล้ว สถานะของมันคือ **🏆 P1-CORE (ต้องโชว์อาจารย์แบบสมบูรณ์ที่สุด)** แต่... มันไม่ได้รอดแบบ 100% รูปแบบเดิมครับ มันมีการ **"ซอยย่อย (Split) ลึกระดับ Field"** เพื่อให้ทำทันใน 1 เทอม

นี่คือบทสรุปของ 5.1 ว่าเหลืออะไรให้เขียนโค้ดบ้างครับ:

##### 🏆 **1. สิ่งที่รอดและต้องทำให้เสร็จใน P1 (Core Engine)**

- **Form-to-CLI Rendering:** (พิมพ์ฟอร์มปุ๊บ แปลงเป็นโค้ดปั๊บ) อันนี้คือสิ่งที่อาจารย์จะได้เห็นตอน Demo แน่นอน (เป็นฟอร์ม 6 หน้า หรือ 6-Tab) แต่ในทางวิศวกรรม (Engineering) ฝั่ง Frontend ต้องทำระบบ **Debouncing** (พิมพ์เสร็จหน่วงเวลา 400ms ค่อยยิง API) เพื่อกันเซิร์ฟเวอร์พัง
- **Jinja2 Template Engine:** เราจะใช้ Jinja2 ฝั่ง Backend (Python) เป็นตัวผูกข้อมูล
- **Multi-Vendor (เฉพาะ Basic):** รองรับโครงสร้างคำสั่งพื้นฐาน (Conservative Command Set) เพื่อให้ชัวร์ว่าเอาไปยิงใส่อุปกรณ์รุ่นเก่าที่มหาลัยให้ยืม แล้วอุปกรณ์จะไม่เอ๋อ

---

##### 🔪 **2. การซอยย่อย Config Items (แบ่งว่า Template ไหนทำ P1, อันไหน P2)**

เพื่อให้โปรเจกต์เสร็จทัน เราเอาตาราง Config ที่คุณลิสต์ไว้มาหั่นแบ่งตามความสำคัญและผลกระทบ (Impact) ดังนี้:

**หมวดที่ต้องเขียน Template ให้เสร็จใน P1:** (พวกนี้คือเบสิค Network ถ้าขาดไปทำงานไม่ได้)

- **System/Service:** ชื่อเครื่อง (Hostname), เปิด/ปิด LLDP, ป้ายประกาศ (Banner), เปิด SSH
- **Interface & VLAN:** จ่าย IP, ทำ Access/Trunk Port, สร้าง VLAN, ทำ SVI
- **Routing & DHCP:** Static Route, Default Route, และ DHCP Pool (แจก IP)
- **Security (แบบง่าย):** รหัสผ่านเข้าเครื่อง (Enable secret), `service password-encryption`

**หมวดที่ถูกเลื่อนไป P2:** (พวกนี้ทำยาก โค้ดยาว และมีความซับซ้อนสูง)

- 🚀 **Advanced Routing:** OSPF, RIP
- 🚀 **Advanced Security:** ACL (Access Control List), Port Security
- 🚀 **NAT:** การทำ Network Address Translation

---

##### ✂️ **3. สิ่งที่โดน CUT (ตัดทิ้งแบบถาวร)**

- ❌ **Complex Multi-Vendor Policy:** การเขียนเงื่อนไขที่ซับซ้อนข้ามยี่ห้อแบบแปลกๆ (อันนี้โดนตัดทิ้งเพราะเกินสโคป และเสี่ยงเวลาเอา AI มาช่วยวิเคราะห์ในอนาคตครับ)

**สรุปภาพรวม:** ในเทอม 1 ทีม Frontend และ Backend จะต้องทุ่มเทเวลาเกินครึ่งให้กับหมวด 5.1 นี้ครับ เพื่อทำหน้าฟอร์ม 6 หน้าให้กรอกง่ายที่สุด และแปลงออกมาเป็น Config (Jinja2) ของกลุ่มพื้นฐานให้เสถียรที่สุด

**ถ้าหมวด 5.1 พื้นฐาน (P1) พัง... P2 ทั้งหมดจะเกิดไม่ได้เลยครับ!**

####  **AI-Powered Config & AI Review [🚀 P2]:** 

###### 🚀 **"ถูกยกยอดไปทำใน P2 (เทอม 2) ทั้งยวงครับ!"** 🚀

ไม่ว่าจะเป็นฟีเจอร์ "การพิมพ์สั่งแชทบอทให้เขียน Config" หรือ "การให้ AI ช่วยตรวจ (Review) Config" ทั้งหมดนี้ **จะไม่ได้ทำในเทอม 1 (P1) เลยแม้แต่นิดเดียวครับ**

เหตุผลทางวิศวกรรมระดับคริติคอลที่ต้องผลัก AI ไปอยู่เทอม 2 มีดังนี้ครับ:

**1. ความเสี่ยงเรื่อง API Rate Limit ระหว่างพรีเซนต์ (The Demo Killer)**

- โมเดลที่เราใช้คือ Gemini 1.5 Flash (แบบ Free Tier) ซึ่งมีข้อจำกัดเรื่องจำนวน Request ต่อนาที
- ลองจินตนาการภาพว่า ตอนกำลังพรีเซนต์โปรเจกต์ อาจารย์กรรมการบอกว่า _"ไหนลองสั่ง AI รัวๆ ให้ดูหน่อยสิ"_ แล้วระบบขึ้น Error `429 Too Many Requests`... งานงอกแน่นอนครับ! ดังนั้นใน P1 เราจึงโฟกัสที่ระบบ Template (Offline) ให้ชัวร์ก่อน 100%

**2. ความเสี่ยงที่ AI จะมั่ว (Hallucination)**

- การให้ AI เจนคำสั่ง Network ตรงๆ มีความเสี่ยงสูงมากที่จะได้คำสั่งที่อุปกรณ์ (Cisco รุ่นเก่า) ไม่รู้จัก ถ้าเผลอเอาไปรัน อุปกรณ์อาจจะค้าง (Brick) ได้
- ดังนั้น ใน P1 เราต้องไปทำโครงสร้างพื้นฐาน (P1-INFRA) ที่เรียกว่า **"AI Guardrails (กรอบป้องกัน AI)"** ให้เสร็จก่อน เช่น การดึง Context จาก Database ไปบังคับ AI ว่าต้องใช้คำสั่งตระกูลไหน พอโครงนี้แน่นแล้ว เทอม 2 (P2) ค่อยเอา AI มาต่อยอดครับ

**3. ให้อาจารย์เห็นว่าเราเป็น "วิศวกร" ไม่ใช่แค่ "คนเรียกใช้ API"**

- ปรัชญาหลักของคุณคือ _"ใช้ AI เมื่อต้องการความเข้าใจ ไม่ใช้เมื่อต้องการความถูกต้อง"_
- การที่เราทำระบบ Rule-based (Jinja2 Template) ใน P1 ก่อน เป็นการบอกกรรมการว่า **"ระบบเราทำงานได้อย่างสมบูรณ์แบบโดยไม่ต้องง้อ AI"** (Offline Mode) ส่วน AI เป็นแค่ "ตัวช่วย (Co-pilot)" เสริมหล่อใน P2 เท่านั้น

**สรุปคือ:** ใน P1 หน้าต่างแชท AI จะยังไม่ต้องโผล่มาเลยครับ ปล่อยให้มันไปเฉิดฉายใน P2 เต็มๆ หลังจากที่ระบบหลัก (Template) ของเราแข็งแกร่งจนล้มไม่ลงแล้วครับ!

อ้างอิงจากไฟล์ Weight List ฉบับสุดท้าย ฟีเจอร์ AI เหล่านี้จะถูกแบ่งชะตากรรมออกเป็น **2 กลุ่มชัดเจน** ครับ:

---

##### 🚀 **กลุ่มที่ 1: "ทำใน P2" (AI ที่เป็นผู้ช่วยที่ดี)**

กลุ่มนี้ทำได้จริง เป็นไปได้ และโชว์กรรมการได้สวยงาม:

1. **Chat AI / Natural Language Config Gen:** แชทสั่งงานให้ AI ร่าง Config ให้ (แต่รันผ่าน Prompt Guardrails)
2. **AI Config Review ("Ask AI to Review"):** ให้ AI ช่วยตรวจโค้ดที่เราเขียนจาก 6-Tab ว่ามีตรงไหนผิดหลัก Best Practice ไหม

---

##### ✂️ **กลุ่มที่ 2: "ตัดทิ้งถาวร (CUT)" (ห้ามแตะเด็ดขาด!)**

กลุ่มนี้คือกลุ่มอันตราย ถ้าฝืนทำมีความเสี่ยงที่ระบบจะพัง หรือ AI ตอบมั่ว (Hallucination) สูงมาก:

1. ❌ **Complex Multi-Vendor Policy:** _(ระบุชัดเจนในข้อ 7.3)_ การเอา AI ไปเขียน Policy ข้ามค่าย (เช่น สั่งทีเดียวให้แก้ทั้ง Cisco, Huawei, MikroTik ด้วย Logic เดียวกัน) มีความเสี่ยงที่ AI จะมั่ว Syntax สูงเกิน 90%
2. ❌ **Automated Risk Assessment:** _(ระบุชัดเจนในข้อ 7.3 เรื่อง Cross-Device Impact)_ ถ้าจะให้ AI ประเมินความเสี่ยงได้ถูกต้อง มันต้องเข้าใจ "ภาพรวม" ทั้ง Topology ซึ่งแปลว่าคุณต้องสร้าง Routing Simulator ขึ้นมาหลังบ้านด้วย... อันนี้โปรเจกต์ระดับ ป.เอก เลยครับ! ตัดทิ้งด่วน
3. ❌ **Legacy/Unsupported Device Fallback:** ให้ AI "เดา" คำสั่งสำหรับอุปกรณ์เก่ามากๆ ที่ไม่มีคู่มือ... เสี่ยงทำอุปกรณ์มหาลัยพัง (Brick) ชนิดกู่ไม่กลับครับ เราใช้หลักการ Conservative (ใช้คำสั่งมาตรฐานที่ปลอดภัยเท่านั้น) ดีกว่าครับ
4. ❌  การทำ **MOP (Method of Procedure) Generation & Auto-Documentation** ในโลกความเป็นจริง (Enterprise) มันคือเรื่องสำคัญของการทำ Change Management (เอกสารขออนุมัติผู้บริหารก่อนเปลี่ยน Config) ทำแล้วได้อะไรไหม? คำตอบคือ **ไม่เลยครับ** อาจารย์ไม่ได้อยากเห็นแอปของคุณพิมพ์รายงานเก่ง แต่อยากเห็นแอปของคุณควบคุม Network ได้เจ๋งและปลอดภัยแค่ไหน

ดังนั้น ผมขอสนับสนุนให้ **"หั่นทิ้ง (CUT) ไปเลยครับ!"** ✂️

**บทสรุปคือ:** ใน P2 เราจะใช้ AI **"เฉพาะในเรื่องที่ AI ถนัด (สรุปข้อความ, แนะนำ, ร่างโค้ดเบื้องต้น)"** แต่เราจะ **ไม่ใช้ AI ไปประเมินความเสี่ยง หรือกำหนด Policy ที่ซับซ้อน** เพราะถ้าเน็ตมหาลัยล่มเพราะ AI มั่ว คนซวยคือเราครับ ไม่ใช่ AI!

**รายละเอียด Config Items ที่ต้องทำ Template (อ้างอิงลำดับความสำคัญ):**

| Config Category | Items | Priority |
|---|---|---|
| **System/Service** | Hostname, LLDP/CDP Toggle, Banner, SSH enable | 🏆 P1 |
| **Interface & VLAN** | IP+Mask, Access/Trunk, Create VLAN, SVI IP | 🏆 P1 |
| **Routing & DHCP** | Static, Default Route, DHCP Pool | 🏆 P1 |
| **Security (Basic)** | Enable secret, Console PW, `service password-encryption` | 🏆 P1 |
| **Advanced** | OSPF, RIP, ACL, NAT, Port Security | 🚀 P2 |

### 4.2 Configuration Deployment (อ้างอิงหมวด 7)
เป็นจุดที่ **"อันตรายและเสี่ยงที่สุด"** ในโปรเจกต์เครือข่ายเลยครับ เพราะถ้าพิมพ์คำสั่งผิดแม้แต่ตัวเดียว (เช่น `switchport trunk allowed vlan 10` ลืมคำว่า `add`) อุปกรณ์อาจจะหลุดจากเน็ตเวิร์ก (Brick) ทันที

ดังนั้น เมื่อผ่านการ Weighting แล้ว หมวดนี้จึงถูก **หั่นครึ่ง (Split) และตัดส่วนที่อันตรายเกินไปทิ้ง** ดังนี้ครับ:
#### 🏆 **1. สิ่งที่รอดใน P1-CORE (ทำแค่ UI / การจำลอง)**

- **Plan → Apply UI Workflow (Flow การกดยืนยัน):**
    - ใน P1 เราจะทำหน้าจอ UI ให้สมบูรณ์ที่สุด เมื่อผู้ใช้สร้าง Config จาก 6-Tab เสร็จ กดปุ่ม "Deploy" ระบบจะเด้ง Modal (หน้าต่าง Pop-up) ขึ้นมาสรุปว่า **"คำสั่งเหล่านี้กำลังจะถูกส่งไปที่อุปกรณ์ตัวไหนบ้าง (Plan)"** และมีปุ่มให้กด "Confirm Apply"
    - **จุดสำคัญ:** ในเทอม 1 (P1) พอกด Confirm ปุ๊บ ระบบอาจจะแค่แสดงสถานะเป็น `Success (Simulated)` แต่ **ยังไม่ส่ง SSH ไปที่อุปกรณ์จริงๆ** ครับ (ทำเพื่อโชว์ Flow ให้จบกระบวนการเฉยๆ)
#### 🚀 **2. สิ่งที่ถูกยกยอดไป P2 (การลงมือทำจริงผ่าน Netmiko)**

*  **SSH Command Push (การส่งคำสั่งจริง):**
    - โค้ดหลังบ้าน (Python + Netmiko) ที่ทำหน้าที่วิ่งเข้าไป Mange อุปกรณ์จริงๆ ถูกยกไป P2 ทั้งหมด
    - **เหตุผล:** การทดสอบโค้ดยิง SSH จำเป็นต้องมี **GNS3 Lab (Network Simulator)** ที่เสถียรเพื่อเอาไว้ทดลองยิงคำสั่งให้มั่นใจก่อน เราไม่สามารถเขียนโค้ดแล้วเอาไปยิงใส่อุปกรณ์จริงที่มหาลัยให้ยืมได้เลย เพราะถ้าอุปกรณ์พัง (ตั้งค่าผิดจนเข้าไม่ได้) เราจะไม่มีอุปกรณ์ใช้สอบครับ ดังนั้นเซฟตัวเองด้วยการทำใน GNS3 เทอมหน้าดีกว่า
* **Write Memory (บันทึก Config):**
    - เลื่อนไปเทอม 2 (มันเป็นเงาตามตัวของข้อ 2 ถ้าเรายังไม่ยิงคำสั่งใน P1 เราก็ยังสั่ง `write mem` หรือ `copy run start` ไม่ได้ครับ)
* **Multi-Device Batch Deploy:**
    - เลื่อนไปเทอม 2 การยิงทีละเครื่องยังเสี่ยง การทำลูป (Loop) หรือ Thread ยิงพร้อมกัน 10 เครื่อง ต้องรอให้ข้อ 2 นิ่งสนิท 100% ก่อนถึงจะเริ่มทำได้ครับ
* **Real-time Deploy Logs:**
    - เลื่อนไปเทอม 2 เพราะมันคือการ Streaming text กลับมาจาก Netmiko ขณะกำลังส่งคำสั่ง (ใน P1 จะยังไม่มี Log ตัวนี้โชว์ เพราะยังไม่ได้ยิงจริง)
    
#### ✂️ **3. สิ่งที่โดน CUT ทิ้ง (ห้ามทำเด็ดขาด)**

- ❌ **Auto-Rollback on Error (ระบบดึง Config กลับอัตโนมัติเมื่อพัง):**
    - **ทำไมถึงตัด:** ใน Database ถ้ายิง SQL ผิด เราสามารถสั่ง `Rollback` ได้เพราะมันเป็นระบบ Atomic Transaction **แต่ใน Router/Switch รุ่นเก่าของ Cisco (IOS) มันไม่มีระบบ Rollback อัตโนมัติครับ!**
    - ถึงแม้ Cisco จะมีคำสั่ง `configure replace` แต่มันก็ไม่เสถียรในอุปกรณ์รุ่นเก่าๆ ถ้าเราฝืนเขียนโค้ด Auto-Rollback มันมีโอกาสสูงมากที่ระบบจะพยายามย้อนกลับแล้วพังหนักกว่าเดิม ดังนั้น **ตัดทิ้ง** ให้เป็นหน้าที่ของคน (Manual Recovery) ปลอดภัยกว่าครับ
* ❌ **Idempotency Check (เช็คซ้ำก่อนยิง):**
    - **ขอแนะนำให้ ตัดทิ้ง (CUT) ถาวรครับ!**
    - **เหตุผลทางวิศวกรรม:** คำว่า Idempotency (รันกี่ครั้งผลก็เหมือนเดิม) เป็นฟีเจอร์ระดับเทพของระบบอย่าง Ansible หรือ Terraform การจะทำแบบนั้นได้ แปลว่าระบบคุณต้อง **"ดึง Running Config ลงมา -> วิเคราะห์ (Parse) ทุกบรรทัด -> เทียบกับคำสั่งใหม่ (Diff) -> ตัดคำสั่งที่ซ้ำออก"**
    - การทำ Text Parsing บน Cisco CLI แบบเป๊ะๆ 100% เป็นเรื่องยากระดับปราบเซียน (แม้แต่บริษัทยักษ์ใหญ่ยังปวดหัว) สำหรับสโคป ป.ตรี การพยายามทำ Idempotency จะสูบเวลาของทีมไปจนหมดครับ ให้ใช้วิธี **"เตือน User ให้เช็คเอง (Human Validation)"** ดีกว่าครับ
### 4.3 Security Compliance & Validation (อ้างอิงหมวด 8)
ถือว่าเป็น **"Killer Feature" (จุดขายหลัก)** ที่จะทำให้โปรเจกต์ของคุณโดดเด่นกว่ากลุ่มอื่นเลยครับ แต่เพื่อความสมจริงในการพัฒนา มันถูกจับมา "ปรับจูน" น้ำหนักใหม่ดังนี้ครับ:
#### 🏆 **8.1 CIS Benchmark Scanning: "รอดเป็น P1-CORE แต่ถูกลดสเกล (Scale Down)"**

จากเดิมที่คุณตั้งเป้าไว้ว่าจะทำถึง "24 Rules (กฎ)" ซึ่งมันใหญ่เกินไปและบางกฎเขียนโค้ดเช็คได้ยากมาก สำหรับโปรเจกต์ 1 เทอม เราจึงปรับให้เหลือ **"8 Core Rules (กฎหลัก)"** ครับ

**ทำไมถึงลดเหลือ 8 ข้อ?**

- เพราะเราต้องการ **"Risk-Reward Ratio" (ลงทุนน้อยแต่ได้ผลลัพธ์ว้าว)**
- กฎ 8 ข้อที่เราเลือกมา (เช่น การเช็ค `enable secret`, การปิด `telnet`, การบังคับใช้ `ssh version 2`) เป็นกฎที่มี Impact สูงมากในโลก Network Security
- และในทางวิศวกรรม (Engineering) การเขียน Regular Expression (Regex) เพื่อดักจับ 8 ข้อนี้บนหน้าเว็บ ถือว่าทำได้เสร็จไวและนำไปโชว์ตอน Demo ได้อย่างสวยงามครับ (ระบบฟ้องเป็นแถบสีแดง/สีเขียวได้เลย)

#### ✂️ **8.2 Impact Analysis (ประเมินผลกระทบ): "ถูกตัดทิ้งถาวร (CUT) ครับ!"**

โดนหั่นทิ้งแบบไม่ต้องสงสัยเลยครับ! เหตุผลคือ:

- คำว่า Impact Analysis หมายถึง _"ถ้ายุ่งกับ Router ตัวนี้ แล้ว Switch อีก 3 ตัวข้างหลังจะเน็ตหลุดไหม?"_
- การจะให้คอมพิวเตอร์ตอบคำถามนี้ได้ โปรแกรมของคุณต้อง **"สร้าง Network Simulator ขนาดย่อมๆ หรือใช้ Graph Database"** เพื่อประมวลผลเส้นทาง Routing ทั้งระบบ (เหมือนที่แอปพลิเคชันระดับโลกอย่าง Batfish ทำ)
- ความซับซ้อนของมันเกินกว่าสโคป ป.ตรี ไปไกลมากครับ ถ้าฝืนทำ ทีมของคุณจะจมอยู่กับบั๊กจนทำฟีเจอร์หลัก (Config Builder) ไม่เสร็จ

**กฎ CIS 8 ข้อหลักที่ต้องใช้ Regex Scan ใน P1:**

| # | Rule | Severity | Implementation |
|---|---|---|---|
| 1 | `enable secret` ต้องมี | 🔴 Critical | เช็ค Regex `enable secret` |
| 2 | `service password-encryption` ต้องเปิด | 🔴 Critical | เช็ค Regex บรรทัดนี้ |
| 3 | `ip ssh version 2` ต้องบังคับ | 🔴 Critical | เช็ค Regex บรรทัดนี้ |
| 4 | Telnet ต้องปิด | 🔴 Critical | เช็ค `no transport input telnet` |
| 5 | `ip http server` ต้องปิด | 🟡 Warning | เช็ค `no ip http server` |
| 6 | SNMP Community ≠ `public`/`private` | 🟡 Warning | เช็คค่า Community String |
| 7 | VTY Line ต้องมี `access-class` | 🟡 Warning | เช็ค Access-class บน VTY |
| 8 | Banner MOTD ต้องมี | 🔵 Info | เช็ค `banner motd` |
**สรุปภาพรวมหมวด 8:** อาจารย์จะได้เห็นแอปของคุณสามารถ **"สแกนหาช่องโหว่ความปลอดภัยพื้นฐานได้ 8 จุดแบบอัตโนมัติ" (P1-CORE)** ซึ่งแค่นี้ก็เพียงพอที่จะดึงคะแนนความว้าวได้แล้ว โดยที่เราไม่ต้องเอาตัวไปเสี่ยงกับการเขียน AI วิเคราะห์ผลกระทบระดับเทพ (Impact Analysis) ที่ไม่มีทางทำเสร็จทันครับ!

### 4.4 AI Architecture & Guardrails (อ้างอิงหมวด 10)
สถาปัตยกรรมการนำ AI มาใช้ ต้องทำด้วยความระมัดระวัง (Safety-first)
* **Context Injection [🏆 P1-CORE]:** ใช้ฐานข้อมูล (PostgreSQL) เป็นตัวฉีด Context (Device Info, Running Config) เข้าไปใน System Prompt แทนที่จะใช้ RAG
* **RAG / Vector Database / spaCy NLP [✂️ CUT]:** ตัดทิ้งทั้งหมด RAG ก่อให้เกิด Overhead ในการเตรียมข้อมูลเอกสาร (Data Ingestion) มากเกินไป ในขณะที่ Context Injection ผ่าน DB Query สามารถให้ Runtime Context ที่แม่นยำกว่า และเปลี่ยนจากการใช้ spaCy NLP มาใช้ Regex + `yacryptopan` ในการทำ PII Masking แทน ซึ่งเบาและเร็วกว่ามาก
* **Human-in-the-Loop [🏆 P1-CORE]:** หลักการสำคัญคือ AI จะเป็นเพียง Co-pilot เท่านั้น ผู้ใช้ (Human) ต้องเป็นคนกด "Confirm Apply" ทุกครั้ง AI ไม่มีสิทธิ์ Execute คำสั่งลง Network โดยตรง
### 4.5 Authentication & Authorization (อ้างอิงหมวด 1)
แต่สิ่งที่เปลี่ยนไปคือ **"สถานะและการโฟกัส"** ของหมวดนี้ครับ โดยในไฟล์ Weight List ล่าสุด หมวดนี้ถูกจัดให้อยู่ในกลุ่ม 🏗️ **P1-INFRA (โครงสร้างพื้นฐานหลังบ้าน)** ซึ่งหมายความว่า:

> **Architecture Update (2026-08-27):** เปลี่ยนจาก Stateful JWT เป็น Database-backed Opaque Server-side Session เพราะแบบเดิมต้อง Query `auth_sessions` ทุก Request อยู่แล้ว จึงไม่ได้ประโยชน์ Stateless และ Session แบบ Opaque ลดความซับซ้อนพร้อม Revoke ได้ทันที

1. **Login Page & Inline Error:** ยังต้องทำเหมือนเดิม เพื่อให้หน้าเว็บสมบูรณ์
2. **Opaque Server-side Session (HttpOnly Cookie):** ต้องทำตั้งแต่วันแรก (Sprint 0) โดย Browser ถือ Token สุ่ม ส่วน Backend เก็บเฉพาะ Token Hash ใน `auth_sessions`
3. **RBAC (แบ่ง 3 Roles - Admin, Operator, Viewer):** ยังต้องทำ เพื่อป้องกันคนแก้ Config มั่ว

**ทำไมถึงไม่โดนตัด และทำไมถึงอยู่แค่ P1-INFRA?**

- **ไม่โดนตัดเพราะ:** ระบบต้องมี Login, Server-side Session และ RBAC ที่บังคับใช้ฝั่ง Backend มิฉะนั้น Protected API จะไม่มีขอบเขตความปลอดภัย
- **ไปอยู่ P1-INFRA เพราะ:** ฟีเจอร์นี้เป็นสิ่งที่ "ต้องมี" แต่ **"ไม่ได้มีความว้าวทาง Engineering ที่จะเอาไปเป็นจุดขายหลักตอน Demo"** (อาจารย์เห็นหน้า Login ก็เฉยๆ เพราะใครๆ ก็ทำได้) ดังนั้นเราเลยจับมันไปอยู่หลังบ้าน คือบอกอาจารย์ว่า "เราทำนะ ปลอดภัยด้วย" แต่ตอน Demo (P1-CORE) เราจะรีบล็อกอินผ่านๆ ไปให้เร็วที่สุด เพื่อเอาเวลาไปโชว์ความว้าวของ 6-Tab Config Builder และ CIS Security Scan แทนครับ

สรุปคือ **หมวด 1 Auth & RBAC ได้ทำครบทุกฟีเจอร์ย่อยครับ แค่ถูกลดแสงไฟส่องหน้าลง เพื่อไปส่องฟีเจอร์หลักแทน** 
### 4.6 Dashboard & Monitoring (อ้างอิงหมวด 2)

ในไฟล์ Weight Feature List หมวดนี้ถูกจัดให้อยู่ในกลุ่ม 🏗️ **P1-INFRA** (ความเสี่ยง 🟢 Low) โดยรายละเอียดฟีเจอร์ย่อยทั้ง 4 ตัวที่ยังคงอยู่ครบ มีดังนี้ครับ:

1. **Metrics Cards (การ์ดสถิติ):** รอดแน่นอน เพราะใช้แค่ SQL Query เบาๆ เพื่อนับจำนวน Device, สถานะ Online/Offline, จำนวน Config, และ CIS Failures จาก Database (FastAPI ดึงข้อมูลแป๊บเดียวเสร็จ)
2. **Recent Activity Feed:** รอดครับ เพราะเป็นการดึงข้อมูล 10 แถวล่าสุดจากตาราง Audit Trail มาแสดงผล (ทำง่ายมาก)
3. **Quick Action Shortcuts:** รอดชัวร์ เพราะเป็นแค่ปุ่มลิงก์ HTML/React ธรรมดาที่กดแล้วพาไปหน้าอื่น
4. **System API Status:** รอดครับ แค่เขียน API Ping หากันเช็คไฟเขียว/ไฟแดง

**เหตุผลเชิงวิศวกรรมที่ Dashboard ไปอยู่ใน P1-INFRA:**

- **มันทำง่ายและเป็น Standard:** Dashboard คือหน้าบ้านที่ทุก Web App ต้องมี การเขียน Frontend (React) ดึงข้อมูลมาโชว์ 4 ส่วนนี้ ถือเป็นงานระดับพื้นฐาน (Basic CRUD & Query)
- **ไม่ต้องเสียเวลา Demo นาน:** ตอนนำเสนอโปรเจกต์ (P1-CORE) หน้า Dashboard เป็นแค่ "ทางผ่าน" ให้กรรมการดูว่าระบบมีหน้าตาสวยงาม ดูสถิติได้จริง แต่กรรมการจะไม่ตื่นเต้นกับหน้านี้เท่าไหร่ สิ่งที่จะทำให้กรรมการว้าวคือ "กระบวนการสร้าง Config (6-Tab)" และ "การสแกน CIS" มากกว่าครับ

**สรุปคือ:** Dashboard ไม่โดนตัดทิ้งเลยครับ ทีม Frontend สามารถออกแบบ UI และขึ้นโครง (Mockup) ตามที่วางแผนไว้ในหน้า "Mockup จากภาพพี่ออม" ได้แบบ 100% เต็มเลยครับ!

### 4.7 Manual Device Enrollment & Management (อ้างอิงหมวด 3)

สำหรับหมวด **`3.1 Manual Device Enrollment & Management (Non-AI)`** ถือว่าเป็นส่วนตั้งต้นของ P1-CORE เพราะระบบต้องมีวิธีรับอุปกรณ์เป้าหมายที่ผู้ใช้ทราบ IP อยู่แล้ว โดยไม่ต้องรอ Network Discovery

เมื่อผ่านการประเมิน (Weight) แล้ว ฟีเจอร์ย่อยใน 3.1 จะถูกจัดสรรดังนี้ครับ:

#### 🏆 🟢 **กลุ่มที่รอด 100% และถูกยกระดับเป็น "P1-CORE" (ต้องโชว์อาจารย์)**

1. **Manual Device Enrollment & Managed Device CRUD:**
    - ผู้ใช้ระบุ Management IP, Protocol/Port, เลือก Device Credential Profile และกรอกข้อมูลประกอบ เช่น Site, Group หรือ Description
    - ระบบต้องเชื่อมต่อแบบ Read-only และเก็บข้อมูลระบุตัวตนขั้นต่ำ เช่น Hostname, Vendor, Model และ OS Version ก่อนสร้างเป็น Managed Device ส่วน Interface และ LLDP/CDP Neighbor Collection ขยายเพิ่มใน P2 เมื่อทำ Discovery/NTV
    - ข้อมูลที่มาจากอุปกรณ์ต้องปรับปรุงผ่าน Collection ไม่ให้ผู้ใช้แก้เป็นข้อมูลยืนยันโดยตรง
    - Device CRUD หมายถึงการจัดการ Record และข้อมูลประกอบใน MyNetMate การลบ Record ไม่ได้ลบหรือเปลี่ยน Configuration ของอุปกรณ์จริง
2. **Device Reachability & Collection Status:**
    - Ping ใช้บอก Reachability เบื้องต้นเท่านั้น การตอบ Ping ไม่ได้ยืนยันว่าเป็น Router/Switch หรือแปลว่า Collection สำเร็จ
    - ระบบถือว่าอุปกรณ์พร้อมใช้งานเป็น Managed Device เมื่อ Authentication, Read-only Collection และการ Parse ข้อมูลสำคัญสำเร็จตามเกณฑ์

#### 🏗️ 🟢 **กลุ่มที่รอด แต่อยู่เบื้องหลัง "P1-INFRA"**

3. **Device Grouping (การจัดกลุ่มตาม Site/Vendor):**
    - **รอดครับ:** ฟีเจอร์นี้ไม่ต้องพรีเซนต์ให้ดูหวือหวา แต่มันอยู่ใน P1-INFRA เพราะเราต้อง **ออกแบบ Database Schema (Alembic)** ให้รองรับ Column พวก Site หรือ Role ไว้ตั้งแต่วันแรก (Sprint 0) เพื่อเตรียมพร้อมดึงไปจัดกลุ่มในอนาคต

#### 🟡 **กลุ่มที่อาจจะถูกลดระดับความสำคัญ (P2 หรือ Nice-to-have)**

4. **Running-Config Upload (อัปโหลดไฟล์ Config เดิม):**

    - **คำแนะนำทางวิศวกรรม:** ถ้าทำทันใน P1 ก็ทำได้เลยเพราะแค่สร้างปุ่ม Upload Text File ลง Database แต่ถ้าเวลาจำกัด **ฟีเจอร์นี้สามารถปัดไป P2 ได้อย่างปลอดภัย** เพราะมันไม่กระทบกับ End-to-End Flow หลักของการ Demo ครับ

### 4.8 Network Discovery (อ้างอิงหมวด 3)

#### 🚀 **"ถูกยกยอดไปอยู่ P2 (เทอมหน้า) ทั้งหมวดแบบ 100% ครับ!"** 🚀

ฟีเจอร์ย่อยทั้งหมดในหมวดนี้ ไม่ว่าจะเป็น:
* IP Range Ping Sweep (กวาดหา IP)
* SNMP sysDescr Polling (ดึงชื่อ Vendor/Model)
* LLDP/CDP Neighbor Discovery (หาเพื่อนบ้าน)
* OS Fingerprinting (เดา OS)
* 3-Stage Discovery Pipeline (สถาปัตยกรรมหลังบ้าน)

**ทั้งหมดนี้จะไม่ถูกทำใน P1 (CE Project 1) เลยครับ** แต่จะถูกเก็บไว้เป็นฟีเจอร์ไม้ตายใน P2 ด้วยเหตุผลทางวิศวกรรม (Engineering Justifications) ที่แข็งแรงมาก 3 ข้อหลักๆ ดังนี้ครับ:

1. **🚨 ความเสี่ยงเรื่อง Network มหาลัย (The Blocker):**
   - การทำ IP Range Ping Sweep มีพฤติกรรมคล้ายกับพฤติกรรมของ Hacker (Network Scanning) ซึ่งระบบ Firewall ของมหาวิทยาลัยจะ **Block** และอาจแบน IP เครื่องของคุณทันที ถ้าทำใน P1 แล้วเกิดปัญหาตอน Demo งานจะเข้าทันทีครับ (ตามที่เขียนไว้ใน Top 5 Risks ข้อ 3)
2. **❌ ไม่ใช่ Critical Path ของการ Demo:**
   - จุดขายหลักใน P1 คือ **"การสร้างและตรวจสอบ Config (Template + CIS)"** ดังนั้น Manual Device Enrollment ซึ่งให้ผู้ใช้ระบุ Management IP และ Credential Profile แล้วให้ระบบเก็บข้อมูลจากอุปกรณ์เป้าหมาย จึงเพียงพอสำหรับเริ่ม Flow โดยไม่ต้องทำการค้นหา IP อัตโนมัติใน P1
3. **⛓️ มันคือคอขวดที่ไปผูกกับ Feature 4 (Topology):**
   - ฟีเจอร์ Topology (การวาดแผนผัง) ต้องอาศัยข้อมูลจาก LLDP/CDP ในหมวด 3.2 นี้แหละครับ เมื่อเราดึง 3.2 ไป P2 หมวด 4 (Topology) ก็เลยต้องตามไป P2 ด้วยโดยปริยาย (ทำพร้อมกันในเทอม 2)

**คำแนะนำสำหรับ CE Project 1:** 
เวลาพรีเซนต์ให้อาจารย์ฟัง ให้บอกอย่างมั่นใจเลยครับว่า *"เราได้ออกแบบสถาปัตยกรรม (3-Stage Pipeline) เผื่อไว้สำหรับ Discovery แล้ว แต่ด้วยข้อจำกัดด้านความปลอดภัยของ Network ภายในมหาลัย เราจึงจัด Priority ให้ไปอยู่ใน Phase 2 ซึ่งจะทำการทดสอบบนสภาพแวดล้อมปิด (GNS3) อย่างรัดกุมก่อนนำมาใช้จริงครับ"* 

ตอบแบบนี้รับรองว่าอาจารย์ประทับใจในความเป็น "วิศวกร" ที่ประเมินความเสี่ยงเป็นแน่นอนครับ!


### 4.9 Network Topology Visualization (อ้างอิงหมวด 4)

#### 🚀 **"ถูกยกยอดไปทำใน P2 (เทอม 2) ทั้งหมวดแบบ 100% ครับ!"** 🚀

สาเหตุหลักที่หมวดนี้ไม่ได้อยู่ใน P1 (เทอม 1) เลย ไม่ใช่เพราะมันทำไม่ได้นะครับ แต่เป็นเพราะ **"เหตุผลเรื่อง Dependency (การพึ่งพาข้อมูลกัน)"** ล้วนๆ เลยครับ

อธิบายทางวิศวกรรมคือ:
1. **มันคือผลพลอยได้จาก Discovery:** ฟีเจอร์ที่ว้าวที่สุดของ Topology คือ `Auto-Layout from Discovery` (ให้ระบบลากเส้นโยงให้อัตโนมัติ) แต่เนื่องจากตัว Network Discovery (หมวด 3.2) มันถูกเลื่อนไป P2 แล้ว (เพราะเรื่องติด Block มหาลัย) ทำให้หมวด Topology ขาดข้อมูลตั้งต้น (LLDP/CDP) ที่จะเอามาวาดเส้นครับ
2. **ถ้าไม่มี Observation จะเหลือเพียง Canvas ว่าง:** การให้ผู้ใช้สร้าง Device/Port หรือวาด Link อย่างอิสระจะทำให้ NTV กลายเป็นโปรแกรมวาด Diagram และข้อมูลอาจไม่ตรงกับเครือข่ายจริง จึงไม่ทำ Freehand Link หรือ Manual Override ใน NTV MVP หาก LLDP/CDP ใช้ไม่ได้ ระบบแสดง Collection/Parser Status หรือ Unresolved/Empty State และให้ผู้ใช้ Re-collect ส่วน Evidence-based Manual Override เก็บเป็น Future Enhancement หลังประเมินผลทดสอบอุปกรณ์จริง
3. **โฟกัสผิดจุด:** หัวใจของ P1 คือ **"การสร้าง Config"** ครับ การเอาเวลา 2-3 สัปดาห์ไปนั่งเขียนโค้ด React วาดรูป อาจจะทำให้เวลาทำระบบ Config Builder (หน้าฟอร์ม 6-Tab) ไม่พอครับ

**สรุปคือ:** 
ฟีเจอร์ย่อยทั้งหมด ทั้ง Interactive Canvas, ไอคอนอุปกรณ์, เมนูคลิกขวา, และ Auto-Layout **ถูกรวมเป็นแพ็กเกจใหญ่คู่กับ Discovery เตรียมไว้สำหรับลุยหนักๆ ใน P2 ครับ** (ส่วนฟีเจอร์ PNG Export นั้นโดนคุณตัดทิ้งไปตั้งแต่ต้นทางแล้ว เลยหายวับไปเลยครับ 😆)

### 4.10 PII Sensitive Data Masking (อ้างอิงหมวด 6)

#### 🛡️ **"รอดเป็น P1-INFRA แต่โดนหั่นความซับซ้อนทิ้งครับ!"** 🛡️

หมวดนี้เป็นฟีเจอร์ "ปิดทองหลังพระ" ที่สำคัญมาก เพราะถ้าเราส่งไฟล์ Config ของมหาลัย (ที่มี IP จริงและ Password จริง) ขึ้นไปให้ Gemini ตรงๆ... เรากำลังทำข้อมูลองค์กรรั่วไหลครับ!

ดังนั้น หมวด 6 จึงถูกจับมาอยู่ใน **P1-INFRA** (ต้องทำตั้งแต่วันแรกๆ) แต่มีการปรับเปลี่ยนแนวทางการเขียนโค้ด (Engineering Implementation) ดังนี้ครับ:

#### ✅ **สิ่งที่รอด (ต้องทำใน P1-INFRA)**

1. **IP Address Anonymization (การเข้ารหัส IP):** รอดครับ! เราจะใช้ไลบรารี `yacryptopan` (ที่สืบทอดมาจาก Crypto-PAn) ใน Python ซึ่งมันเจ๋งตรงที่มันเข้ารหัส IP แบบยังคงรักษา Subnet ไว้ (เช่น `192.168.1.10` อาจจะกลายเป็น `10.5.5.10` แต่ AI ยังดูออกว่าเป็นวงเดียวกัน)
2. **Password & Secret Masking (การเซ็นเซอร์รหัสผ่าน):** รอดครับ! พวกบรรทัด `enable secret 5 xxxxx` หรือ `password 7 yyyyy` ระบบเราจะใช้ **Regex (Regular Expression)** ตรวจจับแล้วเปลี่ยนเป็น `[MASKED_PASSWORD]` ให้หมด ก่อนส่งออกอินเทอร์เน็ต

#### ✂️ **สิ่งที่โดน CUT (ตัดทิ้งถาวร)**

- ❌ **spaCy NLP (การใช้ AI แบบวิเคราะห์ภาษาเพื่อหาข้อความสำคัญ):**
    - ในเอกสารเดิมอาจจะมีความคิดที่ว่า "ใช้โมเดล NLP มาช่วยสแกนหาชื่อบริษัท หรือข้อมูลแปลกๆ ใน Config"
    - **โดนตัดทิ้ง 100% ครับ** เพราะโมเดล NLP กินทรัพยากรเซิร์ฟเวอร์หนักมาก (Overhead สูง) ทำให้ระบบตอบสนองช้าเปล่าๆ การใช้แค่ Regex หา Pattern ของ Config (ซึ่งมีรูปแบบตายตัวอยู่แล้ว) ก็แม่นยำและเร็วกว่าแบบคนละเรื่องเลยครับ

**สรุปการทำงานของหมวด 6:** มันจะทำตัวเป็น **"ท่อกรอง (Middleware)"** ใน Backend ครับ สมมติว่าใน P2 คุณพิมพ์แชทให้ AI ตรวจ Config ระบบจะเอา Config ไปวิ่งผ่านท่อ PII Masking นี้ก่อน (IP โดนสับ, รหัสผ่านโดนลบ) แล้วถึงจะยิงออกไปหา Gemini ครับ

เป็นฟีเจอร์ที่ไม่ค่อยมีใครเห็นหน้าตา UI แต่วิศวกร (และอาจารย์) จะประทับใจใน Security Architecture ของคุณแน่นอนครับ!


### 4.11 Version Control & Audit Trail (อ้างอิงหมวด 9)

สำหรับหมวด **`9. Version Control & Audit Trail (ระบบจัดการเวอร์ชันและประวัติการใช้งาน)`** หมวดนี้ถูก **"จับแยกทางกัน (Split)"** ตามความยากง่ายของระบบครับ ผลลัพธ์หลังจากการประเมิน (Weight) ออกมาเป็นแบบนี้ครับ:

#### 🏗️ **1. Audit Trail (เก็บประวัติการใช้งาน): "รอดชิวๆ เป็น P1-INFRA"**

- **สถานะ:** รอด 100%
- **รายละเอียด:** ฟีเจอร์นี้คือการที่ Database (PostgreSQL) จะคอยจดบันทึกว่า _"ใคร (User), ทำอะไร (Action), กับอุปกรณ์ไหน (Device), เมื่อไหร่ (Timestamp)"_ เช่น นาย A กดแก้ไข IP ของ Router-1 เมื่อเวลา 10.00 น.
- **ทำไมถึงรอด:** มันทำง่ายมากครับ แค่เขียนโค้ด Backend (FastAPI) ให้เพิ่มข้อมูลลงตาราง Log ทุกครั้งที่มีคนกดปุ่มเซฟ แถมยังเอาไปโชว์ในหน้า Dashboard (Recent Activity Feed) ได้ด้วย เป็นพื้นฐานที่ระบบใหญ่ๆ ต้องมีครับ
##### 🏆 **กลุ่ม P1 (ทำเทอม 1: เน้น UI และ Database เป็นหลัก)**

- **Side-by-Side Diff & Unified Diff (ดูความต่างของ Config):** 🟢 **P1-CORE**
    - ทำในเทอม 1 ครับ มันจะไปโผล่อยู่ในหน้าจอ "Plan -> Apply" (ตอนก่อนกด Deploy) เพื่อให้ User เห็นว่า Config ที่พิมพ์ในฟอร์มมันแปลงเป็นโค้ดบรรทัดไหนบ้าง (UI/UX)
- **Audit Trail (บันทึก Who/When/What):** 🟢 **P1-INFRA**
    - รอดแน่นอนครับ ตามที่อธิบายไปก่อนหน้านี้ว่ามันคือมาตรฐานความปลอดภัย (ทำผ่าน FastAPI)
- **CIS Override Logging (บันทึกเหตุผลตอนข้ามกฎ):** 🟢 **P1-CORE**
    - ทำคู่กับระบบ CIS Benchmark 8 ข้อใน P1 ครับ สมมติระบบฟ้องว่า "ไม่ได้ตั้งรหัสผ่าน" แต่ User ดึงดันจะ Deploy ให้ได้ ระบบต้องบังคับให้พิมพ์เหตุผล (เช่น _"เอาไว้ทดสอบชั่วคราว"_) แล้วเก็บลง Database ครับ (สำคัญมากตอน Audit)

#### 🚀 **2. Version Control (ระบบย้อนกลับ Config กึ่ง Manual): "ยกยอดไป P2"**

- **สถานะ:** ไปเทอม 2
- **รายละเอียด:** การที่ผู้ใช้สามารถเข้ามาดูได้ว่า Config ของเดือนที่แล้วหน้าตาเป็นยังไง แล้วกดปุ่ม **"Restore / Rollback"** เพื่อให้ระบบเอา Config เก่านั้นกลับไปทับของปัจจุบันบนตัวอุปกรณ์
- **ทำไมถึงไป P2:** เพราะฟีเจอร์นี้มันต้อง **"สั่งยิงคำสั่งเข้าไปที่อุปกรณ์จริง (SSH Command Push)"** ครับ ซึ่งกระบวนการยิงคำสั่งเราตกลงกันไว้แล้วว่าจะเก็บไปทำใน P2 ร่วมกับ GNS3 ดังนั้นฟีเจอร์นี้เลยต้องตามไป P2 ด้วยครับ
##### 🚀 **กลุ่ม P2 (ทำเทอม 2: ผูกกับ Netmiko และ SSH)**

พวกนี้คือกลุ่มที่ต้องวิ่งไปแตะอุปกรณ์จริง (Physical Hardware) จึงต้องรอให้ระบบ SSH นิ่งก่อนในเทอม 2 ครับ:

- **Pre-Deploy Snapshot:** 🚀 **P2** (ต้องสั่ง `show run` ผ่าน SSH ก่อนจะเริ่มยิงคำสั่ง)
- **Post-Deploy Snapshot:** 🚀 **P2** (พอตั้งค่าเสร็จ ก็ต้องยิง `show run` อีกรอบเพื่อถ่ายรูปเก็บไว้)
- **Manual SSH Pull:** 🚀 **P2** (กดปุ่มเพื่อให้ Netmiko วิ่งไปดึง Config ปัจจุบันมาลง Database)
- **One-Click Rollback:** 🚀 **P2** (การกดปุ่มเพื่อยิง Config ชุดเก่ากลับไปทับของใหม่)
#### ✂️ **3. Auto-Rollback on Error (ระบบดึง Config กลับอัตโนมัติเมื่อพัง): "ตัดทิ้งถาวร (CUT)"**

- **สถานะ:** ตัดทิ้ง 100%
- **รายละเอียด:** แนวคิดที่ว่า ถ้าระบบกำลังยิงคำสั่งอยู่แล้วดันมี Error (เช่น ไฟดับ เน็ตตัด หรือคำสั่งผิด) ระบบจะ **ย้อนเวลากลับเองอัตโนมัติ** เหมือนเวลา Database ทำ `ROLLBACK`
- **ทำไมถึงโดนตัด:** อุปกรณ์ Network ยุคเก่า (โดยเฉพาะ Cisco IOS ที่มหาลัยมี) **ไม่มีระบบ Atomic Transaction ครับ** คือถ้าคำสั่งเข้าไปแล้ว มันทำงานเลย ถ้าจะย้อนกลับ ต้องมานั่งไล่พิมพ์คำสั่ง `no ...` สวนกลับไปทีละบรรทัด ซึ่งโค้ดหลังบ้านจะเขียนยากและซับซ้อนระดับโลก (บางอุปกรณ์มีคำสั่ง `configure replace` แต่ก็พึ่งพาไม่ได้ 100%) เราเลยตัดฟีเจอร์นี้ทิ้งเพื่อลดความเสี่ยงที่ระบบจะพังคาตาอาจารย์ครับ

**สรุปคือ:** เทอม 1 เราจะ **"จด"** ทุกอย่างที่ทุกคนทำ (Audit Trail) แต่ถ้าอยาก **"ย้อนเวลา"** (Version Control) ต้องรอเทอม 2 และเราจะ **ไม่ทำ** ระบบย้อนเวลาอัตโนมัติ (Auto-Rollback) ครับ!


### 4.12 AI Architecture (อ้างอิงหมวด 10)
โอ้โห! หมวด 10 นี้นี่คือ "นิยายไซไฟ" ของโปรเจกต์เลยครับ ตอนเขียนร่างแรกคือวาดฝันไว้อลังการมาก (ระดับ Enterprise AI) แต่พอเอาเข้าจริง (มา Weighting) เราต้องเจอโลกแห่งความจริงครับ 😂

นี่คือชะตากรรมของหมวด **10. AI Architecture** หลังผ่านมีดผ่าตัดมาแล้วครับ:

---

#### ✂️ **1. โดนตัดทิ้งถาวร (CUT): "ลาก่อน RAG!"**
- **10.1 RAG (Vector Database, Embedding, Document Sources):** โดนตัดทิ้ง 100% ครับ
- **ทำไมถึงตัด:** การจะทำ RAG ให้เวิร์ค ทีมคุณต้องเสียเวลาเป็นเดือนๆ ไปกับการคลีนไฟล์ PDF ของ Cisco, หั่นคำ (Chunking), ยัดลง Vector DB แล้วผลลัพธ์ก็อาจจะตอบมั่วอยู่ดี เราจึงเปลี่ยนแผนไปใช้ "Context Injection" จาก Database แทน (ดึงแค่ชื่อยี่ห้อ รุ่นจากตาราง Devices มาใช้ก็พอแล้ว เบากว่า ไวกว่า ไม่มั่วด้วย)

---

#### 🏆 **2. รอดเป็นโครงสร้างพื้นฐาน (P1-INFRA): "The Secret Sauce"**
- **10.2 Dynamic System Prompt Engineering:** รอดทั้งหมดครับ!
  - การฉีดข้อมูลหน้างาน (Device Context Injection)
  - การสวมบทบาท (Persona Setting) 
  - การบังคับตอบเป็นกล่อง (Structured Output / JSON)
- **ทำไมถึงรอดใน P1:** แม้แชท AI จะไปอยู่เทอม 2 แต่ "ท่อส่งข้อมูล" พวกนี้ ฝั่ง Backend (FastAPI) ต้องวางโครงสร้างให้เสร็จตั้งแต่เทอม 1 เพื่อเตรียมพร้อมครับ นี่คืออาวุธลับที่จะมาแทนที่ RAG ครับ

---

#### 🚀 **3. ยกยอดไปเทอม 2 (P2): "รอให้แชท AI เกิดก่อน"**
- **Intent Detection & Task Routing (กระบวนการรับคำสั่ง 4 Steps):** ไปอยู่ P2 100% ครับ
- **ทำไมถึงไป P2:** เพราะกระบวนการ 4 Steps นี้ (สแกนคำ -> ดึงข้อมูล -> ส่งให้ Gemini -> เอาไปโชว์) คือเบื้องหลังการทำงานของหน้าต่าง "แชทบอท" ล้วนๆ ครับ ซึ่งเรารู้กันแล้วว่าฟีเจอร์ "สั่งงานด้วยการพิมพ์แชท (Natural Language)" ถูกยกไป P2 ทั้งหมด ดังนั้นหลังบ้านก้อนนี้ก็ต้องตามไป P2 ครับ

---

#### 🛡️ **4. รอดเป็นจุดขายหลัก (P1-CORE / P1-INFRA): "Guardrails"**
- **10.3 Safety Guardrails:** หมวดนี้คือหัวใจความปลอดภัย รอดเกือบหมดครับ!
  - **Human-in-the-Loop:** 🟢 รอด (P1-CORE) มนุษย์ต้องเป็นคนกดปุ่ม Deploy เท่านั้น
  - **PII Pre-Filter:** 🟢 รอด (P1-INFRA) ซ่อน IP/Password ด้วย `yacryptopan` ก่อนส่งออก
  - **Security Gate:** 🟢 รอด (P1-CORE) ต้องสแกนผ่าน 8 กฎ CIS ก่อนเสมอ
  - **AI Config Flagging (ติดป้ายเตือน AI):** 🚀 อันนี้รอย้ายไป P2 เพราะ P1 ยังไม่มีโค้ดจาก AI ให้ต้องติดป้ายเตือนครับ

**สรุปสั้นๆ (TL;DR):**
ตัดตู้หนังสือทิ้ง (RAG) เอาเวลาไปทำท่อส่งคำสั่ง (Prompt Engineering & Guardrails) ให้แข็งแรง เพื่อเตรียมปูทางให้แชทบอท AI เกิดขึ้นได้อย่างปลอดภัยในเทอม 2 ครับ!

## 5. ความเสี่ยงหลัก 5 ประการและวิธีรับมือ (Top 5 Risks & Mitigation)
โปรเจกต์นี้มีจุดเสี่ยงสูงที่อาจทำให้ไม่จบใน 1 เทอม นี่คือแผนรับมือ:
1. **🔴 IOS Version Incompatibility:** อุปกรณ์ยืมมาไม่รองรับคำสั่ง -> *วิธีแก้:* เขียน Jinja2 Template ด้วยคำสั่งพื้นฐานที่สุด (Conservative Set) และทดสอบบน GNS3 ก่อน
2. **🔴 Gemini API Rate Limit:** Demo สะดุดเพราะยิง API รัวๆ -> *วิธีแก้:* เตรียม Cache JSON ไว้โชว์ตอน Demo และสร้าง Offline Mode Fallback
3. **🔴 Discovery โดน Block ในมหาลัย:** ห้ามสแกน IP (Ping Sweep) -> *วิธีแก้:* สาธิตโหมด Discovery เฉพาะบน GNS3 Lab หรือใช้ Mock Data ตอนนำเสนอ
4. **🟡 SSH Timing Difference:** GNS3 กับของจริงตอบสนองช้าเร็วต่างกัน -> *วิธีแก้:* ตั้ง `read_timeout` ของ Netmiko ให้สูงขึ้น และเผื่อเวลาทดสอบอุปกรณ์จริง
5. **🟡 Team Skill Bottleneck:** ต้องทำ 3 เลเยอร์ (FE/BE/Network) พร้อมกัน -> *วิธีแก้:* ออกแบบ API Contract (OpenAPI) ล่วงหน้า ให้แยกกันทำแล้วมาต่อกันได้

## 6. แผนการดำเนินงาน (Sprint 0 - Foundation Setup)
เพื่อลดความเสี่ยงที่ทีมจะทำงานซ้ำซ้อนหรือติด Blocker ต้องบังคับทำ Sprint 0 (ประมาณ 1-2 สัปดาห์) ให้จบก่อนขึ้นฟีเจอร์ใดๆ:
1. **Repository & CI/CD:** ตกลง Git Branch Strategy (แนะนำ GitHub Flow) 
2. **Environment:** ทุกคนในทีมต้องรัน `docker compose up` แล้วขึ้นระบบ (FastAPI + PostgreSQL + React) ได้ภายใน 5 นาที
3. **Database Migration:** รัน `alembic init` และตั้งค่า Initial Schema
4. **State Management Design:** ร่าง TypeScript Interface ของ Zustand Store (สำหรับ Config Builder) ให้จบก่อนเริ่มเขียน Frontend
5. **Security Secrets:** กำหนด `.env.example` ให้ทีม (จัดการ `CRYPTOPAN_KEY`, `DB_URL` และค่าลับอื่น) ห้าม Hardcode ลงใน Source Code
6. **Testing Framework Setup:** ติดตั้ง `pytest` (Backend) และ `jest` (Frontend) ให้รันผ่านตั้งแต่วันแรก เพื่อใช้ทดสอบ Template Integration

## 🔴 จุดที่ขาดหายไป (Missing)

### 1. ไม่มี Dependency Diagram ระหว่างฟีเจอร์

เอกสารอธิบายเป็นตัวอักษรว่า "Topology ต้องรอ Discovery" และ "Version Control ต้องรอ SSH Push" แต่ไม่มี **ภาพ Dependency Graph** ที่โชว์ว่า Feature ไหนต้องรออันไหนก่อน ถ้ามีจะช่วยให้เพื่อนร่วมทีมเข้าใจได้เร็วมาก

### 2. ไม่มี Effort Estimate (Man-day) ต่อ Feature

ตาราง 7.1 มี Risk Level (🟢/🟡) แต่ไม่มีการประเมินว่าแต่ละ Feature ใช้เวลากี่ Man-day ทำให้ยังแบ่งงานลงคนไม่ได้

### 3. ไม่มี "Config Template ที่ต้องเขียน" แบบจำแนกเป็นไฟล์

ตาราง Config Items (หัวข้อ 4.1) บอกแค่หมวดกว้างๆ (System/Service, Interface & VLAN, ...) แต่ยังไม่ได้บอกว่าจะแตกเป็นไฟล์ `.j2` กี่ไฟล์ อันไหนบ้าง ตรงนี้ทีม Backend ต้องรู้เพื่อแบ่งงานกัน
