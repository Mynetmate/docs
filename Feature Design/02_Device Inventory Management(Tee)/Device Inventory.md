จากแผนภาพ กระบวนการนำเข้าข้อมูล (Device Information) จะแบ่งเป็น 2 แนวทางหลัก ซึ่งมีแนวคิดและเครื่องมือ (Tools) ที่ใช้แตกต่างกัน ดังนี้ครับ:

---

### 1. การนำอุปกรณ์เข้าสู่ระบบโดยผู้ใช้ระบุเป้าหมาย (Manual Device Enrollment)

**แนวคิด:**  
IT Admin หรือ Operator เป็นผู้ระบุอุปกรณ์เครือข่ายที่ทราบตำแหน่งอยู่แล้ว เช่น Management IP Address และเลือกชุดข้อมูลรับรองสำหรับเชื่อมต่ออุปกรณ์ (Device Credential Profile) จากนั้นระบบจะเชื่อมต่ออุปกรณ์แบบอ่านข้อมูลอย่างเดียว เพื่อดึงรายละเอียดจากอุปกรณ์เป้าหมายที่มีอยู่และสามารถเชื่อมต่อได้จริง

วิธีนี้แตกต่างจาก Network Discovery เฉพาะวิธีที่ระบบได้รับ IP เป้าหมาย กล่าวคือ Manual Device Enrollment ให้ผู้ใช้ระบุ IP เอง ส่วน Network Discovery ให้ระบบค้นหา IP ภายในขอบเขตที่อนุญาต แต่ทั้งสองวิธีต้องผ่านกระบวนการเชื่อมต่อ เก็บข้อมูล และตรวจสอบตัวตนอุปกรณ์ก่อนบันทึกเป็น Managed Device

การกรอก IP Address หรือการตรวจพบว่าอุปกรณ์ตอบ Ping เพียงอย่างเดียว ยังไม่เพียงพอที่จะยืนยันว่าเป็นอุปกรณ์ที่ระบบบริหารจัดการได้

**ข้อมูลที่ผู้ใช้ระบุ:**

1. Management IP Address ของอุปกรณ์
2. Protocol และ Port ที่ใช้เชื่อมต่อ เช่น SSH Port
3. ชุดข้อมูลรับรองสำหรับอุปกรณ์ (Device Credential Profile)
4. Vendor หรือ Device Type เบื้องต้น เพื่อช่วยเลือกรูปแบบการเชื่อมต่อ โดยข้อมูลนี้ยังไม่ถือเป็นข้อมูลยืนยัน
5. ข้อมูลประกอบที่ผู้ใช้จัดการเองได้ เช่น Site, Device Group, Role หรือ Description
    

ข้อมูลที่ต้องอ่านจากอุปกรณ์ เช่น Hostname, Model, OS Version, Serial Number, Interface และข้อมูล LLDP/CDP Neighbor ไม่ควรให้ผู้ใช้กรอกเป็นข้อมูลยืนยันด้วยตนเอง

**เครื่องมือและขั้นตอนการทำงาน (Tools & Flow):**

1. **กรอกข้อมูลอุปกรณ์เป้าหมาย:**  
    ผู้ใช้กรอก Management IP Address และเลือก Device Credential Profile ผ่านหน้าเว็บที่พัฒนาด้วย React
    
2. **ตรวจสอบข้อมูลเบื้องต้น:**  
    Backend ใช้ Pydantic ตรวจสอบรูปแบบ IP Address, Port, Protocol และ Credential Profile Reference รวมถึงตรวจว่า IP อยู่ภายใน Allowlist ของ Isolated Lab ที่ได้รับอนุญาต
    
3. **ตรวจสอบการเข้าถึง:**  
    ระบบอาจใช้ Ping เพื่อตรวจสอบการเข้าถึงเบื้องต้น แต่ผล Ping จะใช้เป็นเพียงสถานะ Reachability และไม่ถือเป็นหลักฐานยืนยันตัวอุปกรณ์
    
4. **เชื่อมต่ออุปกรณ์แบบอ่านอย่างเดียว:**  
    ระบบใช้ Netmiko เชื่อมต่อผ่าน SSH เป็นแนวทางหลัก และอาจใช้ SNMP แบบอ่านอย่างเดียวตามความสามารถของอุปกรณ์แต่ละรุ่น ระบบเรียกเฉพาะคำสั่งสำหรับอ่านข้อมูลที่กำหนดไว้ตาม Vendor Driver และห้ามแก้ไข Configuration ในขั้นตอนนี้
    
5. **เก็บข้อมูลจากอุปกรณ์:**  
    ระบบดึงข้อมูลที่จำเป็น เช่น Hostname, Vendor, Model, OS Version, Interface Status และ LLDP/CDP Neighbor ตามความสามารถของอุปกรณ์
    
6. **แปลงและตรวจสอบข้อมูล:**  
    Backend ใช้ TextFSM หรือ NTC Templates แปลงผลลัพธ์ข้อความจากอุปกรณ์ให้เป็นข้อมูลที่มีโครงสร้าง แล้วตรวจสอบว่าข้อมูลสามารถระบุตัวอุปกรณ์ได้เพียงพอหรือไม่
    
7. **บันทึกผลลงฐานข้อมูล:**
    
    - หากเชื่อมต่อและเก็บข้อมูลสำเร็จ ระบบใช้ SQLAlchemy บันทึกหรือปรับปรุงข้อมูล Managed Device, Interface และผลการเก็บข้อมูลลง PostgreSQL
        
    - หากเชื่อมต่อหรือเก็บข้อมูลไม่สำเร็จ ระบบบันทึกเฉพาะความพยายามนำเข้า สถานะข้อผิดพลาด และเวลาที่ตรวจสอบ โดยยังไม่สร้างอุปกรณ์เป็น Verified Topology Node
        
8. **บันทึกประวัติและรักษาความปลอดภัย:**  
    ระบบบันทึกว่าใครเป็นผู้เริ่มนำอุปกรณ์เข้าสู่ระบบ เมื่อใด และผลเป็นอย่างไร โดยห้ามบันทึก Password, SSH Key, SNMP Community String หรือข้อมูลลับลง Audit Log
    

**กรณีอัปโหลด CSV หรือ Running Configuration:**

- หากรองรับ CSV ให้ใช้สำหรับระบุเป้าหมายหลายอุปกรณ์ เช่น Management IP, Credential Profile Reference และ Site เท่านั้น อุปกรณ์แต่ละรายการยังต้องผ่านการเชื่อมต่อและเก็บข้อมูลจริงก่อนเป็น Managed Device
    
- Running Configuration Upload เป็นฟีเจอร์แยกสำหรับเก็บหรือตรวจสอบ Configuration ไม่สามารถใช้ยืนยันว่าอุปกรณ์กำลังเชื่อมต่ออยู่จริง และไม่ควรสร้าง Verified Topology Node หรือ Link จากไฟล์เพียงอย่างเดียว

---

### 2. การค้นหาอุปกรณ์อัตโนมัติ (Network / Auto Discovery)
**แนวคิด:**
ให้ระบบทำหน้าที่เป็น "นักสำรวจ" วิ่งไปตรวจสอบเครือข่ายเพื่อหาว่ามีอุปกรณ์อะไรอยู่บ้าง, เชื่อมต่อกันอย่างไร, และมีสถานะ (Status) เป็นแบบไหน ซึ่งช่วยลดเวลาการทำงาน (Pain point) และความผิดพลาดจากการจดบันทึกของคน (Human Error) ได้มาก

**เครื่องมือและการทำงาน (Tools & Flow):** การทำงานจะแบ่งออกตาม "ความทันสมัย" ของอุปกรณ์ปลายทางครับ:

*   **ขั้นที่ 1: การกวาดหา (Sweeping) หาตัวตน**
    *   ระบบอาจจะใช้ Python พื้นฐานทำ **Ping Sweep** หรือดึง **ARP Table** เพื่อหาว่ามี IP ไหนตอบสนอง (Alive) บ้าง
*   **ขั้นที่ 2: การดึงข้อมูลความสัมพันธ์ (Data Collection & Enrichment)** 
    หลังจากรู้ IP ระบบจะต้องหาว่ามันคือรุ่นอะไร และต่ออยู่กับใคร (Topology)
    *   **สำหรับอุปกรณ์รุ่นใหม่ (API-Driven):** Backend จะใช้ไลบรารี **Python `requests`** วิ่งผ่าน RESTCONF (หรือใช้ **`ncclient`** สำหรับ NETCONF) เพื่อดึงข้อมูล LLDP/CDP Neighbors ข้อมูลที่ได้กลับมาจะเป็น **JSON** ซึ่งแกะง่ายมาก
    *   **สำหรับอุปกรณ์รุ่นเก่า (CLI-Driven):** Backend จะใช้ไลบรารีอย่าง **`Netmiko`** (หรือใช้ **`Nornir`** ในกรณีที่อยากยิงคำสั่งค้นหาไปพร้อมๆ กัน 100 ตัวเพื่อความเร็ว) แอบ SSH เข้าไปพิมพ์คำสั่ง `show lldp neighbors` หรือ `show version`
*   **ขั้นที่ 3: การแปลงข้อมูล (Data Parsing)**
    *   ในกรณีอุปกรณ์เก่าที่ได้ผลลัพธ์มาเป็น "ข้อความบนหน้าจอดำๆ" (Raw Text) ระบบต้องเอาข้อความนั้นมาโยนเข้าตะแกรงร่อนที่ชื่อว่า **`Genie Parsers`** หรือ **`TextFSM`** เพื่อแปลงข้อความดิบให้กลายเป็น Python Dictionary (เช่น สกัดออกมาว่าบรรทัดนี้คือ Hostname, บรรทัดนี้คือ MAC Address)
*   **ขั้นที่ 4: บันทึกลง Inventory**
    *   ข้อมูลที่แปลงเสร็จแล้วจะถูกนำไปอัปเดตสถานะ (Status), โมเดล (Model), และการเชื่อมต่อ (Connection) ลงในฐานข้อมูล **PostgreSQL** โดยอัตโนมัติ

### 🎯 สรุปภาพรวมการทำงานร่วมกัน (อิงตามรูป)

### สรุปการทำงานร่วมกัน

Manual Device Enrollment และ Network Discovery แตกต่างกันที่วิธีได้มาซึ่งอุปกรณ์เป้าหมาย แต่ทั้งสองวิธีต้องผ่านกระบวนการเชื่อมต่อแบบอ่านอย่างเดียว การเก็บข้อมูล และการตรวจสอบตัวตนอุปกรณ์ก่อนบันทึกเป็น Managed Device ใน Device Inventory

ผู้ใช้สามารถแก้ไขข้อมูลที่เป็นข้อมูลประกอบ เช่น Site, Device Group, Role และ Description ได้ ส่วนข้อมูลที่ระบบอ่านจากอุปกรณ์ เช่น Hostname, Vendor, Model, OS Version และ Interface ต้องปรับปรุงผ่านการเก็บข้อมูลรอบใหม่ เพื่อป้องกันข้อมูลในระบบไม่ตรงกับอุปกรณ์เป้าหมาย

การลบ Device Record ออกจากระบบเป็นการนำข้อมูลออกจากการบริหารจัดการของ MyNetMate เท่านั้น ไม่ได้เป็นการลบ ปิด หรือเปลี่ยน Configuration ของอุปกรณ์เครือข่ายจริง


## เพื่อให้กระบวนการ Discovery สำเร็จ ข้อมูลที่ User (IT Admin) ต้องระบุหรือเตรียมไว้ในระบบ มีดังนี้ครับ:

### 1. ขอบเขตการค้นหา (Discovery Scope / Target)
ระบบต้องรู้ว่า "จะให้ไปหาที่ไหน" โดยสามารถกำหนดได้หลายรูปแบบ:
*   **Seed IP (IP เริ่มต้น):** ระบุ IP ของ Core Switch หรือ Router ตัวหลักเพียงตัวเดียว จากนั้นให้ระบบแอบเข้าไปอ่านตาราง LLDP/CDP/ARP แล้วกระโดดไปหาอุปกรณ์ตัวอื่นในเครือข่ายต่อๆ ไปเหมือนใยแมงมุม (วิธีนี้เป็นที่นิยมมาก)
*   **IP Subnet / IP Range:** กำหนดช่วง IP ตรงๆ เช่น `192.168.10.0/24` หรือ `10.0.0.1 - 10.0.0.254` เพื่อให้ระบบทำ Ping Sweep ไล่สแกนทุกเบอร์ในวงนั้น
*   **List of IPs:** ไฟล์ CSV หรือลิสต์ IP ที่เจาะจงว่าให้ไปสำรวจเฉพาะเครื่องเหล่านี้

### 2. ชุดรหัสผ่าน (Credential Profiles)
นี่คือส่วนที่สำคัญที่สุดครับ หากระบบเจอ IP ที่มีชีวิต (Alive) แต่ไม่มีรหัสผ่าน ก็ไม่สามารถเข้าไปดึงข้อมูล Topology, Version, หรือ Hostname ได้เลย ระบบส่วนใหญ่มักจะให้สร้างเป็น "Credential Group" ไว้ลองสุ่มเข้าอุปกรณ์:
*   **SSH Credentials:** Username และ Password สำหรับล็อกอินหน้าจอ CLI (ใช้ร่วมกับ Netmiko/Nornir)
*   **Enable Password (Secret):** รหัสผ่านสำหรับการเข้าสู่โหมด Privileged EXEC (สิทธิ์ Admin) เพื่อรันคำสั่ง `show` บางประเภท
*   **SNMP Community String:** รหัสสำหรับอ่านค่า (Read-Only) ผ่านโปรโตคอล SNMP เช่น คำว่า `public` หรือ `KMITL_RO`
*   **API Tokens / Credentials:** กรณีที่อุปกรณ์รุ่นใหม่รองรับ RESTCONF/NETCONF อาจต้องใช้ Token หรือ Username/Password ชุดเฉพาะสำหรับ API

### 3. โปรโตคอลและพอร์ตเชื่อมต่อ (Protocols & Ports)
ระบบต้องรู้ว่าจะให้ลองเคาะประตู (Port) บานไหนเพื่อเข้าไปเอาข้อมูล:
*   **SSH Port:** ค่ามาตรฐานคือ 22 แต่บางองค์กรอาจเปลี่ยนเป็น 8022
*   **NETCONF Port:** ค่ามาตรฐานคือ 830
*   **SNMP Port:** ค่ามาตรฐานคือ 161 (UDP)

### 4. กฎเกณฑ์ข้อจำกัด (Discovery Rules & Exclusions) - *Optional แต่แนะนำ*
เพื่อความปลอดภัยและไม่ให้ระบบทำงานหนักเกินไป ควรมีข้อมูลที่บอกว่า "อะไรไม่ควรไปยุ่ง":
*   **Excluded IPs:** ช่วง IP ห้ามสแกน (เช่น วง IP ของผู้บริหาร, Server สำคัญ, หรือ Network อุปกรณ์การแพทย์)
*   **Depth Limit:** จำนวนความลึกในการกระโดดหา (Hop count) ในกรณีใช้ Seed IP เช่น อนุญาตให้กระโดดต่อจาก Core Switch ไปหาตัวอื่นได้แค่ 3 ทอด (Hops) เพื่อไม่ให้ระบบหลงออกไปนอกเครือข่ายของบริษัท

---

**สรุป Flow ก่อนเริ่ม Auto Discovery:**
1. ผู้ใช้ตั้งค่า **IP Range หรือ Seed IP** (เช่น 192.168.1.1)
2. ผู้ใช้ระบุ **Credential Profiles** ไว้ 2-3 ชุด (ระบบจะหยิบไปสุ่มลองล็อกอินทีละชุดจนกว่าจะเข้าได้)
3. ผู้ใช้กด **Start Discovery**
	1. Backend (Nornir / Netmiko / API) เริ่มวิ่งไปกวาดข้อมูล กลับมาป้อนเข้า Device Inventory ครับ
