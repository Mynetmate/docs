# คำถามสำหรับคุยกับทีมก่อนออกแบบฐานข้อมูลแดชบอร์ดและการติดตามสถานะ (Dashboard & Monitoring)

ตอนนี้เรายังไม่ได้คุยเรื่องชื่อตาราง (Table) หรือชื่อช่องข้อมูล (Field) แต่ต้องการตกลงก่อนว่า **เมื่อผู้ใช้กดอัปเดตสถานะ ระบบจะสร้างและเก็บข้อมูลอย่างไร** รวมถึงความสัมพันธ์และจำนวนระหว่างข้อมูล (Relationships and Cardinality)

ตัวอย่างเช่น เราต้องตกลงว่า:

- การกดอัปเดตสถานะด้วยตนเอง (Manual Refresh) หนึ่งครั้งเลือกอุปกรณ์ได้หนึ่งตัวหรือหลายตัว
- อุปกรณ์ (Device) หนึ่งตัวเก็บข้อมูลสถานะย้อนหลังได้กี่ชุด
- ถ้าอ่านข้อมูลได้ไม่ครบ จะถือว่าสำเร็จหรือล้มเหลว
- ข้อมูลส่วนใดแดชบอร์ดและการติดตามสถานะ (Dashboard & Monitoring: D&M) ทำเอง และส่วนใดขอใช้จากการค้นหาอุปกรณ์เครือข่าย (Network Discovery)

การตกลงเรื่องเหล่านี้ก่อนจะช่วยป้องกันไม่ให้แต่ละคนสร้างตารางหรือระบบเชื่อมต่ออุปกรณ์ซ้ำกัน

## คำที่ใช้ในข้อความนี้

| คำที่ใช้ | ความหมายแบบสั้น |
|---|---|
| **รอบอัปเดตสถานะ (Operational Refresh Run)** | การดำเนินงานที่เริ่มเมื่อผู้ใช้กดอัปเดตสถานะ (Refresh) หนึ่งครั้ง |
| **ผลการเก็บข้อมูลรายอุปกรณ์ (Device Collection Attempt/Result)** | ผลว่าอุปกรณ์แต่ละตัวเชื่อมต่อและอ่านข้อมูลสำเร็จหรือล้มเหลว |
| **ชุดข้อมูลสถานะ (Operational Snapshot)** | ข้อมูลที่อ่านจากอุปกรณ์สำเร็จในช่วงเวลาหนึ่ง เช่น สถานะช่องเชื่อมต่อ (Interface), เครือข่ายเสมือน (VLAN) หรือเส้นทางปริยาย (Default Route) |
| **ชุดข้อมูลสำเร็จล่าสุด (Last Known State)** | ชุดข้อมูลเดิมที่ยังใช้ดูอ้างอิงเมื่อการอัปเดตรอบใหม่ล้มเหลว |
| **ค่าที่ควรเป็น (Expected State)** | ค่าที่ผู้ใช้กำหนดไว้ก่อนว่าอุปกรณ์หรือช่องเชื่อมต่อ (Interface) ควรทำงานอย่างไร |
| **รายการปัญหาที่ตรวจพบ (Operational Finding)** | ผลที่ระบบคำนวณด้วยกฎตายตัว (Deterministic Rule) จากข้อมูลจริงและค่าที่ควรเป็น ไม่ใช่ผลวิเคราะห์จากปัญญาประดิษฐ์ (AI) |

## ภาพรวมการทำงานที่เสนอ

```text
ผู้ใช้กดอัปเดตสถานะ (Refresh)
└─ เกิดรอบอัปเดตสถานะ (Operational Refresh Run) 1 รอบ
   ├─ เก็บข้อมูลอุปกรณ์ A
   │  └─ สำเร็จ → สร้างชุดข้อมูลสถานะ (Operational Snapshot) ใหม่
   └─ เก็บข้อมูลอุปกรณ์ B
      └─ ล้มเหลว → ไม่สร้างชุดใหม่
                    และยังแสดงชุดข้อมูลสำเร็จล่าสุด (Last Known State) พร้อมคำเตือน

ชุดข้อมูลสถานะล่าสุด (Latest Operational Snapshot)
+ ค่าที่ผู้ใช้กำหนดว่าควรเป็น (Expected State)
+ กฎตรวจสอบแบบตายตัว (Deterministic Rule)
└─ ได้รายการปัญหาปัจจุบัน
   ├─ ช่องเชื่อมต่อต้นทาง (Uplink) สำคัญไม่ทำงาน
   ├─ ช่องเชื่อมต่อ (Port) เป็นสถานะถูกปิดเพราะพบความผิดปกติ (Err-disabled)
   ├─ ช่องเชื่อมต่อเครือข่ายภายนอก (WAN) สำคัญไม่ทำงาน
   └─ อุปกรณ์กำหนดเส้นทาง (Router) ที่ควรมีเส้นทางปริยาย (Default Route) แต่ตรวจไม่พบ
```

อยากขอความเห็นจากทีม 7 เรื่องต่อไปนี้ก่อนออกแบบความสัมพันธ์และตารางจริง

## 1. รอบอัปเดตสถานะ (Operational Refresh Run) หนึ่งรอบควรรองรับอุปกรณ์กี่ตัว

ข้อเสนอคือ ฐานข้อมูลควรรองรับรอบอัปเดตสถานะ (Operational Refresh Run) หนึ่งรอบที่เลือกอุปกรณ์ (Device) ได้หลายตัว แต่หน้าเว็บรุ่นแรกอาจเริ่มจากการเลือกครั้งละหนึ่งตัวก่อน

ตัวอย่าง:

```text
รอบอัปเดตสถานะ (Refresh Run) #101
├─ Router-01  → สำเร็จ
├─ Core-SW-01 → สำเร็จ
└─ Floor-SW-01 → ล้มเหลว
```

เหตุผลที่เสนอให้ฐานข้อมูลรองรับหลายตัว คือในอนาคตอาจต้องการ:

- เลือกหลายอุปกรณ์
- อัปเดตอุปกรณ์ทั้งหมดในพื้นที่ติดตั้ง (Site)
- อัปเดตอุปกรณ์สวิตช์ (Switch) หรืออุปกรณ์กำหนดเส้นทาง (Router) เป็นกลุ่ม

โดยไม่ต้องรื้อโครงสร้างฐานข้อมูลใหม่

### คำถามที่ต้องการคำตอบ

- ต้องการให้ระบบรองรับหลายอุปกรณ์ตั้งแต่โครงสร้างฐานข้อมูลหรือไม่
- หรือยืนยันว่าจะจำกัดทั้งระบบเป็นครั้งละหนึ่งอุปกรณ์เท่านั้น

### **ข้อสรุปสมเหตุสมผลและแยกขอบเขตชัดเจน:**

- **โครงสร้างฐานข้อมูล:** รอบอัปเดตหนึ่งรอบรองรับอุปกรณ์ได้ตั้งแต่ 1 ตัวขึ้นไป
- **หน้าเว็บรุ่นแรก:** ผู้ใช้เลือกและอัปเดตได้ครั้งละ 1 อุปกรณ์
- **กรณี 0 อุปกรณ์:** ไม่สร้างรอบอัปเดต
- **อนาคต:** เพิ่มการเลือกหลายอุปกรณ์ได้โดยไม่ต้องแก้โครงสร้างฐานข้อมูล

ความสัมพันธ์จะเป็น:

```
รอบอัปเดตสถานะ 1 รอบ
└─ มีผลการเก็บข้อมูลรายอุปกรณ์อย่างน้อย 1 รายการ
   ├─ อุปกรณ์ A → สำเร็จ
   ├─ อุปกรณ์ B → สำเร็จ
   └─ อุปกรณ์ C → ล้มเหลว
```

แต่หน้าเว็บ MVP จะสร้างเพียง:

```
รอบอัปเดตสถานะ #101
└─ Router-01 → สำเร็จ
```

ข้อความสรุปสำหรับใส่เอกสาร:

> โครงสร้างฐานข้อมูลต้องรองรับการอัปเดตอุปกรณ์หลายตัวภายในรอบเดียว โดยรอบหนึ่งต้องมีอุปกรณ์อย่างน้อยหนึ่งตัว อย่างไรก็ตาม หน้าเว็บของผลิตภัณฑ์ขั้นต่ำที่ใช้งานได้ (MVP) จะให้ผู้ใช้เลือกและอัปเดตสถานะครั้งละหนึ่งอุปกรณ์ก่อน ส่วนการเลือกหลายอุปกรณ์พร้อมกันจะพิจารณาเพิ่มในอนาคต

หมายความว่า MVP **มี Manual Refresh แบบทีละอุปกรณ์** แต่เตรียมฐานข้อมูลสำหรับหลายอุปกรณ์ไว้ครับ

## 2. ควรเก็บชุดข้อมูลสถานะ (Operational Snapshot) ที่สำเร็จหลายรอบหรือไม่

ข้อเสนอคือ อุปกรณ์หนึ่งตัวสามารถมีชุดข้อมูลสถานะ (Operational Snapshot) ที่เก็บสำเร็จได้หลายชุดตามแต่ละรอบ แต่แดชบอร์ด (Dashboard) จะแสดงชุดที่สำเร็จล่าสุดเป็นสถานะปัจจุบัน

ตัวอย่าง:

```text
Router-01
├─ 09:00 เก็บสำเร็จ
├─ 10:00 เก็บสำเร็จ
└─ 11:00 เก็บล้มเหลว

แดชบอร์ด (Dashboard) แสดงข้อมูลจาก 10:00
พร้อมเตือนว่ารอบ 11:00 ล้มเหลวและข้อมูลเริ่มเก่า
```

การเก็บหลายชุดไม่ได้หมายความว่าผลิตภัณฑ์ขั้นต่ำที่ใช้งานได้ (Minimum Viable Product: MVP) ต้องมีกราฟย้อนหลัง แต่ช่วยรักษาหลักฐานว่าแต่ละรอบอ่านข้อมูลอะไรได้

ระยะเวลาหรือจำนวนชุดที่จะเก็บสามารถตกลงภายหลังได้

### คำถามที่ต้องการคำตอบ

- ยอมให้หนึ่งอุปกรณ์มีชุดข้อมูลที่สำเร็จหลายชุดหรือไม่
- หรือต้องการเก็บเพียงชุดล่าสุดแล้วเขียนทับของเดิม

### ข้อสรุป
ผมคิดว่า **ควรให้ฐานข้อมูลเก็บชุดข้อมูลสถานะที่สำเร็จได้หลายรอบ** แต่ยังไม่ต้องทำหน้ากราฟหรือหน้าดูประวัติใน MVP

เหตุผลสำคัญคือ ถ้าเก็บเฉพาะชุดล่าสุดแล้วเขียนทับ ระบบจะรู้เพียงว่า “ตอนนี้เป็นอย่างไร” แต่จะสูญเสียหลักฐานว่าแต่ละรอบอ่านข้อมูลอะไรได้ เช่น:

```
10:00  Interface Gi0/1 = Up
11:00  Interface Gi0/1 = Down
```

ถ้าเขียนทับ จะเหลือเพียง `Down` และตอบไม่ได้ว่าเมื่อใดสถานะเริ่มเปลี่ยน

ประโยชน์ของการเก็บหลายชุดคือ:

- เชื่อมโยงผลข้อมูลกับรอบอัปเดตแต่ละรอบได้
- เปรียบเทียบสถานะปัจจุบันกับรอบก่อนหน้าได้ในอนาคต
- ใช้พิสูจน์ว่า Manual Refresh อ่านข้อมูลใหม่จริง
- ตรวจสอบย้อนหลังได้เมื่อ Dashboard แสดงข้อมูลผิดปกติ
- เมื่อรอบใหม่ล้มเหลว ระบบยังใช้ชุดที่สำเร็จล่าสุดได้อย่างชัดเจน
- ใช้วิเคราะห์ปัญหาระหว่างพัฒนาและสาธิตโครงงานได้ง่ายขึ้น

อย่างไรก็ตาม ไม่ควรเก็บแบบไม่จำกัด เพราะสถานะ Interface, VLAN และ Routing อาจทำให้ข้อมูลเพิ่มขึ้นเร็ว

ข้อเสนอสำหรับ MVP คือ:

- ฐานข้อมูลรองรับชุดข้อมูลที่สำเร็จหลายชุดต่ออุปกรณ์
- เมื่อเก็บข้อมูลสำเร็จ ให้สร้างชุดใหม่ ไม่เขียนทับชุดเดิม
- เมื่อเก็บข้อมูลล้มเหลว ไม่สร้างชุดข้อมูลสถานะใหม่
- Dashboard แสดงเฉพาะชุดที่สำเร็จล่าสุด
- ยังไม่ต้องมีหน้าดูประวัติหรือกราฟย้อนหลัง
- กำหนดจำนวนหรือระยะเวลาเก็บข้อมูลภายหลัง เช่น เก็บเฉพาะชุดล่าสุดจำนวนหนึ่งต่ออุปกรณ์
- ไม่จำเป็นต้องเก็บผลคำสั่งดิบทั้งหมด เก็บเฉพาะข้อมูลที่ MVP ใช้แสดงและตรวจสอบ

ความสัมพันธ์ที่ได้คือ:

```
อุปกรณ์ (Device) 1 ตัว
└─ มีชุดข้อมูลสถานะที่สำเร็จได้ 0 ถึงหลายชุด

รอบที่สำเร็จ
└─ สร้างชุดข้อมูลสถานะใหม่ 1 ชุด

รอบที่ล้มเหลว
└─ ไม่สร้างชุดข้อมูลสถานะใหม่
   และ Dashboard ใช้ชุดที่สำเร็จล่าสุดพร้อมแสดงคำเตือน
```

ข้อสรุปสำหรับเอกสาร:

> ฐานข้อมูลควรรองรับการเก็บชุดข้อมูลสถานะที่สำเร็จหลายรอบต่ออุปกรณ์ โดยแต่ละรอบที่เก็บข้อมูลสำเร็จจะสร้างชุดข้อมูลใหม่และไม่เขียนทับชุดเดิม ส่วนรอบที่ล้มเหลวจะไม่สร้างชุดข้อมูลสถานะใหม่ แดชบอร์ดของ MVP จะแสดงเฉพาะชุดที่สำเร็จล่าสุดและยังไม่เปิดให้ดูประวัติย้อนหลัง ทั้งนี้ต้องกำหนดนโยบายจำกัดจำนวนหรือระยะเวลาการเก็บข้อมูลก่อนพัฒนาจริง

ดังนั้นคำตอบคือ **ควรเก็บหลายรอบในระดับฐานข้อมูล แต่ลดความลึกของ MVP ด้วยการแสดงเพียงชุดล่าสุด** ครับ


## 3. ถ้าเก็บข้อมูลได้เพียงบางส่วน (Partial Collection) ควรถือว่าสำเร็จหรือไม่

ตัวอย่างอุปกรณ์กำหนดเส้นทาง (Router):

```text
อ่านสถานะช่องเชื่อมต่อ (Interface) สำเร็จ
แต่อ่านตารางเส้นทาง (Routing Table) ไม่สำเร็จ
```

ข้อเสนอสำหรับผลิตภัณฑ์ขั้นต่ำที่ใช้งานได้ (Minimum Viable Product: MVP) คือ ถ้าข้อมูลสำคัญของอุปกรณ์ชนิดนั้นอ่านได้ไม่ครบ ให้ถือว่าการเก็บข้อมูลรอบนั้นล้มเหลวและไม่สร้างชุดข้อมูลสถานะ (Operational Snapshot) ใหม่

แดชบอร์ด (Dashboard) จะยังแสดงชุดข้อมูลสำเร็จล่าสุด (Last Known State) พร้อมบอกว่าการอัปเดตรอบใหม่ล้มเหลว

เหตุผลคือ หากยอมเก็บข้อมูลเพียงบางส่วน อาจเกิดกรณีนี้:

```text
ข้อมูลช่องเชื่อมต่อ (Interface) มาจากเวลา 11:00
ข้อมูลเส้นทาง (Routing) มาจากเวลา 10:00
```

ผู้ใช้อาจเข้าใจผิดว่าข้อมูลทั้งสองส่วนมาจากเวลาเดียวกัน

หากทีมต้องการรองรับข้อมูลบางส่วน ระบบต้องแยกเวลาและความใหม่ของข้อมูลช่องเชื่อมต่อ (Interface), เครือข่ายเสมือน (VLAN) และข้อมูลเส้นทาง (Routing) ออกจากกัน ซึ่งจะเพิ่มความซับซ้อน

### คำถามที่ต้องการคำตอบ

- ผลิตภัณฑ์ขั้นต่ำที่ใช้งานได้ (MVP) ควรยอมรับเฉพาะรอบที่เก็บข้อมูลสำคัญครบหรือไม่
- หรือควรเก็บข้อมูลส่วนที่สำเร็จและติดป้ายแยกแต่ละส่วน

# ตอบ 
สำหรับ MVP ผมแนะนำว่า **การเก็บข้อมูลได้เพียงบางส่วนไม่ควรถือว่าสำเร็จเต็มรูปแบบ** และไม่ควรนำข้อมูลชุดนั้นมาแทนสถานะปัจจุบันบนแดชบอร์ด

แต่ระบบควรบันทึกว่าอ่านส่วนใดสำเร็จและส่วนใดล้มเหลว เพื่อใช้ตรวจสอบปัญหา

หลักการที่เหมาะสมคือ:

- เก็บข้อมูลสำคัญครบ → สถานะ `สำเร็จ (Success)` และสร้างชุดข้อมูลสถานะใหม่
- เก็บข้อมูลสำคัญได้บางส่วน → สถานะ `สำเร็จบางส่วน (Partial)` แต่ไม่สร้างชุดข้อมูลสถานะใหม่
- เก็บไม่ได้เลยหรือเชื่อมต่อไม่ได้ → สถานะ `ล้มเหลว (Failed)` และไม่สร้างชุดข้อมูลสถานะใหม่
- แดชบอร์ดยังคงแสดงชุดข้อมูลที่สำเร็จล่าสุด พร้อมคำเตือนว่ารอบล่าสุดไม่สำเร็จ

ตัวอย่าง:

```
รอบล่าสุด เวลา 11:00
├─ สถานะช่องเชื่อมต่อ (Interface) → สำเร็จ
└─ ตารางเส้นทาง (Routing Table)   → ล้มเหลว

ผลของรอบ: สำเร็จบางส่วน (Partial)
การสร้างชุดข้อมูลสถานะใหม่: ไม่สร้าง
ข้อมูลที่แดชบอร์ดแสดง: ชุดที่สำเร็จล่าสุดจากเวลา 10:00
คำเตือน: การอัปเดตล่าสุดสำเร็จเพียงบางส่วน
```

เหตุผลที่ไม่ควรนำข้อมูลบางส่วนมาแสดงเป็นสถานะล่าสุดคือ อาจทำให้ข้อมูลในหน้าเดียวกันมาจากคนละเวลา เช่น Interface มาจาก 11:00 แต่ Routing มาจาก 10:00 โดยผู้ใช้ไม่รู้ ซึ่งเพิ่มทั้งความสับสนและความซับซ้อนของฐานข้อมูล

อย่างไรก็ตาม คำว่า “ข้อมูลสำคัญครบ” ต้องกำหนดตามชนิดอุปกรณ์ เช่น:

- อุปกรณ์สวิตช์ (Switch): สถานะ Interface และ VLAN
- อุปกรณ์กำหนดเส้นทาง (Router): สถานะ Interface และ Routing
- ข้อมูลเสริมที่ไม่จำเป็นต่อ MVP หากอ่านไม่ได้ อาจยังถือว่ารอบสำเร็จแต่แสดงคำเตือนได้

ข้อสรุปสำหรับใส่เอกสาร:

> ผลิตภัณฑ์ขั้นต่ำที่ใช้งานได้ (MVP) จะสร้างชุดข้อมูลสถานะใหม่เฉพาะเมื่อเก็บข้อมูลสำคัญของอุปกรณ์ได้ครบ หากเก็บได้เพียงบางส่วน ระบบจะบันทึกผลเป็น “สำเร็จบางส่วน (Partial)” พร้อมระบุส่วนที่สำเร็จและล้มเหลว แต่จะไม่นำข้อมูลดังกล่าวมาแทนชุดข้อมูลสถานะปัจจุบัน แดชบอร์ดจะยังแสดงชุดข้อมูลที่สำเร็จล่าสุดพร้อมคำเตือนว่าการอัปเดตรอบล่าสุดไม่สมบูรณ์

ดังนั้นคำตอบคือ **เก็บรายละเอียดของส่วนที่สำเร็จไว้เพื่อการตรวจสอบ แต่ไม่ใช้เป็น Operational Snapshot ใหม่** ครับ
## 4. ค่าที่ผู้ใช้กำหนดว่า “ควรเป็น” (Expected State) จะเก็บอย่างไร

ระบบต้องมีข้อมูลที่ผู้ใช้กำหนดไว้ก่อน จึงจะบอกได้ว่าสถานะที่อ่านมาผิดจากสิ่งที่ตั้งใจหรือไม่

ตัวอย่างช่องเชื่อมต่อ (Interface):

```text
บทบาท: ช่องเชื่อมต่อต้นทาง (Uplink)
เป็นช่องเชื่อมต่อสำคัญ (Critical Interface): ใช่
สถานะที่คาดหวัง: ต้องเปิดใช้งาน
```

ตัวอย่างอุปกรณ์กำหนดเส้นทาง (Router):

```text
อุปกรณ์กำหนดเส้นทาง (Router) ตัวนี้เป็นทางออกของบริษัท
จึงต้องมีเส้นทางปริยาย (Default Route)
```

ข้อเสนอคืออุปกรณ์ (Device) หรือช่องเชื่อมต่อ (Interface) หนึ่งรายการมีชุดค่าที่ควรเป็น (Expected State) ที่ใช้งานอยู่ไม่เกินหนึ่งชุด

เมื่อผู้ใช้แก้ค่า ให้ประวัติการดำเนินงาน (Audit Trail) บันทึกว่าใครแก้และแก้เมื่อใด แทนการทำระบบเก็บทุกเวอร์ชัน (Version History) ของค่าที่ควรเป็นในผลิตภัณฑ์ขั้นต่ำที่ใช้งานได้ (MVP)

### คำถามที่ต้องการคำตอบ

- เห็นด้วยกับการเก็บเฉพาะค่าปัจจุบันและใช้ประวัติการดำเนินงาน (Audit Trail) ตรวจย้อนหลังหรือไม่
- หรือต้องการเปิดดูค่าที่ควรเป็นทุกเวอร์ชันย้อนหลัง

ผม **เห็นด้วยกับการเก็บเฉพาะค่าที่ควรเป็นชุดปัจจุบัน และใช้ประวัติการดำเนินงาน (Audit Trail) ตรวจย้อนหลังสำหรับ MVP** เพราะหน้า Dashboard ต้องใช้ค่าปัจจุบันในการตรวจสอบเป็นหลัก ยังไม่มีความจำเป็นต้องเปิดดูหรือกู้คืนทุกเวอร์ชัน

แต่มีเงื่อนไขสำคัญว่า Audit Trail ต้องเก็บ **ค่าก่อนแก้และค่าหลังแก้** ไม่ใช่เก็บเพียงข้อความว่า “ผู้ใช้แก้ไข Expected State”

ตัวอย่างค่าที่ควรเป็น:

```
อุปกรณ์: Core-SW-01
ช่องเชื่อมต่อ: Gi0/1

บทบาท: ช่องเชื่อมต่อต้นทาง (Uplink)
ช่องเชื่อมต่อสำคัญ (Critical Interface): ใช่
สถานะที่ควรเป็น: เปิดใช้งาน
```

เมื่อผู้ใช้เปลี่ยนค่า:

```
ผู้แก้ไข: User A
เวลา: 13 สิงหาคม 2026 เวลา 10:30
รายการที่แก้: สถานะที่ควรเป็น
ค่าก่อนแก้: เปิดใช้งาน
ค่าหลังแก้: ปิดใช้งาน
เหตุผล: ปิดช่องเชื่อมต่อชั่วคราว
```

หลักการจัดเก็บที่แนะนำ:

- อุปกรณ์หรือช่องเชื่อมต่อหนึ่งรายการมีชุดค่าที่ควรเป็นปัจจุบันเพียงหนึ่งชุด
- เมื่อแก้ไข ให้ปรับข้อมูลชุดปัจจุบัน
- Audit Trail บันทึกผู้แก้ไข เวลา การกระทำ ค่าก่อนแก้ และค่าหลังแก้
- เมื่อยกเลิกค่าที่ควรเป็น ต้องบันทึกเหตุการณ์ลบหรือยกเลิกด้วย
- หากยังไม่ได้กำหนดค่าที่ควรเป็น ระบบต้องไม่สรุปว่าอุปกรณ์ผิดปกติจากกฎนั้น
- ยังไม่ต้องมีหน้าดูทุกเวอร์ชัน เปรียบเทียบเวอร์ชัน หรือกู้คืนเวอร์ชันใน MVP

ตัวอย่างการนำไปใช้:

```
สถานะที่อ่านได้ล่าสุด
+ ค่าที่ควรเป็นปัจจุบัน
+ กฎตรวจสอบแบบตายตัว
= รายการปัญหาปัจจุบัน
```

ตัวอย่างเช่น:

```
สถานะจริง: Uplink ไม่ทำงาน
ค่าที่ควรเป็น: ต้องเปิดใช้งาน
ผลตรวจสอบ: พบปัญหา
```

ข้อควรถามเพื่อนที่ทำ Audit Trail คือ:

> Audit Trail สามารถเก็บค่าก่อนแก้และค่าหลังแก้ของแต่ละเหตุการณ์ได้หรือไม่

หาก Audit Trail เก็บเพียง “ใครทำอะไร เมื่อใด” จะตรวจย้อนหลังได้แค่ว่ามีการแก้ไข แต่ตอบไม่ได้ว่าค่าเดิมคืออะไร ในกรณีนั้น D&M อาจต้องมีประวัติการเปลี่ยนค่าอย่างง่ายของตัวเอง

ข้อสรุปสำหรับเอกสาร:

> ผลิตภัณฑ์ขั้นต่ำที่ใช้งานได้ (MVP) จะเก็บค่าที่ผู้ใช้กำหนดว่าควรเป็น (Expected State) เฉพาะชุดปัจจุบัน และใช้ประวัติการดำเนินงาน (Audit Trail) สำหรับตรวจสอบการเปลี่ยนแปลงย้อนหลัง โดย Audit Trail ต้องบันทึกผู้แก้ไข เวลา ค่าก่อนแก้ และค่าหลังแก้ ส่วนความสามารถเปิดดู เปรียบเทียบ หรือกู้คืนค่าทุกเวอร์ชันยังไม่อยู่ในขอบเขตของ MVP

ดังนั้นคำตอบคือ **เลือกเก็บค่าปัจจุบันร่วมกับ Audit Trail แบบมีค่าก่อนและหลัง** ไม่จำเป็นต้องสร้างระบบ Version History แยกใน MVP ครับ

## 5. ควรบันทึกรายการปัญหาที่ตรวจพบ (Operational Finding) ทุกครั้ง หรือคำนวณเมื่อเปิดแดชบอร์ด

ข้อเสนอคือแดชบอร์ด (Dashboard) คำนวณปัญหาปัจจุบันจาก:

```text
ชุดข้อมูลที่เก็บสำเร็จล่าสุด (Latest Successful Snapshot)
+ ค่าที่ผู้ใช้กำหนดว่าควรเป็น (Expected State)
+ กฎตรวจสอบแบบตายตัว (Deterministic Rule)
= รายการปัญหาปัจจุบัน
```

ตัวอย่างผลลัพธ์:

- ช่องเชื่อมต่อต้นทาง (Uplink) สำคัญไม่ทำงาน
- ช่องเชื่อมต่อ (Port) เป็นสถานะถูกปิดเพราะพบความผิดปกติ (Err-disabled)
- ช่องเชื่อมต่อเครือข่ายภายนอก (WAN) สำคัญไม่ทำงาน
- อุปกรณ์กำหนดเส้นทาง (Router) ที่กำหนดว่าต้องมีเส้นทางปริยาย (Default Route) แต่ตรวจไม่พบ

ข้อเสนอสำหรับผลิตภัณฑ์ขั้นต่ำที่ใช้งานได้ (MVP) คือยังไม่บันทึกรายการปัญหาทุกครั้ง แต่คำนวณจากข้อมูลต้นทางเมื่อเปิดแดชบอร์ด (Dashboard) หรือเมื่อมีการอัปเดต

ข้อดี:

- ลดข้อมูลซ้ำ
- ไม่ต้องจัดการประวัติรายการปัญหาจำนวนมาก
- เมื่อแก้กฎ สามารถคำนวณผลใหม่จากข้อมูลต้นทางได้

ข้อเสีย:

- ยังตอบไม่ได้ว่า “เมื่อวานเวลา 10:00 แดชบอร์ด (Dashboard) เคยแจ้งปัญหาอะไร”

หากทีมต้องการเปิดดูประวัติการแจ้งปัญหา จะต้องบันทึกผลแต่ละรอบและกำหนดว่าจะเก็บไว้นานเท่าใด

### คำถามที่ต้องการคำตอบ

- ผลิตภัณฑ์ขั้นต่ำที่ใช้งานได้ (MVP) ต้องการเพียงรายการปัญหาปัจจุบันหรือไม่
- หรือต้องมีประวัติรายการปัญหาย้อนหลังตั้งแต่รุ่นแรก

### ควรบันทึกรายการปัญหาที่ตรวจพบ (Operational Finding) หรือไม่

สำหรับผลิตภัณฑ์ขั้นต่ำที่ใช้งานได้ (MVP) เสนอให้ **คำนวณเฉพาะปัญหาปัจจุบันและยังไม่บันทึกประวัติ** โดยใช้:

```
ชุดข้อมูลที่สำเร็จล่าสุด
+ ค่าที่ควรเป็น
+ กฎตรวจสอบแบบตายตัว
= รายการปัญหาปัจจุบัน
```

ระบบจะคำนวณใหม่เมื่อเปิดแดชบอร์ดหรืออัปเดตสถานะสำเร็จ วิธีนี้ลดข้อมูลซ้ำและทำระบบง่ายขึ้น แต่จะยังดูประวัติการแจ้งปัญหาย้อนหลังไม่ได้

**ข้อสรุปสำหรับ MVP:** แสดงเฉพาะรายการปัญหาปัจจุบัน ส่วนประวัติปัญหาให้พิจารณาในอนาคตครับ
## 6. อุปกรณ์กำหนดเส้นทาง (Router) หนึ่งตัวอาจมีเส้นทางปริยาย (Default Route) ที่ใช้งานอยู่หลายเส้นหรือไม่

อุปกรณ์กำหนดเส้นทาง (Router) อาจมีเส้นทางออกหลัก เส้นทางสำรอง หรือหลายเส้นทางที่มีค่าเท่ากันและใช้งานพร้อมกัน

กรณีหลายเส้นทางที่มีค่าเท่ากันและใช้งานพร้อมกันเรียกว่า **การใช้หลายเส้นทางที่มีค่าเท่ากัน (Equal-Cost Multi-Path: ECMP)** ซึ่งช่วยกระจายข้อมูลจราจร (Traffic) ไปยังหลายเส้นทาง

ตัวอย่าง:

```text
เส้นทางปริยาย (Default Route) 1 → ฮอปถัดไป (Next Hop) A → WAN-1
เส้นทางปริยาย (Default Route) 2 → ฮอปถัดไป (Next Hop) B → WAN-2
```

ข้อเสนอคือ โครงสร้างข้อมูลควรรองรับเส้นทางปริยาย (Default Route) ได้หลายรายการ แม้หน้าแดชบอร์ด (Dashboard) รุ่นแรกอาจแสดงเพียง:

```text
เส้นทางปริยายที่ใช้งานอยู่ (Active Default Routes): 2
```

เหตุผลคือไม่ควรบังคับสมมติฐานว่าอุปกรณ์กำหนดเส้นทาง (Router) หนึ่งตัวมีทางออกได้เพียงเส้นเดียว

### คำถามที่ต้องการคำตอบ

- ให้โครงสร้างข้อมูลรองรับเส้นทางปริยาย (Default Route) หลายรายการหรือไม่
- อุปกรณ์และสถานการณ์ทดสอบของทีมมีกรณีเส้นทางสำรองหรือการใช้หลายเส้นทางที่มีค่าเท่ากัน (ECMP) หรือไม่
-
ผมเห็นด้วยว่า **โครงสร้างข้อมูลควรรองรับเส้นทางปริยายที่ใช้งานอยู่ตั้งแต่ 0 ถึงหลายเส้น** แม้ MVP จะทดสอบเพียงกรณีพื้นฐานก็ตาม เพราะอุปกรณ์จริงอาจมีหลายฮอปถัดไป (Next Hop)

สำหรับ MVP:

- ฐานข้อมูลรองรับหลายเส้นทาง
- แดชบอร์ดแสดงเพียง “พบ/ไม่พบ” และจำนวนเส้นทาง
- กรณี ECMP เป็นสถานการณ์ทดสอบเสริม ไม่ใช่เงื่อนไขบังคับ
- ควรตรวจจากตารางเส้นทางที่กำลังใช้งาน ไม่ใช่เส้นทางสำรองที่ตั้งค่าไว้แต่ยังไม่ทำงาน

ข้อสรุปสำหรับเอกสาร:

> โครงสร้างข้อมูลจะรองรับเส้นทางปริยาย (Default Route) ที่ใช้งานอยู่ได้ตั้งแต่ 0 ถึงหลายเส้นต่อชุดข้อมูลสถานะ ส่วนแดชบอร์ดของ MVP จะแสดงว่าพบเส้นทางหรือไม่และจำนวนที่พบ การทดสอบหลายเส้นทางแบบ ECMP เป็นกรณีเสริม หากอุปกรณ์หรือระบบจำลองของทีมรองรับครับ
## 7. การค้นหาอุปกรณ์เครือข่าย (Network Discovery) จะมีส่วนกลางสำหรับเชื่อมต่อและอ่านข้อมูลอุปกรณ์หรือไม่

ข้อนี้ต้องการคำตอบจากคนทำการค้นหาอุปกรณ์เครือข่าย (Network Discovery) โดยตรง เพราะมีผลว่าแดชบอร์ดและการติดตามสถานะ (Dashboard & Monitoring: D&M) ต้องสร้างระบบอ่านข้อมูลอุปกรณ์เองหรือขอใช้ระบบกลาง

อยากทราบว่าการค้นหาอุปกรณ์เครือข่าย (Network Discovery) จะมีส่วนที่ทำสิ่งต่อไปนี้หรือไม่:

- รับคำขอให้อ่านข้อมูลจากอุปกรณ์ที่ลงทะเบียนแล้ว
- เชื่อมต่ออุปกรณ์ด้วยบัญชีที่อ่านข้อมูลได้อย่างเดียว (Read-only Account)
- ส่งคำสั่งอ่านสถานะของอุปกรณ์สวิตช์ (Switch) และอุปกรณ์กำหนดเส้นทาง (Router)
- แยกผลสำเร็จหรือล้มเหลวเป็นรายอุปกรณ์
- เก็บเวลาเริ่มและเวลาสิ้นสุด
- ระบุสาเหตุที่ล้มเหลวอย่างปลอดภัย
- แปลงข้อความจากอุปกรณ์เป็นข้อมูลที่ฟีเจอร์ (Feature) อื่นนำไปใช้ได้

ตัวอย่างคำสั่งที่แดชบอร์ดและการติดตามสถานะ (D&M) อาจต้องใช้:

```text
อุปกรณ์สวิตช์ (Switch):
- show interfaces status
- show interfaces switchport
- show interfaces trunk
- show vlan brief

อุปกรณ์กำหนดเส้นทาง (Router):
- show ip interface brief
- show interfaces description
- show ip route
```

ตอบ เพื่อนบอกมีระบบกลางให้เรียก หรือง่ายๆเพื่อนบอกไปเรียกของเพื่อนได้
### ทางเลือก A — การค้นหาอุปกรณ์เครือข่าย (Network Discovery) มีระบบกลางที่รองรับงานเหล่านี้

แดชบอร์ดและการติดตามสถานะ (D&M) จะส่งคำขอไปใช้ระบบกลางและรับผลกลับมา โดยไม่สร้างส่วนเชื่อมต่ออุปกรณ์ซ้ำ

### ทางเลือก B — การค้นหาอุปกรณ์เครือข่าย (Network Discovery) ทำเฉพาะการค้นหาอุปกรณ์และเก็บข้อมูลเพื่อนบ้านจากโปรโตคอล LLDP/CDP

แดชบอร์ดและการติดตามสถานะ (D&M) จะรับผิดชอบการอ่านสถานะช่องเชื่อมต่อ (Interface), เครือข่ายเสมือน (VLAN) และข้อมูลเส้นทาง (Routing) ของตนเอง

### คำถามที่ต้องการคำตอบ

- การค้นหาอุปกรณ์เครือข่าย (Network Discovery) รับผิดชอบถึงระดับใด
- มีส่วนใดที่แดชบอร์ดและการติดตามสถานะ (D&M) ขอใช้ร่วมกันได้
- ผลข้อมูลที่ส่งให้ฟีเจอร์ (Feature) อื่นมีรูปแบบและสถานะอะไรบ้าง

## รูปแบบคำตอบที่ต้องการจากทีม

ยังไม่ต้องเสนอชื่อตารางหรือชื่อช่องข้อมูล ขอให้ตอบแต่ละข้อในรูปแบบนี้:

```text
ข้อที่:
เห็นด้วย / ไม่เห็นด้วย / ยังไม่แน่ใจ:
เหตุผล:
ฟีเจอร์ที่ได้รับผลกระทบ (Affected Feature):
ข้อเสนอที่ต้องการเปลี่ยน:
```

## เรื่องที่ต้องได้คำตอบก่อนเป็นอันดับแรก

ข้อ 7 สำคัญที่สุด เพราะจะกำหนดว่า:

- แดชบอร์ดและการติดตามสถานะ (D&M) ต้องสร้างส่วนเชื่อมต่อและอ่านข้อมูลอุปกรณ์เอง
- หรือควรขอใช้ส่วนกลางจากการค้นหาอุปกรณ์เครือข่าย (Network Discovery)

หากยังไม่มีคำตอบเรื่องอื่น ทีมยังสามารถออกแบบต่อโดยทำเครื่องหมายว่า “รอยืนยัน” ได้ แต่ไม่ควรสร้างระบบเชื่อมต่ออุปกรณ์ซ้ำกันก่อนตกลงข้อ 7
