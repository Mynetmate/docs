# Dashboard & Monitoring — สรุปการอัปเดต 04-09-2569

> **สำหรับทีม:** รอบนี้แยก P1 Dashboard ออกจาก P2 Operational Monitoring ให้ชัดเจน เอกสารเป็น Design/Contract และยังไม่ใช่หลักฐานว่า Full-stack พัฒนาเสร็จแล้ว

หลังจากรายงานความคืบหน้าครั้งที่ 1 และ 2 ผมได้กลับมาทบทวนขอบเขตของ Dashboard & Monitoring เพราะเอกสารเดิมรวมทั้ง Dashboard พื้นฐานและระบบติดตามเครือข่ายเชิงลึกไว้ด้วยกัน ทำให้ขอบเขตกว้างและต้องรอข้อมูลจาก Device Inventory กับ Network Discovery หลายส่วน

ผมจึงแบ่งงานออกเป็นสองระยะให้ชัดเจนครับ

**สำหรับ P1** ผมกำหนดให้ Dashboard เป็นหน้าสรุปข้อมูลที่ระบบมีอยู่แล้ว เพื่อให้ผู้ใช้เปิดมาแล้วตอบได้ทันทีว่า:

- มีอุปกรณ์ทั้งหมดกี่ตัว และสถานะล่าสุดเป็นอย่างไร
- มีผลตรวจสอบความปลอดภัยระดับสำคัญหรือไม่
- ผู้ใช้เพิ่งทำกิจกรรมอะไรในระบบ
- Backend, Database และ Offline Mode พร้อมทำงานหรือไม่
- มีทางลัดไปยังงานหลักตามสิทธิ์ของผู้ใช้
    
Dashboard จะไม่สร้างข้อมูล Device, Security หรือ Audit ซ้ำ แต่จะ**อ่านข้อมูลจาก Feature ที่เป็นเจ้าของ แล้วนำมาสรุปเป็นหน้าเดียว**

ส่วนความสามารถเชิงลึก เช่น การสั่งเก็บข้อมูลสถานะจากอุปกรณ์, Operational Snapshot, รายละเอียด Interface, VLAN, Access/Trunk, Uplink, WAN, Default Route, Expected State, กราฟย้อนหลัง และระบบแจ้งเตือน ผมยังไม่ได้ตัดทิ้ง แต่แยกไว้เป็น P2 Operational Monitoring เพราะต้องพึ่ง Device Inventory และ Network Discovery ที่มีโครงสร้างข้อมูลนิ่งก่อน

ด้านเอกสาร ผมได้จัดหมวดใหม่เป็น:

- `P1_Core` สำหรับขอบเขต Dashboard รุ่นแรก, Component Diagram, API Contract และ Acceptance Test
- `P2_Operational_Monitoring` สำหรับ Database Schema และความสามารถติดตามสถานะเชิงลึก
- `Archive_Research` สำหรับงานค้นคว้าและแนวคิดเดิมที่ไม่ใช่ข้อกำหนดปัจจุบัน
- Glossary กลางเพื่อป้องกันการใช้คำว่า ติดต่อไม่ได้ เก็บข้อมูลไม่ได้ ข้อมูลเก่า และระบบขัดข้องปะปนกัน
    
**ส่วนที่ตกลงกับ Audit Trail**  คือ Recent Activity จะอ่านข้อมูลอย่างเดียว แสดงเฉพาะเหตุการณ์ที่อนุญาต ใช้ Pagination และไม่ส่ง IP Address, รายละเอียด Error หรือข้อมูลลับไปยังหน้า Dashboard

**ตอนนี้งาน D&M อยู่ในสถานะ** “ออกแบบขอบเขตและสัญญาการเชื่อมต่อแล้วบางส่วน” ยังไม่ได้หมายความว่าพัฒนา Full-stack เสร็จ ส่วนที่ยังต้องรอทีมยืนยันมีสามเรื่อง:

1. ความหมายของสถานะอุปกรณ์และเวลาตรวจสอบล่าสุดจาก Device Inventory
	1. ต้องรู้ว่า `Offline` กับ `Unreachable` ต่างกันอย่างไร และควรใช้เวลาใดเป็น “ตรวจล่าสุด”  
		ตัวอย่าง: อุปกรณ์เพิ่งลงทะเบียนแต่ยังไม่เคยตรวจ ไม่ควรถูกนับว่าเสีย
2. โครงสร้างผลตรวจระดับ Critical จาก Security & Validation
	1. ต้องรู้ว่า Critical นับจากผลใด และผลที่ถูกยอมรับความเสี่ยงแล้วต้องนับอยู่หรือไม่  
		ตัวอย่าง: ตรวจพบ Critical 3 รายการ แต่ได้รับการยอมรับแล้ว 1 รายการ Dashboard ควรแสดง 3 หรือ 2
3. แหล่งที่เก็บค่า Offline Mode ของระบบ
	1. ต้องรู้ว่าค่าจริงเก็บที่ไหน เพื่อให้ Dashboard อ่านจากแหล่งเดียวกับระบบ  
		ตัวอย่าง: ถ้า Dashboard อ่านจากฐานข้อมูล แต่ระบบจริงอ่านจาก `.env` อาจแสดงว่า AI เปิดอยู่ ทั้งที่ระบบปิด AI แล้ว
    

เมื่อได้คำตอบ ผมจะปรับ API Contract และ Acceptance Test ให้ตรงกับข้อมูลจริง จากนั้นจึงเริ่มพัฒนา Dashboard ฝั่ง Backend และ Frontend แบบ End-to-End ครับ

สิ่งที่อยากขอให้อาจารย์ช่วยยืนยันคือ:

1. สำหรับ P1 ให้นำเสนอ Dashboard เป็นหน้าสรุปพื้นฐานก่อน และเลื่อนรายละเอียด VLAN, Access/Trunk, Port, Link, WAN และ Route ไปทำหลัง Dependency พร้อมได้หรือไม่
2. สถานะ “ยังไม่เคยตรวจ” ควรแยกจาก “ตรวจแล้วแต่ติดต่อไม่ได้” หรือไม่ เพื่อไม่ให้ Dashboard แจ้งว่าอุปกรณ์เสียทั้งที่ยังไม่มีข้อมูล
3. เห็นด้วยหรือไม่ที่ Dashboard P1 ไม่สร้างตารางข้อมูลซ้ำ แต่ดึงข้อมูลจาก Device Inventory, Security และ Audit Trail ผ่านข้อตกลงข้อมูลกลาง
    

หากอาจารย์มีเวลาน้อย ให้สรุปสั้นที่สุดว่า:

> “หลังรายงานครั้งที่ 2 ผมลด D&M P1 ให้เป็น Dashboard สรุปข้อมูลจาก Device, Security, Audit และ System Health ส่วนการเก็บ Snapshot และรายละเอียด Port/VLAN/WAN/Route แยกไป P2 ตอนนี้ Audit Contract พร้อมแล้ว เหลือยืนยันข้อมูลจาก Device Inventory, Security และ Settings ก่อนเริ่มทำ Full-stack ครับ”

เอกสารหลักที่ควรเปิดให้อาจารย์ดูคือ [P1_Core](P1_Core/) และแสดง [P2_Operational_Monitoring](P2_Operational_Monitoring/) เพียงเพื่อยืนยันว่า Feature เชิงลึกไม่ได้หาย แต่ถูกจัดลำดับใหม่ครับ


## คำถามเพื่อน

สำหรับกำหนดขอบเขต D&M P1 มีเพื่อนที่ต้องถามหลัก ๆ แค่ 3 ฝั่งครับ แต่ควรถามรายละเอียดให้ครบดังนี้

1. Device Inventory — Tee
    - `online`, `offline`, `unreachable` ต่างกันอย่างไร
    - อุปกรณ์ที่ยังไม่เคยตรวจใช้สถานะอะไร
    - `maintenance` ใครเป็นคนตั้ง
    - Dashboard ใช้ `last_seen_at` หรือ `last_collected_at`
    - รองรับการกรองตาม Site/Group ใน P1 หรือไม่
    - เอกสารหรือ Schema ใดคือฉบับยืนยัน
2. Security & Validation — King
    - Dashboard ต้องนับ Critical เป็น “จำนวน Finding” หรือ “จำนวนอุปกรณ์”
    - ใช้ผลสแกนล่าสุดของแต่ละอุปกรณ์ใช่หรือไม่
    - Finding ที่ Override/ยอมรับความเสี่ยงแล้วต้องถูกนับหรือไม่
    - ชื่อตารางหรือวิธีที่ Dashboard ขอข้อมูลคืออะไร
    - ถ้ายังไม่เคยสแกน ควรแสดง `0` หรือ “ยังไม่มีข้อมูล”
3. Settings/System — ทีมต้องกำหนด Owner
    - `offline_mode` เก็บในฐานข้อมูลหรือ `.env`
    - Feature ใดเป็นเจ้าของและเปลี่ยนค่านี้
    - Dashboard อ่านค่าผ่าน Service/Repository ใด
    - ถ้า Gemini ติดต่อไม่ได้ แต่ระบบส่วนอื่นทำงานได้ ควรแสดง `Degraded` ใช่หรือไม่

ส่วนที่ไม่ต้องถามซ้ำ:

- Authentication/RBAC: มี Contract แล้ว
- Audit Trail/Recent Activity: ยืนยันแล้ว
- PII และ Redaction ของ Recent Activity: ยืนยันแล้ว
- P2 Operational Monitoring: ยังไม่ต้องปิด Contract ตอนนี้

ดังนั้น “จำนวนเพื่อนที่ต้องคุย” มีเพียง Tee, King และคนที่รับผิดชอบ Settings/System ครับ หลังได้คำตอบสามฝั่งนี้จึงพอสำหรับล็อก API และเริ่ม D&M P1 ได้
