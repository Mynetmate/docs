# Building a Network Co-Pilot

"ตอนที่ผมเริ่มต้นทำงานในสายนี้ในฐานะวิศวกรเครือข่ายระดับจูเนียร์ ผมมีคำถามเยอะมาก เยอะมากๆ จริงๆ! คำตอบหลายอย่างพอจะหาได้จากหนังสือหรืออินเทอร์เน็ต แต่มันใช้เวลานานมากในการค้นหาจากหลายๆ แหล่งแล้วเอามาปะติดปะต่อกัน บางครั้งคำตอบก็อยู่ในรูปแบบของ 'ความรู้ที่รู้กันเฉพาะกลุ่ม (Tribal Knowledge)' ซึ่งแปลว่าผมต้องเสียเวลาเป็นชั่วโมงๆ ไปกับการนั่งไล่ดู Config เก่าๆ หรือต้องไปถามวิศวกรรุ่นพี่ แล้วถึงจะได้คำตอบที่พอใช้ได้ (ซึ่งก็ไม่แน่ว่าจะได้เสมอไป) พูดสั้นๆ คือ ผมหวังมาตลอดว่าอยากจะมี 'นักบินผู้ช่วยด้านเครือข่าย (Network Co-pilot)' ที่สามารถช่วยผมคัดกรองคำตอบ, ทำความเข้าใจระบบเครือข่าย, ตอบคำถามผมได้ตลอด 24 ชั่วโมง และเป็นเหมือนเพื่อนสนิทคู่คิดด้าน Network ของผม

บทนี้จะโฟกัสไปที่การสร้างเพื่อนคู่คิดแบบนั้นแหละครับ ให้มองว่า Network Co-pilot คือผู้ช่วย AI ที่เข้าใจเรื่อง Network โดยอ้างอิงจาก 'ข้อมูลเครือข่าย' ที่คุณป้อนให้มัน แทนที่คุณจะต้องไปนั่งอ่านคู่มือเป็นตั้งๆ หรือนั่งไล่จำคำสั่ง CLI คุณสามารถคุยกับ Co-pilot ของคุณได้เลย เช่น _"ช่วย Config OSPF บน Router Cisco ตัวนี้ให้หน่อย"_ หรือ _"ทำไม Error Counter ของพอร์ตนี้ถึงเด้งขึ้นตอนเที่ยงคืนของทุกๆ วันพุธเว้นพุธ?"_

Network Co-pilot ที่ดี **ไม่ได้ถูกสร้างมาเพื่อ 'แทนที่' ความเชี่ยวชาญของวิศวกรเครือข่าย แต่มันถูกสร้างมาเพื่อ 'ขยายขีดความสามารถ (Amplify)' ต่างหาก** มันช่วยให้เราทำงานได้เร็วขึ้น จับจุดผิดพลาด และคอยแนะนำเพื่อให้เราทำงานสำเร็จได้มากขึ้น

ในบทนี้ เราจะมาสร้างองค์ประกอบหลักที่ทำให้ Network Co-pilot ทำงานได้จริง เราอาจจะไม่ได้ทำแอปพลิเคชันระดับ Production ตัวเต็ม (เพราะถ้าทำขนาดนั้นคงต้องเขียนหนังสือแยกอีกเล่ม!) แต่เราจะสร้างชิ้นส่วนสำคัญที่ทำให้คุณเห็นภาพว่าทั้งหมดมันทำงานร่วมกันได้อย่างไร

นี่คือสิ่งที่เราจะทำในบทนี้:

- การเลือกและประเมินโมเดล AI (Model selection and evaluation)
- การสร้างสมองหลักของ AI (Building the core AI engine)
- การควบรวมองค์ความรู้ด้านเครือข่าย (Network knowledge integration)

เนื้อหาบางส่วนอาจจะเป็นการทบทวนสิ่งที่เราเคยพูดถึงในบทก่อนๆ ซึ่งไม่เป็นไรครับ เพราะเราตั้งใจจะเน้นย้ำเรื่อง 'Network Co-pilot' ในบทนี้ แม้ว่าจะต้องอ้างอิงถึงองค์ประกอบบางอย่างที่เราเคยเรียนไปแล้วก็ตาม"

**💡 อธิบายและขยายความ (Explanation):**

ผู้เขียนกำลังปูพื้นฐาน **"เหตุผลความจำเป็น" (Pain point)** ของวิศวกรเครือข่าย นั่นคือความรู้ด้าน Network มักจะกระจัดกระจาย หรือไม่ก็อยู่ในหัวของคนเก่าคนแก่ (Tribal Knowledge) ทำให้คนทำงานใหม่ๆ หรือแม้แต่คนเก่าที่เจอปัญหาแปลกๆ ต้องเสียเวลามากในการหาคำตอบ

เขาเปรียบเทียบ AI ว่าเป็น **"Co-pilot (นักบินผู้ช่วย)"** ซึ่งเป็นคำที่อธิบายบทบาทของ AI ในยุคปัจจุบันได้ดีที่สุด นักบินผู้ช่วยไม่ได้มาแย่งงานนักบินหลัก (ตัววิศวกร) แต่นักบินผู้ช่วยมีหน้าที่ประมวลผลข้อมูลมหาศาลรอบตัว แล้วสรุปมาให้นักบินหลักตัดสินใจ ทำให้บินได้ปลอดภัยและเร็วขึ้น (Amplify expertise)


**🔗 ความสอดคล้องกับโปรเจกต์ MyNetMate ของเรา:**

ข้อความนี้ **"สอดคล้องกับแก่นแท้ของ MyNetMate แบบ 100%"** ครับ และคุณสามารถนำประโยคเหล่านี้ไปใช้ตอบคำถามอาจารย์ที่ปรึกษาเพื่อป้องกันการถูกโจมตีเรื่อง AI ได้เลยครับ:

1. **ปรัชญาของโปรเจกต์ตรงกันเป๊ะ:** หนังสือบอกชัดเจนว่า _"A good network co-pilot does not replace a network engineer’s expertise; it amplifies it."_ ซึ่งสอดคล้องกับสโลแกนโปรเจกต์คุณที่ว่า **"ใช้ AI เมื่อต้องการ 'ความเข้าใจ' ไม่ใช้ AI เมื่อต้องการ 'ความถูกต้อง'"** เราไม่ได้ให้ AI ทำงานแทนแบบ Auto-pilot แต่เราให้มันเป็น Co-pilot ช่วยเราคิด
2. **ความสำคัญของการป้อนข้อมูลเครือข่ายให้ AI:** หนังสือบอกว่า AI จะเก่งได้ด้วย _"network data you are willing to supply"_ ซึ่งตรงกับ Architecture ของเราที่เราใช้ **PostgreSQL (Source of Truth)** เป็นตัวเก็บ Inventory/Topology แล้วป้อนข้อมูลนี้ให้ **Gemini (AI)** รู้ก่อนที่มันจะตอบคำถาม
3. **การแก้ปัญหา Tribal Knowledge:** MyNetMate จะกลายเป็นศูนย์กลางที่เก็บข้อมูล Config ของทั้ง Cisco, MikroTik, Huawei ไว้ที่เดียวกัน ทำให้เราไม่ต้องไปพึ่งพาความรู้ที่อยู่ในหัวของพี่ๆ วิศวกรเก่าๆ อีกต่อไป

**สรุป:** ข้อความนี้เหมือนเป็นคำประกาศเจตนารมณ์ (Manifesto) ของโปรเจกต์ MyNetMate เลยครับ ยืนยันว่าเรากำลังมาถูกทางอย่างมาก!
## Technical requirements

1. **สร้างพื้นที่จำลอง (Virtual Environment):** เพื่อให้แยกสภาพแวดล้อมการทำงานของโปรเจกต์นี้ออกจากการเขียน Python ทั่วไปในเครื่อง จะได้ไม่มีปัญหาเวอร์ชันชนกัน
2. **ติดตั้งไลบรารีและตั้งค่ากุญแจ (API Key):**
    - `$ pip install openai requests panda`: คำสั่งติดตั้งชุดเครื่องมือของ Python
        - `openai` = ใช้คุยกับ ChatGPT
        - `requests` = ใช้ดึงข้อมูล/ยิง API ผ่าน HTTP
        - `panda` = (หนังสือพิมพ์ผิดครับ ที่ถูกต้องคือ `pandas` เติม s) ใช้จัดการข้อมูลตาราง วิเคราะห์ข้อมูล
    - `$ export OPENAI_API_KEY="your-openai-api-key"`: คำสั่งฝัง **"กุญแจลับ (API Key)"** เข้าไปในระบบปฏิบัติการของคอมพิวเตอร์ เพื่อให้โค้ด Python ดึงไปใช้งานได้โดยไม่ต้องเขียนรหัสผ่านทิ้งไว้ในไฟล์โค้ดตรงๆ (เป็นเรื่องของความปลอดภัย)


**🔗 ความสอดคล้องกับโปรเจกต์ MyNetMate ของเรา:**

อันนี้สอดคล้องกับ **ขั้นตอนการตั้งค่าโปรเจกต์ตอนเริ่มต้น (Setup Project)** ของเราเป๊ะๆ เลยครับ เพียงแต่เครื่องมือที่เราใช้จะต่างกันนิดหน่อยให้เข้ากับงานของเรา:

1. **ไลบรารี (Libraries):** ของเราจะไม่ติดตั้ง `openai` แต่เราจะใช้ `$ pip install google-generativeai` เพื่อคุยกับ **Gemini** แทนครับ ส่วน `requests` เราก็ใช้เหมือนกันครับ
2. **การตั้งค่า API Key:** หลักการของหนังสือถูกต้องเรื่องความปลอดภัย แต่ปัจจุบันในโปรเจกต์ที่ใช้ FastAPI (เหมือนที่เราทำ) เขา **ไม่นิยมใช้คำสั่ง `export` แล้วครับ** เพราะพอรีสตาร์ทคอมพิวเตอร์มันก็หายไป
    - **ทางแก้ของเรา (Best Practice):** เราจะสร้างไฟล์ที่ชื่อว่า `.env` ไว้ในโปรเจกต์ แล้วเขียนรหัสไว้ข้างในว่า `GEMINI_API_KEY=รหัสของเรา` จากนั้นให้ FastAPI ดึงไปใช้ ซึ่งเป็นวิธีที่เป็นมาตรฐานสากลมากกว่าครับ
