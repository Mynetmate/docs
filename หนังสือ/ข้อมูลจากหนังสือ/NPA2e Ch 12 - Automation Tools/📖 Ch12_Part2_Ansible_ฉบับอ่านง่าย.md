## 🅰️ Ansible คืออะไร?
**Ansible** (ดูแลโดย Red Hat) คือเครื่องมือ Automation แบบ Agentless (ไม่ต้องติดตั้งโปรแกรมปลายทาง) ที่ทรงพลังและเรียนรู้ง่ายที่สุดตัวหนึ่ง เพราะใช้ภาษา **YAML** ในการเขียนคำสั่ง ทำให้มนุษย์อ่านเข้าใจได้ทันที (Human-readable)

หลักการทำงานกับ Network Device คือ Ansible จะจำลองตัวเองรันอยู่ในเครื่องศูนย์กลาง (Control Node) แล้วใช้การเชื่อมต่อผ่าน **SSH (Push Model)** ส่งคำสั่ง Command Line ลงไปที่ Router/Switch คล้ายกับที่คนทำ

## 📁 โครงสร้างหลักของ Ansible (Architecture)

เพื่อให้ Ansible ทำงานได้ จะต้องประกอบด้วยองค์ประกอบ 3 ส่วนหลัก:

### 1. Inventory (บัญชีรายชื่ออุปกรณ์)
เปรียบเหมือน "สมุดหน้าเหลือง" ที่รวบรวมรายชื่ออุปกรณ์ทั้งหมดในระบบ 
- เขียนได้ทั้งฟอร์แมต INI หรือ YAML
- **การจัดกลุ่ม (Groups):** สามารถจัดกลุ่มอุปกรณ์ได้ เช่น `[routers]`, `[switches]` หรือแยกตามสาขา `[bkk_site]`
- **ตัวแปร (Variables):** สามารถกำหนดตัวแปรให้แต่ละ Group (`group_vars`) หรือแต่ละ Host (`host_vars`) ได้เลย เพื่อให้ Playbook นำไปใช้
- **Dynamic Inventory:** ถ้าระบบมีอุปกรณ์เยอะมาก สามารถตั้งให้ Ansible วิ่งไปดึงรายชื่อจาก Database (เช่น CMDB หรือ NMS) แบบอัตโนมัติได้

### 2. Playbook (ชุดคำสั่งอัตโนมัติ)
เปรียบเหมือน "คู่มือปฏิบัติงาน (Runbook)" ที่บอกว่าต้องทำอะไรบ้าง โครงสร้างของมันแบ่งเป็นลำดับชั้น:
1. **Playbook:** ไฟล์ YAML หลักที่รวมทุกอย่างไว้
2. **Play:** กำหนดว่าจะเอาคำสั่งไปรันกับกลุ่มอุปกรณ์ (Inventory Group) ไหน
3. **Task:** ขั้นตอนย่อย 1 ขั้นตอน (เช่น "โชว์เวอร์ชัน", "ตั้งค่า OSPF")
4. **Module:** เครื่องมือเฉพาะทางที่ใช้ทำ Task นั้นๆ

### 3. Modules (โมดูลคำสั่ง)
Ansible มี Module สำเร็จรูปสำหรับ Network Device โดยแบ่งเป็น 3 ประเภทหลัก:
- `command` (เช่น `cisco.ios.ios_command`): ส่งคำสั่งระดับ exec mode (เช่น คำสั่ง `show` ต่างๆ)
- `config` (เช่น `cisco.ios.ios_config`): ส่งคำสั่งเพื่อตั้งค่าระดับ global configuration (เช่น สร้าง VLAN, เซ็ต IP)
- `facts` (เช่น `cisco.ios.ios_facts`): ดึงข้อมูลสถานะของอุปกรณ์ (เช่น OS version, Serial number) มาเก็บเป็นตัวแปรแบบอัตโนมัติ

## 🛠️ ฟีเจอร์ที่น่าสนใจสำหรับการทำ Network Automation

1. **Configuration Templates (Jinja2):** 
   Ansible มักใช้คู่กับ **Jinja2** เสมอ โดยแยกไฟล์ Template โครงสร้าง Config ไว้ต่างหาก แล้วเอาตัวแปร (Variables) ของแต่ละอุปกรณ์มาสวมทับ ทำให้สร้าง Config ได้รวดเร็วและเป็นมาตรฐาน
2. **Idempotency (ความปลอดภัยในการรันซ้ำ):**
   นี่คือจุดแข็งของ Ansible! โมดูลฝั่ง Config จะถูกออกแบบมาให้ "เช็กก่อนส่ง" ถ้าพบว่าอุปกรณ์ตั้งค่าถูกต้องอยู่แล้ว มันจะข้ามการทำงานนั้นไป (ไม่ส่ง Config ซ้ำซาก) ป้องกันระบบชะงัก
3. **Register (เก็บผลลัพธ์):**
   สามารถส่งคำสั่ง `show` แล้วใช้คำสั่ง `register` เพื่อเก็บผลลัพธ์กลับมาใส่ตัวแปร จากนั้นเอาไปตรวจสอบเงื่อนไข (Compliance Check) ผ่านโมดูล `assert` ได้
4. **Roles (การจัดระเบียบโค้ด):**
   ถ้า Playbook เริ่มยาวและซับซ้อน เราสามารถแพ็กเกจมันให้กลายเป็น **Roles** (คล้ายๆ การทำ Function/Class ใน Python) เพื่อเอาไปแชร์ให้คนอื่นใช้ต่อได้ง่ายๆ

## 🧩 ส่วนเสริม (Third-Party Collections)
วงการ Network นิยมใช้ Collection เสริมเพื่อให้ Ansible เก่งขึ้น เช่น:
- **NAPALM:** ช่วยทำให้คำสั่งเป็นมาตรฐานเดียวกัน (Multivendor Abstraction) ไม่ว่าจะเป็น Cisco หรือ Juniper ก็ใช้คำสั่งเดียวกันได้
- **NTC Modules:** นำไลบรารี **Netmiko** และ **TextFSM** มาผสานร่างกับ Ansible ทำให้สามารถ Parse ข้อมูล CLI ดิบให้ออกมาเป็น JSON/Dictionary ได้เลย (รองรับอุปกรณ์กว่า 100 รุ่น)

## 🔗 ถอดบทเรียนประยุกต์ใช้กับ MyNetMate

เราสามารถนำแนวคิดของ Ansible มาใช้พัฒนาระบบ Backend ของเราได้เลยครับ:

1. **Inventory ของเราล้ำกว่า:** Ansible ใช้ไฟล์ YAML (`hosts.yml`) เป็น Inventory แต่ **MyNetMate ใช้ PostgreSQL (Database)** เป็น Dynamic Inventory ซึ่งเสถียรและตอบโจทย์ระบบ Web Application ได้ดีกว่า
2. **Netmiko + TextFSM:** หนังสือบอกว่า NTC Modules ใน Ansible ใช้ Netmiko + TextFSM เป็นเบื้องหลัง นี่คือการ **"คอนเฟิร์มว่า Tech Stack (FastAPI + Netmiko + TextFSM) ที่เราเลือกใช้นั้นคือมาตรฐานระดับอุตสาหกรรม"** ครับ!
3. **Idempotency (ความทนทานต่อการรันซ้ำ):** เป็นสิ่งที่เราต้องนำมาเขียนโค้ดเพิ่มใน MyNetMate ครับ (เช่น ก่อนที่ AI จะส่งคำสั่งสร้าง VLAN ให้เขียนลอจิกแอบเช็กก่อนว่ามี VLAN นั้นอยู่แล้วหรือยัง ถ้ามีแล้วก็ให้ AI แจ้งเตือนผู้ใช้แทนการส่ง Config ทับลงไป)
4. **Compliance Check (วิเคราะห์ผลกระทบ):** คล้ายกับระบบ Impact Analysis ที่เราออกแบบไว้ คือเช็กก่อนและหลัง Config เพื่อความปลอดภัย

> **💡 บทสรุป:** Ansible เหมาะสำหรับฝั่ง System Admin ที่ไม่อยากเขียนโค้ด Python เอง แต่สำหรับโปรเจกต์ระดับ Web Application แบบเรา การเขียน Python ตรงๆ (แบบ Nornir ในส่วนถัดไป) จะตอบโจทย์ได้มากกว่าครับ
