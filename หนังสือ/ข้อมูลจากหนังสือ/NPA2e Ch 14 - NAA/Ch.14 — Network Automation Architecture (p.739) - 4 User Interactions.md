เนื้อหาในหัวข้อ **"User Interactions" (การปฏิสัมพันธ์ของผู้ใช้)** สามารถสรุปและอธิบายรายละเอียดโดยอิงตามข้อเท็จจริงจากหนังสือได้ดังนี้ครับ

### 1. หัวข้อนี้พูดถึงอะไร?

หัวข้อนี้พูดถึง **ความสำคัญของ "ส่วนต่อประสานกับผู้ใช้งาน (User Interfaces)" ในระบบอัตโนมัติสำหรับเครือข่าย** หนังสือเน้นย้ำว่าแม้เรากำลังสร้างระบบอัตโนมัติ แต่สุดท้ายแล้ว "ผู้ใช้งานที่เป็นมนุษย์ (End user)" ก็ยังคงต้องเข้ามาปฏิสัมพันธ์กับระบบเหล่านั้นอยู่เสมอ

หัวใจสำคัญคือการทำความเข้าใจบทบาท ทักษะ และแรงจูงใจของผู้ใช้งานแต่ละกลุ่ม (Persona) เพื่อเลือกใช้อินเทอร์เฟซที่เหมาะสม ซึ่งจะช่วยยกระดับประสบการณ์ผู้ใช้ (UX) และทำให้ผู้คนยอมรับการนำโซลูชันนี้ไปใช้งานได้ดีขึ้น นอกจากนี้ยังพูดถึงความท้าทายหลักในการจัดการ **"ข้อมูลขาเข้า (Data In)"** และ **"ข้อมูลขาออก (Data Out)"** เพื่อให้ระบบทำงานได้อย่างราบรื่นและลดข้อผิดพลาดจากมนุษย์

### 2. รายละเอียดและตัวอย่างทั้งหมดที่ปรากฏในหนังสือ


**ประเด็นที่ 1: การออกแบบอินเทอร์เฟซตามกลุ่มผู้ใช้งาน (Tailoring UX)** การเปลี่ยนเพียงแค่หน้าตาอินเทอร์เฟซ (UI) สามารถพลิกโฉมประสบการณ์ผู้ใช้ (UX) ได้โดยไม่จำเป็นต้องไปปรับเปลี่ยนระบบเบื้องหลัง (Underlying system)

- **ตัวอย่างที่หนังสือยกมา:** ลองจินตนาการว่าคุณกำลังบริหารจัดการผู้ให้บริการคอนเทนต์อินเทอร์เน็ตที่มีจุดเชื่อมต่อ (PoPs) และ BGP peerings จำนวนมาก
    
    - **ทีมปฏิบัติการเครือข่าย (Network operations team):** มักจะชื่นชอบอินเทอร์เฟซแบบบรรทัดคำสั่ง (CLI-like interface) เพราะเป็นวิธีที่พวกเขาคุ้นเคยในการใช้แก้ปัญหา (Troubleshoot)
        
    - **ทีมจัดการความจุเครือข่าย (Network capacity team):** จะรู้สึกสบายใจมากกว่าหากได้ใช้งานผ่านหน้าแดชบอร์ด (Dashboard) ที่นำเสนอข้อมูลในรูปแบบที่เข้าใจและนำไปใช้ต่อได้ง่าย
        

**ประเด็นที่ 2: เทรนด์การใช้งานเครือข่ายเสมือนบริการ (Network as a Service - NaaS)** การใช้งานโซลูชันบนคลาวด์อย่างแพร่หลายทำให้ผู้คนเคยชินกับการเข้าถึงโครงสร้างพื้นฐานได้แบบแทบจะเรียลไทม์

- **คำอธิบายแนวคิด:** การสร้างประสบการณ์การใช้งานเครือข่ายแบบบริการตนเอง (Self-service experience) ให้คล้ายคลึงกับคลาวด์ จะตอบสนองความคาดหวังของผู้ใช้ ลดความยุ่งยากในการใช้งาน และช่วยให้ทีมวิศวกรเครือข่ายใช้เวลาได้อย่างมีประสิทธิภาพมากขึ้น แม้การทำ NaaS จะซับซ้อน แต่ส่วน User Interaction คือด่านหน้า (Front end) ที่ต้องพร้อมมอบ UX ที่เหมาะสม
    

**ประเด็นที่ 3: ประเภทของอินเทอร์เฟซที่จะนำเสนอ** หนังสือระบุว่าจะครอบคลุมทั้งอินเทอร์เฟซแบบกราฟิก (Graphical) และแบบข้อความ (Text-based) ทั้งสำหรับใช้จัดการสถานะเครือข่าย หรือแค่ใช้เฝ้าสังเกตการณ์

- **คำอธิบายแนวคิด:** รวมไปถึงระบบแชร์ความรู้ (Knowledge share) หรือการทำเอกสาร (Documentation) เพราะมีความสำคัญต่อการทำความเข้าใจและต่อยอดระบบ เคล็ดลับคือต้องดึงศักยภาพของเครื่องมือเหล่านี้ออกมาให้เป็น "ด่านแรกของระบบอัตโนมัติ" ไม่ใช่เป็นแค่หน้าจอสำหรับมนุษย์ทั่วไป
    

**ประเด็นที่ 4: ความท้าทายเรื่องการจัดการข้อมูล (Data In และ Data Out)** ความท้าทายร่วมกันของทุกส่วนปฏิสัมพันธ์คือการกำหนดข้อมูลทั้งสองทิศทาง

- **1. ข้อมูลขาเข้า (Data In):** ข้อมูลที่ผู้ใช้ป้อนเข้ามาต้องตรงตามความคาดหวังของระบบ ปฏิบัติตามโครงสร้าง (Schemas) และมีกฎการตรวจสอบ (Validation rules) เพื่อรักษาคุณภาพข้อมูล นอกจากนี้ยังต้องเน้น "ความเรียบง่าย" คือขอข้อมูลจากผู้ใช้ให้น้อยที่สุดเท่าที่จำเป็น และปล่อยให้ระบบอัตโนมัติจัดการส่วนที่เหลือเพื่อลดข้อผิดพลาดจากมนุษย์
    
    - **ตัวอย่างกฎการตรวจสอบข้อมูล:** สมมติว่าข้อมูลอินพุตคือที่อยู่ IPv6 ของโฮสต์ ตัว UI จะต้องไม่ยอมรับรูปแบบใดๆ ก็ตามที่ไม่เป็นไปตามมาตรฐาน RFC ที่กำหนดรูปแบบของ IPv6
        
    - **ตัวอย่างการลดภาระผู้ใช้ (ความเรียบง่าย):** หากมีการร้องขอให้ติดตั้งอุปกรณ์ใหม่ในพื้นที่หนึ่ง และชื่อของอุปกรณ์นั้นมีมาตรฐานการตั้งชื่อ (Naming convention) กำหนดไว้อยู่แล้ว ผู้ใช้ก็ไม่จำเป็นต้องมีตัวเลือกให้พิมพ์ตั้งชื่ออุปกรณ์เอง แต่ระบบอัตโนมัติจะเป็นคนกำหนดชื่อนั้นให้โดยอัตโนมัติ
        
    - **ตัวอย่างความรับผิดชอบร่วมกันของระบบ:** คุณภาพข้อมูลไม่ได้เป็นหน้าที่ของหน้า UI อย่างเดียว จากตัวอย่างเรื่อง IPv6 ข้างต้น ในขั้นตอนต่อมาของระบบอัตโนมัติ อาจมีการตรวจสอบพบปัญหาและแจ้งเตือนได้ หากที่อยู่ IP นั้นถูกใช้งานไปแล้ว หรือไม่ตรงกับการออกแบบ Routing
        
- **2. ข้อมูลขาออก (Data Out):** ข้อมูลที่ผู้ใช้แต่ละคนต้องการจะแตกต่างกันไปตามบทบาทของพวกเขา ข้อมูลขาออกต้องมีรายละเอียดเพียงพอให้เข้าใจผลลัพธ์ของงานที่ระบบทำไป (อาจใช้ข้อความ ลิงก์ หรือรูปภาพ) และที่สำคัญ ข้อมูลขาออกไม่ได้หมายถึงผลลัพธ์สุดท้ายเมื่อจบงานเท่านั้น แต่หมายรวมถึงสิ่งที่แสดงระหว่างทางด้วย
    
    - **ตัวอย่างข้อมูลผลลัพธ์ตามระบบที่ใช้:** หากเวิร์กโฟลว์เริ่มต้นขึ้นผ่านระบบจัดการทิกเก็ต (Ticketing system) ข้อมูลขาออก (Data out) ก็มักจะอยู่ในรูปแบบของการอัปเดตสถานะลงในทิกเก็ตนั้น
        
    - **ตัวอย่างข้อมูลขออกระหว่างทาง:** ในระหว่างที่ระบบอัตโนมัติกำลังรันเวิร์กโฟลว์ อาจมีการส่งข้อมูลออกมาแสดงให้ผู้ใช้เห็นเพื่อบอกความคืบหน้า หรือเพื่อขอให้ผู้ใช้เข้ามามีส่วนร่วม เช่น "การส่งคำร้องขออนุมัติงาน (A task approval request)"

Graphical user interfaces
หัวข้อย่อยนี้พูดถึงบทบาทและวัตถุประสงค์ที่หลากหลายของ GUI ซึ่งแต่ละรูปแบบล้วนมีลักษณะเฉพาะตัวของมันเอง โดยเนื้อหาหลักสามารถสรุปได้เป็น 3 ประเด็นสำคัญตามที่หนังสือระบุไว้ครับ:

- **การแนะนำ GUI ยอดนิยม 3 ประเภท**: เนื้อหาในส่วนนี้จะทำการทบทวนและตรวจสอบ GUI ที่ได้รับความนิยมมากที่สุด 3 รูปแบบ ซึ่งถูกนำมาใช้ตอบโจทย์หน้าที่การทำงานที่แตกต่างกัน
    
- **ข้อเท็จจริงเกี่ยวกับ GUI ของเครื่องมืออื่นๆ**: หนังสือชี้ให้เห็นว่าเมื่อเราไล่ดูส่วนประกอบของสถาปัตยกรรม จะพบว่ามีเครื่องมืออื่นๆ อีกมากมายที่นำเสนอ GUI ให้ใช้งานเช่นกัน แม้ว่าเป้าหมายหลักของเครื่องมือเหล่านั้นไม่ได้สร้างมาเพื่อปฏิสัมพันธ์กับผู้ใช้ปลายทาง (End user) แต่สร้างขึ้นมาเพื่อให้เป็นอินเทอร์เฟซที่เข้าถึงได้ง่าย (Low-barrier interface) ในการสั่งงานฟังก์ชันต่างๆ ของมันเอง ซึ่งเครื่องมือส่วนใหญ่มักมี UI ที่ใช้งานได้ดีสำหรับวิศวกรเครือข่าย แต่อาจไม่เหมาะสมสำหรับผู้ใช้ปลายทางทุกคน
    
- **หลักการเลือกใช้งาน**: หนังสือให้คำแนะนำสำคัญว่าในการเลือกเครื่องมือที่ถูกต้องนั้น เราจะต้องคำนึงถึงมุมมองของผู้ใช้งานปลายทางอยู่เสมอ
    

IT service management

เนื้อหาในหัวข้อ **"IT service management" (การบริหารจัดการบริการไอที)** สามารถสรุปและอธิบายรายละเอียดโดยอิงตามข้อเท็จจริงที่ปรากฏในหนังสือต้นฉบับได้ดังนี้ครับ

## 1. หัวข้อนี้พูดถึงอะไร?

หัวข้อนี้พูดถึง **"ระบบบริหารจัดการบริการไอที หรือ IT Service Management (ITSM)"** ซึ่งเป็นที่รู้จักกันในชื่อ พอร์ทัลบริการตนเอง (Self-service portals) โดยอธิบายบทบาทของระบบนี้ในฐานะจุดเริ่มต้นหลักของเวิร์กโฟลว์เครือข่าย คุณสมบัติสำคัญที่ช่วยสนับสนุนการทำงานร่วมกับระบบอัตโนมัติ และแนวคิดการปรับใช้องค์กรผ่านการบริหารจัดการความเปลี่ยนแปลง (Change Management)

เจาะลึกรายละเอียดโครงสร้างตามที่หนังสือระบุมีดังนี้:

- **บทบาทและโครงสร้าง**: แพลตฟอร์ม ITSM ทำหน้าที่เป็นประตูทางเข้าสำหรับการร้องขอใช้บริการทุกประเภทที่มีอยู่ในคลังบริการ (Service catalog) ขององค์กร โดยแต่ละบริการจะมีการกำหนดขั้นตอนการส่งมอบไว้ชัดเจนว่าประกอบด้วยหลายขั้นตอนในกระบวนการ การนำมาใช้งานในรูปแบบที่เรียบง่ายที่สุดจะทำหน้าที่เป็นระบบออกตั๋วงาน (Ticketing system) เพื่อบริหารจัดการวงจรชีวิตของคำร้อง (Request lifecycle) ซึ่งรวมถึงขั้นตอนการอนุมัติ การติดตามตรวจสอบย้อนหลัง และการแจ้งเตือน
    
- **แนวโน้มและการเปลี่ยนผ่าน**: ปัจจุบันบริการเครือข่ายต่างๆ ได้มีการขยับขยายมาสู่บริการรูปแบบ ITSM มากขึ้น เนื่องจากมีข้อดีและผลประโยชน์ที่เหนเหนือกว่าระบบสื่อสารรูปแบบเดิม
    
- **ความเข้าใจที่ถูกต้องเกี่ยวกับระบบอัตโนมัติ**: หนังสือระบุข้อเตือนใจว่า การเลือกใช้ระบบ ITSM ไม่ได้หมายความว่าจะเกิดการทำงานแบบอัตโนมัติขึ้นในตัวเองทันที (Using an ITSM doesn’t imply any automation per se) วิศวกรยังคงสามารถดำเนินการทุกขั้นตอนในกระบวนการส่งมอบบริการด้วยมือ (Manual) ได้ทั้งหมด แต่เป้าหมายของกลยุทธ์การทำ Network Automation คือการเปลี่ยนผ่านขั้นตอนเหล่านี้ให้กลายมาเป็นงานที่เครื่องจักรหรือระบบคอมพิวเตอร์สามารถทำแทนได้
    
- **กระบวนการปรับปรุงแบบค่อยเป็นค่อยไป**: ตลอดเส้นทางการทำระบบอัตโนมัติ ผู้ดูแลจะค่อยๆ ปรับปรุงกระบวนการและเพิ่มงานอัตโนมัติเข้าไปทีละส่วนอย่างต่อเนื่อง อย่างไรก็ตาม มันไม่ใช่เรื่องประเภทที่ว่าต้องทำทั้งหมดหรือไม่ได้ทำเลย (It’s not all or none) เพราะในบางสถานการณ์ การเหลือบางขั้นตอนให้เป็นการทำงานด้วยมือ หรือการคงจุดตรวจสอบที่ต้องใช้การตัดสินใจของมนุษย์ (Human judgment gates) ตลอดกระบวนการไว้ ก็ถือเป็นเรื่องที่สมเหตุสมผล
    

## 2. คุณสมบัติหลักของ ITSM ยุคใหม่ที่สนับสนุนระบบอัตโนมัติ

แพลตฟอร์ม ITSM สมัยใหม่มาพร้อมคุณสมบัติมากมายที่ช่วยส่งเสริมการทำงานของระบบอัตโนมัติ เนื่องจากระบบช่วยเพิ่มประสิทธิภาพการใช้ทรัพยากรและปรับปรุงระยะเวลาในการส่งมอบบริการให้เหมาะสมที่สุด โดยหนังสือได้ระบุคุณสมบัติเด่นไว้ดังนี้:

- **การตั้งค่าข้อมูลขาเข้า (Configurable data input)**: รองรับการตรวจสอบความถูกต้องของข้อมูล (Validation) และการแปลงข้อมูลดิบให้กลายเป็นข้อมูลที่มีโครงสร้าง (Structured data) โดยคำนึงถึงหลักความเรียบง่าย ผู้ใช้งานควรป้อนเฉพาะข้อมูลที่เกี่ยวข้องและจำเป็นต่อการส่งมอบบริการเท่านั้น และข้อมูลดังกล่าวต้องเป็นไปตามข้อตกลงเฉพาะที่สอดคล้องกับความคาดหวังของขั้นตอนถัดไปในเวิร์กโฟลว์
    
- **การเชื่อมต่อข้อมูลขาเข้า (Input integrations)**: ทำหน้าที่ดึงข้อมูลจากแหล่งข้อมูลหลายแห่งเข้ามาในระบบเพื่อช่วยเหลือผู้ใช้งานให้กรอกข้อมูลได้ง่ายขึ้น
    
- **การเชื่อมต่อระบบภายนอก (Triggering integrations)**: ทำการสั่งงานหรือเปิดกระบวนการไปยังส่วนประกอบภายนอกผ่านทาง APIs ซึ่งงานอัตโนมัติเหล่านี้มักต้องใช้เวลาและไม่ได้เสร็จสิ้นลงในทันที ดังนั้นระบบภายนอกที่ได้รับคำร้องไป เมื่อทำงานเสร็จสิ้นแล้ว จะต้องสามารถแจ้งเตือนกลับมายังระบบ ITSM เพื่อบอกผลลัพธ์และให้ ITSM ดำเนินกระบวนการต่อได้
    
- **ระบบแจ้งเตือน (Notification systems)**: ทำหน้าที่ปฏิสัมพันธ์และสื่อสารกับมนุษย์ที่มีส่วนร่วมในกระบวนการส่งมอบบริการ
    

## 3. ตัวอย่างทั้งหมดในหนังสือและการอธิบายอย่างละเอียด

หนังสือได้มีการระบุและยกตัวอย่างสถานการณ์ต่างๆ เพื่ออธิบายให้เห็นภาพชัดเจนขึ้น ดังนี้ครับ:

- **ตัวอย่างระบบสื่อสารแบบเดิมที่เป็นปัญหา**:
    
    > "...other communication systems that make coordination harder, like email loops."
    
    - _อธิบายตามหนังสือ_: หนังสือยกตัวอย่าง **"การส่งอีเมลโต้ตอบกลับกันไปมา (Email loops)"** เพื่อชี้ให้เห็นว่าเป็นระบบสื่อสารที่ทำให้การประสานงานร่วมกันระหว่างทีมทำได้ยากลำบาก และเป็นสาเหตุที่บริการเครือข่ายต้องเปลี่ยนมาใช้ ITSM แทน
        
- **ตัวอย่างการเชื่อมต่อข้อมูลขาเข้า (Input Integration)**:
    
    > "For example, if the user has to enter a location to deliver a service, being able to retrieve the available location from a facility management system makes the input process simpler and more reliable."
    
    - _อธิบายตามหนังสือ_: หนังสือยกตัวอย่างว่า **"หากผู้ใช้งานจำเป็นต้องระบุสถานที่เพื่อรับบริการ"** การที่ระบบ ITSM สามารถเชื่อมต่อเพื่อไปดึงรายชื่อสถานที่ที่มีอยู่จริงมาจากระบบบริหารจัดการอาคารหรือสิ่งอำนวยความสะดวก (Facility management system) มาแสดงผลให้เลือกได้ทันที จะช่วยให้ขั้นตอนการป้อนข้อมูลของผู้ใช้งานมีความง่ายขึ้นและมีความน่าเชื่อถือสูงขึ้นมาก
        
- **ตัวอย่างการทำงานของระบบแจ้งเตือนต่อมนุษย์**:
    
    > "...for instance, requesting approval from a qualified team member."
    
    - _อธิบายตามหนังสือ_: หนังสือยกตัวอย่าง **"การส่งคำร้องขอเพื่อขออนุมัติงานจากสมาชิกในทีมที่มีคุณสมบัติเหมาะสม"** เพื่อแสดงบทบาทของระบบแจ้งเตือนในการดึงมนุษย์เข้ามาตรวจสอบในระบบ
        
- **ตัวอย่างหน้าจอการใช้งานจริงบนซอฟต์แวร์ ITSM (Figure 14-2)**: หนังสือแสดงภาพตัวอย่างของระบบตั๋วงานที่ทำงานเชื่อมต่อกับระบบอัตโนมัติภายนอกไว้ดังนี้:
    ![[Pasted image 20260715224231.png]]

- _อธิบายตามหนังสือ_: ภาพนี้คือหน้าจอจริงของตั๋วงานการขอความเปลี่ยนแปลง (Change Request) บนแพลตฟอร์ม ITSM ยอดนิยมอย่าง **ServiceNow** ตัวอย่างในภาพแสดงให้เห็นกระบวนการทำงานว่า:
    
    1. มีผู้ใช้งานส่งคำร้องขอระบบเพื่อขอเพิ่ม **VLAN ใหม่** เข้ามาในระบบเครือข่าย (ระบุในตั๋วเป็น Device: jcy-spine-01.infra.ntc.com, VLAN Name: v316, VLAN ID: 316)
        
    2. หลังจากคำร้องนี้ผ่านการตรวจสอบและได้รับการยอมรับ (Accepted) ขั้นตอนการเปลี่ยนแปลงนี้จะถูกตั้งกำหนดเวลาดำเนินการ (Scheduled)
        
    3. เมื่อถึงเวลา ระบบจะทำการส่งสัญญาณทริกเกอร์หรือสั่งการไปยัง **Ansible playbook ภายนอก** ให้เริ่มทำงานโดยอัตโนมัติเพื่อเข้าไปคอนฟิกอุปกรณ์จริง (ในภาพจะปรากฏลิงก์การทำงานชื่อ Ansible job 3723 output เพื่อให้คลิกดูผลลัพธ์) เครื่องมือเหล่านี้หากมีการเชื่อมต่อระบบ (Integrations) ที่เหมาะสม จะช่วยอำนวยความสะดวกอย่างมากในการปฏิสัมพันธ์ระหว่างผู้ใช้และระบบอัตโนมัติสำหรับเครือข่าย
        
- **ตัวอย่างคำแนะนำเชิงประยุกต์ใช้เรื่องการบริหารจัดการความเปลี่ยนแปลง**:
    
    > "...organization’s change management process to build network automation solutions that fit well into it."
    
    - _อธิบายตามหนังสือ_: หนังสือระบุว่าเรื่องการบริหารจัดการความเปลี่ยนแปลง (Change management) ถือเป็นศาสตร์เฉพาะตัว พร้อมยกคำแนะนำให้วิศวกรทำการศึกษาและทำความเข้าใจ **"กระบวนการบริหารจัดการความเปลี่ยนแปลงภายในองค์กรของตนเอง"** อย่างถ่องแท้ เพื่อที่จะสามารถออกแบบและสร้างโซลูชัน Network Automation ให้เข้ากันและทำงานร่วมกับโครงสร้างกระบวนการเดิมขององค์กรได้อย่างลงตัวและมีประสิทธิภาพสูงสุดครับ

**"แดชบอร์ด (Dashboards)" ในฐานะเครื่องมือนำเสนอข้อมูลรูปแบบภาพแบบอ่านอย่างเดียว (Read-only visualization)** เพื่อจัดการย่อข้อมูลปริมาณมหาศาลที่มาจากแหล่งข้อมูลอันหลากหลายให้อยู่ในรูปแบบที่กระชับและมีประสิทธิภาพ โดยรูปแบบและการแสดงผลจะปรับเปลี่ยนไปตามความต้องการของแต่ละกรณีการใช้งาน (Use case)

นอกจากนี้เนื้อหายังระบุถึงปัจจัยสำคัญ 2 ประการที่ต้องนำมาพิจารณาเมื่อต้องเลือกใช้เครื่องมือแดชบอร์ด ได้แก่:

- **การเชื่อมต่อกับแหล่งข้อมูล (Data source integrations):** ต้องพิจารณาว่ามีอินทิเกรชันสำหรับเชื่อมต่อแหล่งข้อมูลเดิมอยู่มากน้อยเพียงใด และความง่ายในการพัฒนาอินทิเกรชันใหม่ๆ ผ่าน APIs ซึ่งจุดนี้สำคัญมากหากองค์กรมีข้อจำกัดด้านกำลังคนในการพัฒนาระบบเอง เนื่องจากในความเป็นจริงเป็นไปได้ยากที่จะมีอินทิเกรชันสำเร็จรูปมารองรับแหล่งข้อมูลที่มีอยู่ทั้งหมด
    
- **การปรับแต่งแดชบอร์ด (Dashboard customization):** รูปแบบและตัวเลือกในการแสดงผลภาพข้อมูลเพื่อให้เกิดประสิทธิภาพสูงสุดในการใช้งาน รวมถึงคุณสมบัติในการกำหนดหรือสร้างแผนภูมิเหล่านี้ให้อยู่ในรูปแบบโค้ด (Diagrams as code) เพื่อให้การบริหารจัดการมีประสิทธิภาพและประสิทธิผลมากขึ้น
    

## 2. ตัวอย่างในหนังสือและการอธิบายอย่างละเอียด

ในเนื้อหาหัวข้อย่อยนี้มีการระบุและยกตัวอย่างในด้านต่างๆ ไว้ดังนี้:

- **ตัวอย่างการอ้างอิงเนื้อหาเชิงลึก (หน้า 751 หัวข้อ "Telemetry and Observability"):**
    
    - _อธิบายตามหนังสือ:_ หนังสืออ้างถึงเนื้อหาในหน้า 751 เพื่อระบุว่าจะเป็นส่วนที่ลงรายละเอียดเพิ่มเติมเกี่ยวกับการใช้แดชบอร์ดเพื่อแสดงภาพสถานะการทำงาน (Operational state) ที่รวบรวมมาจากโครงสร้างพื้นฐานเครือข่าย โดยผู้อ่านจะได้เรียนรู้ความสำคัญของการใช้ประโยชน์จากข้อมูลที่ทำให้เป็นมาตรฐานแล้ว (Normalized data) และข้อมูลที่ได้รับการปรับปรุงเพิ่มข้อมูลเสริมแล้ว (Enriched data) เพื่อใช้ในการค้นหาข้อมูลขั้นสูง (Advanced queries) ให้ได้ข้อมูลที่เกี่ยวข้อง
        
- **ตัวอย่างเครื่องมือในฝั่ง Business Intelligence (ด้านข่าวกรองธุรกิจ):**
    
    - _อธิบายตามหนังสือ:_ หนังสือยกตัวอย่าง **Tableau** และ **Microsoft Power BI** ซึ่งจัดเป็นผลิตภัณฑ์เชิงพาณิชย์ (Commercial products) ที่มีความเชี่ยวชาญเฉพาะทางในโดเมนนี้
        
- **ตัวอย่างเครื่องมือในฝั่ง IT Engineering (ด้านวิศวกรรมไอที):**
    
    - _อธิบายตามหนังสือ:_ หนังสือยกตัวอย่าง **Grafana** และ **Kibana** ซึ่งเป็นสองโครงการโอเพนซอร์ส (Open source projects) ยอดนิยมที่ได้รับความสนใจและมีผู้ใช้งานจำนวนมากในปัจจุบัน
        
- **ตัวอย่างประเภทของแผนภูมิและไดอะแกรมที่ใช้แสดงผลภาพข้อมูล:**
    
    - _อธิบายตามหนังสือ:_ หนังสือยกตัวอย่างรูปแบบการแสดงผลทั่วไปที่สามารถนำมาใช้บนแดชบอร์ดเพื่อให้เข้าใจข้อมูลได้มีประสิทธิภาพมากขึ้น ได้แก่ แผนภูมิแท่ง/แผนภูมิเส้น (bar/line charts), ฮิสโตแกรม (histograms), แผนภูมิความร้อน (heatmaps) และ แผนภาพซันกีย์ (Sankey diagrams)


ChatOps
### 1. หัวข้อนี้พูดถึงอะไร?

หัวข้อนี้อธิบายถึง **ChatOps** ซึ่งเป็นการนำแอปพลิเคชันรับส่งข้อความแบบทันที (Instant messaging applications) มาประยุกต์ใช้กับระบบอัตโนมัติของเครือข่าย แทนที่จะใช้สื่อสารระหว่างบุคคลเพียงอย่างเดียว องค์กรสามารถใช้บอท (Bot) เพื่อให้ผู้ใช้เข้าถึงฟังก์ชันของระบบอัตโนมัติสำหรับเครือข่ายได้ง่ายขึ้นและลดกำแพงในการใช้งานลง การทำงานผ่าน ChatOps ครอบคลุมหลายรูปแบบ เช่น การสั่งเริ่มเวิร์กโฟลว์ การอัปเดตข้อมูลความจริงหลัก (Source of truth) หรือการดึงสถานะการทำงานจริงของเครือข่ายเพื่อวิเคราะห์ปัญหา พร้อมกับแชร์ข้อมูลให้ทีมรับทราบในเวลาเดียวกัน

วิธีการนี้ช่วยซ่อนความซับซ้อนของระบบเบื้องหลังทั้งหมด ทำให้การใช้งานง่ายและมีประสิทธิภาพมากขึ้น นอกจากนี้ยังพูดถึงโอกาสในการนำเทคโนโลยี AI และประมวลผลภาษาธรรมชาติ (NLP) รวมถึงโมเดลภาษาขนาดใหญ่ (LLM) เข้ามาช่วยยกระดับการโต้ตอบในสถาปัตยกรรมระบบอัตโนมัติให้เป็นธรรมชาติมากขึ้น และในตอนท้ายได้เกริ่นนำเพื่อเตรียมเปลี่ยนผ่านไปยังการอธิบายเรื่องอินเทอร์เฟซแบบข้อความ (Text-based interactions) ในหัวข้อถัดไป

    - บอทจะทำการค้นหาตำแหน่งของสวิตช์และอินเทอร์เฟซที่มี IP หรือ MAC address ดังกล่าวเชื่อมต่ออยู่
        
    - รูปแบบนี้คือการที่มนุษย์เริ่มต้นบทสนทนาด้วยข้อความเพียงข้อความเดียว จากนั้นระบบอัตโนมัติจะรับช่วงต่อจัดการกระบวนการที่เหลือให้ทั้งหมด
        
- **ตัวอย่างประโยชน์จากผลกระทบสะสม (Cumulative effect):**
    
    - ประสบการณ์และความรู้ของทีมจะถูกเพิ่มเติมเข้าไปในลอจิกการทำงานของคำสั่งได้เรื่อยๆ เมื่อเวลาผ่านไป
        
    - หนังสือยกตัวอย่าง **"สคริปต์สำหรับแก้ปัญหา MPLS (MPLS troubleshooting script)"** ที่วิศวกรคนอื่นๆ สามารถเข้ามาเพิ่มฟีเจอร์ใหม่ๆ สะสมเข้าไปได้
        
    - ผลประโยชน์ที่ตามมาคือ หากมีวิศวกรลาออกจากบริษัท องค์ความรู้เหล่านี้จะไม่หายไปแต่จะยังคงอยู่ในระบบต่อไป
        
- **ตัวอย่างการประยุกต์ใช้ปัญญาประดิษฐ์ (AI) และ ChatGPT:**
    
    - สามารถนำ ChatGPT ซึ่งเป็นโมเดล LLM มาช่วยให้มนุษย์สามารถสนทนากับโมเดล เพื่อสร้างคำตอบตามบริบทได้แบบคำต่อคำ
        
    - ตัวอย่างฟีเจอร์ที่มีประสิทธิภาพจากการใช้ AI ได้แก่ การวิเคราะห์ Log เพื่อเสนอสาเหตุของปัญหา (Root cause), การแปลการตั้งค่า (Configuration) ของอุปกรณ์เครือข่ายข้ามไปแพลตฟอร์มอื่น, การวิเคราะห์ความสอดคล้องของการตั้งค่า (Compliance analysis) หรือการสร้าง Code snippets ในภาษาโปรแกรมใดๆ เพื่อแก้ปัญหาเฉพาะหน้า
        
    - ตัวอย่างการเชื่อมต่อกับปลั๊กอิน (Plug-ins) ผ่าน APIs เช่น ระบบสามารถดึงข้อมูลปฏิบัติการจากเครือข่ายได้แบบเรียลไทม์ หรือสามารถไปดึงความต้องการของเครือข่าย (Network intent) มาจาก Source of truth ได้

เนื้อหาในหัวข้อย่อย **"Text-based interactions" (การปฏิสัมพันธ์ผ่านข้อความ)** สามารถสรุปและอธิบายรายละเอียดโดยอิงตามข้อเท็จจริงในหนังสือได้ดังนี้ครับ

### 1. หัวข้อนี้พูดถึงอะไร?

หัวข้อนี้พูดถึงการใช้งาน **อินเทอร์เฟซแบบข้อความ (Text-based UIs)** โดยมุ่งเน้นไปที่เพื่อนเก่าของวิศวกรเครือข่ายอย่าง **Command-Line Interface (CLI)**

หนังสืออธิบายว่า วิศวกรเครือข่ายที่มีประสบการณ์มากกว่า 5 ปีมักจะคุ้นเคยกับการใช้ CLI ในการจัดการอุปกรณ์เครือข่ายอยู่แล้ว แม้ว่าแนวโน้มในปัจจุบันของอุตสาหกรรมจะพยายามลดการพึ่งพา CLI ลง (ตามที่หนังสือได้เน้นย้ำตลอดทั้งเล่ม) แต่ CLI ก็ยังคงเป็นช่องทางที่มีประโยชน์อย่างมากในการใช้สั่งงานโซลูชัน Network Automation สาเหตุสำคัญคือผู้ใช้งานระบบเหล่านี้ส่วนใหญ่ (ซึ่งก็คือวิศวกรเครือข่ายคนอื่นๆ) ยังคงรู้สึกสบายใจและถนัดที่จะใช้งานอินเทอร์เฟซรูปแบบนี้นั่นเอง

### 2. ตัวอย่างในหนังสือและการอธิบาย

หนังสือได้ระบุและยกตัวอย่างเครื่องมือรวมถึงไลบรารีที่เกี่ยวข้องกับการทำ CLI ไว้ดังนี้ครับ:

- **ตัวอย่างเครื่องมือ Automation ที่มี CLI ในตัว:**
    
    - _อธิบายตามหนังสือ:_ หนังสือทำการอ้างอิงย้อนกลับไปยังเครื่องมือในบทที่ 12 คือ **Ansible** และ **Terraform** เพื่อแสดงให้เห็นว่าเครื่องมือจัดการระบบอัตโนมัติระดับองค์กรเหล่านี้ ต่างก็มีช่องทาง CLI เสนอไว้ให้ผู้ใช้งานเลือกใช้ด้วยเช่นกัน
        
- **ตัวอย่างไลบรารีสำหรับการสร้าง CLI ขึ้นมาใช้งานเอง:**
    
    - _อธิบายตามหนังสือ:_ หากวิศวกรต้องการพัฒนา CLI ขึ้นมาใช้งานเอง หนังสือได้ยกตัวอย่างไลบรารียอดนิยมที่สามารถดึงมาประยุกต์ใช้ได้ ได้แก่:
        
        - สำหรับภาษา **Python**: ไลบรารีอย่าง **Click** หรือ **Rich**
            
        - สำหรับภาษา **Go**: ไลบรารีอย่าง **Cobra**
            
- **การเกริ่นนำสู่เนื้อหาถัดไป:**
    
    - _อธิบายตามหนังสือ:_ ในประโยคสุดท้าย หนังสือได้ทิ้งท้ายเพื่อเปลี่ยนผ่านไปยังหัวข้อต่อไป โดยระบุว่าจะพาไปดูวิธีการที่ Network Automation สามารถนำมาใช้สร้างเอกสาร (Documents) และรายงาน (Reports) ให้กับผู้ใช้งานในหลากหลายประเภทครับ

เนื้อหาในหัวข้อย่อย **"Documentation and reporting" (การทำเอกสารและการรายงาน)** สามารถสรุปและอธิบายรายละเอียดโดยอิงตามข้อเท็จจริงในหนังสือได้ดังนี้ครับ

## 1. หัวข้อนี้พูดถึงอะไร?

หัวข้อนี้พูดถึง **การใช้ระบบอัตโนมัติเข้ามาช่วยสร้าง "เอกสารและรายงาน" ในรูปแบบโค้ด (Documentation as code)** เพื่อแก้ปัญหาความล่าช้าและข้อมูลที่ล้าสมัย

หนังสือระบุว่าผู้ใช้งานแต่ละกลุ่มมีความต้องการด้านเอกสารที่แตกต่างกันอย่างชัดเจน หากไม่มีระบบอัตโนมัติ การสร้างเอกสารแต่ละประเภทจะต้องใช้ต้นทุนที่สูงมาก (Costly) และเมื่อสร้างเสร็จ เอกสารเหล่านั้นก็จะล้าสมัยในทันที (Instantly outdated) เนื่องจากระบบเครือข่ายมีการเปลี่ยนแปลงอยู่ตลอดเวลา การนำระบบอัตโนมัติเข้ามาช่วยจะทำให้สามารถสร้างเอกสารที่อัปเดตข้อมูลได้เกือบจะเรียลไทม์ มีรูปแบบที่สม่ำเสมอ ทำซ้ำได้ และประหยัดแรงไปได้มาก

## 2. ตัวอย่างภาษาและเครื่องมือที่หนังสือยกมาอธิบาย

หนังสือได้ยกตัวอย่างความต้องการของผู้ใช้และเครื่องมือที่ใช้ในการทำเอกสารอัตโนมัติไว้ดังนี้ครับ:

- **ตัวอย่างความต้องการของผู้ใช้ที่ต่างกัน:** วิศวกรเครือข่าย (Network engineers) มักจะคุ้นเคยกับการทำความเข้าใจการออกแบบเครือข่ายผ่าน **"แผนภาพ (Diagrams)"** ในขณะที่กลุ่มผู้บริหาร (Leadership members) จะสนใจ **"รายงานความสอดคล้อง (Compliance reports)"** เพื่อใช้ตรวจสอบและยืนยันว่ามีการปฏิบัติตามมาตรฐานจริง
    
- **ตัวอย่างภาษาที่ใช้สร้างข้อความเอกสาร:** มีการอ้างถึงการใช้ **Markdown** (จากบทที่ 12) ที่สามารถเรนเดอร์เป็น HTML ได้ รวมถึงภาษาทางเลือกยอดนิยมอื่นๆ ในการทำเอกสารแบบโค้ด เช่น **AsciiDoc** และ **reStructuredText** ซึ่งสามารถนำไปเรนเดอร์เป็นรูปแบบที่ต้องการได้ (เช่น HTML, PDF, DOCX)
    
    - _ข้อเท็จจริงที่หนังสือนำมาแทรก:_ หนังสือเล่มที่คุณกำลังอ่านอยู่นี้ ก็ถูกเขียนขึ้นด้วยรูปแบบ AsciiDoc เช่นเดียวกัน
        
- **ตัวอย่างเครื่องมือสำหรับสร้างแผนภาพและกราฟโดยเฉพาะ:** หนังสือยกตัวอย่าง **Structurizr** สำหรับการทำโมเดลสถาปัตยกรรม C4 และ **Mermaid** สำหรับการสร้างแผนภาพที่ซับซ้อน
    

## 3. ตัวอย่างการสร้างแผนภาพเครือข่ายด้วยโค้ด (Network diagram as code)

หนังสือได้แสดงตัวอย่างการทำงานร่วมกันของข้อมูลและเทมเพลต เพื่อสร้างแผนภาพเครือข่ายแบบอัตโนมัติด้วย **Mermaid** โดยมีรายละเอียดดังนี้:

**สถานการณ์จำลอง:** ต้องการสร้างแผนภาพสำหรับเครือข่ายที่มีสวิตช์ Spine 2 ตัว, สวิตช์ Leaf 2 ตัว และมีเซิร์ฟเวอร์เชื่อมต่ออยู่กับ Leaf

**ขั้นตอนที่ 1: ข้อมูลตั้งต้น (Data)** ข้อมูลเหล่านี้อาจมาจากระบบคลังข้อมูลเครือข่าย (Inventory) หรือข้อมูลสถานะจริงอย่าง LLDP ซึ่งในฐานข้อมูลความจริงหลัก (Source of truth) อาจมีหน้าตาข้อมูล (YAML) แบบนี้:

YAML

```
---
connections:
  - side_a: sw1-spine
    side_b: sw1-leaf
    ip_prefix: 192.0.2.0/29
  - side_a: sw1-spine
    side_b: sw2-leaf
    ip_prefix: 192.0.2.8/29
  - side_a: sw2-spine
    side_b: sw2-leaf
    ip_prefix: 192.0.2.4/29
  - side_a: sw2-spine
    side_b: sw1-leaf
    ip_prefix: 192.0.2.12/29
  - side_a: sw1-leaf
    side_b: serverA
    ip_prefix: 10.0.0.0/29
  - side_a: sw2-leaf
    side_b: serverA
    ip_prefix: 10.0.0.4/29
```

**ขั้นตอนที่ 2: การใช้เทมเพลต Jinja** นำความรู้จากบทที่ 9 มาสร้างเทมเพลตเพื่อวนลูปอ่านข้อมูลการเชื่อมต่อ (connections) ด้านบน:

Plaintext

```
graph TD
{% for connection in connections %}
  {{ connection.side_a }}({{ connection.side_a }}) ---|{{ connection.ip_prefix }}| {{ connection.side_b }}({{ connection.side_b }})
{% endfor %}
```

**ขั้นตอนที่ 3: ผลลัพธ์ที่ได้จากการเรนเดอร์** เมื่อนำข้อมูลมารวมกับเทมเพลต จะได้ผลลัพธ์ออกมาเป็น "Mermaid snippet" ซึ่งเป็นโค้ดที่สามารถนำไปแทรกลงในเอกสาร Markdown ได้ทันที:

Plaintext

```
graph TD
  sw1-spine(sw1-spine) ---|192.0.2.0/29| sw1-leaf(sw1-leaf)
  sw1-spine(sw1-spine) ---|192.0.2.8/29| sw2-leaf(sw2-leaf)
  sw2-spine(sw2-spine) ---|192.0.2.4/29| sw2-leaf(sw2-leaf)
  sw2-spine(sw2-spine) ---|192.0.2.12/29| sw1-leaf(sw1-leaf)
  sw1-leaf(sw1-leaf) ---|10.0.0.0/29| serverA(serverA)
  sw2-leaf(sw2-leaf) ---|10.0.0.4/29| serverA(serverA)
```
