เนื้อหาในหัวข้อ **"Automation Engine" (เครื่องยนต์หรือระบบที่ขับเคลื่อนการทำงานอัตโนมัติ)** สามารถสรุปและอธิบายรายละเอียดโดยอิงตามข้อเท็จจริงในหนังสือได้ดังนี้

## 1. หัวข้อนี้พูดถึงอะไร?

หัวข้อนี้อธิบายถึงบทบาทหน้าที่ของ **Automation Engine** ซึ่งเป็นส่วนที่ครอบคลุมการปฏิบัติงานเพื่อจัดการ "สถานะของเครือข่าย (Network state)" และดำเนินงานต่างๆ บนเครือข่าย

หนังสือชี้ให้เห็นข้อแตกต่างที่สำคัญมากเมื่อเทียบกับส่วนประกอบอื่นในสถาปัตยกรรม (อ้างอิงจาก Figure 14-1) คือ ในขณะที่ระบบ Telemetry และ Observability มุ่งเน้นไปที่การเก็บรวบรวมข้อมูลเพียงอย่างเดียว **Automation Engine จะส่งผลกระทบและสร้างความเปลี่ยนแปลงต่อสถานะของเครือข่ายโดยตรง** ดังนั้นผู้ใช้งานจึงต้องดำเนินการด้วยความระมัดระวัง

โดยภาพรวมแล้ว หน้าที่หลักขององค์ประกอบนี้สามารถแบ่งออกเป็น 2 กลุ่มใหญ่ คือ **การบริหารจัดการการตั้งค่า (Configuration management)** และ **การปฏิบัติการ (Operations)** งานส่วนใหญ่มักจะจัดอยู่ในสองหมวดหมู่นี้

## 2. ตัวอย่างทั้งหมดในหนังสือและการอธิบายอย่างละเอียด

หนังสือได้ยกตัวอย่างเครื่องมือ, คำแนะนำในการใช้งาน และปัจจัยในการเลือกโซลูชันไว้อย่างชัดเจน ดังนี้:

### ตัวอย่างที่ 1: งานของระบบและเครื่องมือที่ใช้ทำงาน

- **ตัวอย่างงานบนเครือข่าย (Network tasks):** หนังสือยกตัวอย่าง **"การอัปเกรด (Upgrades)"** เป็นหนึ่งในงานที่ Automation Engine ต้องทำ
    
- **ตัวอย่างเครื่องมือจัดการโครงสร้างพื้นฐาน (จากบทที่ 12):** หนังสือยกตัวอย่าง **Ansible, Terraform, และ Nornir**
    
- **ตัวอย่างอินเทอร์เฟซและไลบรารีที่ใช้เชื่อมต่อกับอุปกรณ์ (จากบทที่ 10):** หนังสือยกตัวอย่าง **NETCONF, RESTCONF, และ gNMI**
    

### ตัวอย่างที่ 2: คำแนะนำเพื่อความปลอดภัยก่อนสร้างความเปลี่ยนแปลง

เนื่องจากระบบนี้ส่งผลกระทบต่อเครือข่ายโดยตรง หนังสือจึงยกตัวอย่าง 2 คำแนะนำหลักในการทำงาน ได้แก่:

1. **การทำงานแบบ Dry-run (Dry-run tasks):** หนังสือแนะนำให้เริ่มต้นด้วยการจำลองรันการทำงานโดยที่ยังไม่เปลี่ยนค่าจริง เพื่อสร้างความมั่นใจในระบบอัตโนมัติ โหมดนี้จะแสดง "รายงานโดยละเอียด (Detailed report)" ว่าหากรันจริงจะมีอะไรเปลี่ยนแปลงในโครงสร้างพื้นฐานเครือข่ายบ้างก่อนที่มันจะเกิดขึ้นจริง
    
2. **การใช้ Continuous integration และ Emulation:** หนังสือแนะนำให้ใช้การบูรณาการอย่างต่อเนื่อง (อ้างอิงบทที่ 13) และระบบจำลองเครือข่ายเสมือน (อ้างอิงบทที่ 5) เพื่อใช้ **"ตรวจสอบยืนยันผลกระทบของความเปลี่ยนแปลง (Validate the effect of changes)"** ก่อนที่จะนำไปใช้งานจริงบนระบบโปรดักชัน
    

### ตัวอย่างที่ 3: ปัจจัยในการเลือกโซลูชัน/เครื่องมือที่ดีที่สุด

หนังสือแนะนำให้พิจารณาหลักการ **"ซื้อหรือสร้างเอง (Buy versus build dilemma)"** โดยยกตัวอย่างปัจจัย 4 ข้อที่ต้องนำมาพิจารณา ได้แก่:

1. **อินเทอร์เฟซเครือข่ายที่รองรับ (Supported network interfaces):** โครงสร้างพื้นฐานที่ใช้งานอยู่จะเป็นตัวกำหนดว่ามีตัวเลือกใดให้ใช้บ้าง (อิงตามตัวเลือกในบทที่ 10)
    
2. **เครื่องมือที่มีอยู่แล้ว (Existing tooling):** หากคุณไม่ได้เริ่มจากศูนย์ (มีระบบอัตโนมัติบางอย่างใช้อยู่แล้ว) หนังสือแนะนำให้ประเมินการ **"นำเครื่องมือเดิมกลับมาใช้ใหม่ (Reusing existing tools)"** ก่อนที่จะตัดสินใจนำเครื่องมือใหม่ๆ เข้ามา
    
3. **ทักษะของทีมงาน (Team skills):** โซลูชันอัตโนมัติจำเป็นต้องมีการติดตั้ง บำรุงรักษา และสั่งการทำงาน จึงควรเลือกสิ่งที่เหมาะกับทีม โดยหนังสือยกตัวอย่างการเปรียบเทียบว่าทีมถนัดแบบไหนระหว่าง **"การใช้ภาษาโปรแกรม (Programming language) หรือ การใช้รูปแบบข้อมูล (Data formats)"**
    
4. **การบูรณาการระบบ (Integrations):** ต้องกำหนดให้ชัดเจนว่าผู้ใช้งานระบบอัตโนมัติ หรือกระบวนการอัตโนมัติอื่นๆ จะเข้ามาปฏิสัมพันธ์กับเครื่องมือผ่านช่องทางใด โดยหนังสือยกตัวอย่างว่าอาจจะเป็น **"การสั่งงานโดยผู้ใช้ (User interaction) หรือ ผ่าน APIs"**
    

- **คำแนะนำทิ้งท้าย:** หนังสือเตือนว่า **"อย่าคิดมากเกินไป (Don't overthink)"** กับการเลือกเครื่องมือ เพราะหากคุณกำหนดเป้าหมายและขอบเขตไว้ชัดเจนแล้ว การเปลี่ยนจากเครื่องมือหนึ่งไปสู่อีกเครื่องมือหนึ่งในยามจำเป็น จะกลายเป็นเรื่องที่ทำได้ง่าย
## 1. หัวข้อนี้พูดถึงอะไร?

หัวข้อนี้อธิบายถึงเป้าหมายหลักของโซลูชันระบบเครือข่ายอัตโนมัติส่วนใหญ่ ซึ่งก็คือ **"การจัดการสถานะของเครือข่ายแบบอัตโนมัติ (Automatically manage the network state)"**

หนังสือได้ทำการเจาะลึกลงไปโดยแบ่งกระบวนการจัดการนี้ออกเป็น **4 ขั้นตอน (4 Stages)** ซึ่งองค์กรสามารถค่อยๆ นำมาปรับใช้ทีละขั้นตอนเพื่อเติมเต็มโซลูชันการจัดการให้สมบูรณ์ได้ (ตามที่แสดงการไหลของข้อมูลในแผนภาพ Figure 14-6)

## 2. รายละเอียด 4 ขั้นตอนของการจัดการการตั้งค่า

หนังสือได้อธิบายรายละเอียดของทั้ง 4 ขั้นตอนไว้ดังนี้:

- **1. Configuration backup (การสำรองข้อมูลการตั้งค่า):**
    
    - ทำหน้าที่ดึงข้อมูลและจัดเก็บสถานะการตั้งค่าจริงของเครือข่าย (Actual state) เพื่อนำมาใช้เป็นข้อมูลอ้างอิง
        
    - _ตัวอย่างในหนังสือ:_ ข้อมูลสำรองนี้สามารถนำไปใช้เพื่อย้อนสถานะเครือข่ายกลับไปยังสถานะก่อนหน้าได้ (ตัวอย่างเช่น การทำ **Rollback operation**)
        
- **2. Configuration rendering (การเรนเดอร์ไฟล์การตั้งค่า):**
    
    - ทำหน้าที่สร้างไฟล์การตั้งค่าที่ถูกต้อง (Configuration artifacts) สำหรับแต่ละอินเทอร์เฟซ โดยเกิดจากการนำ "ข้อมูล" และ "เทมเพลต" จาก Source of Truth (SoT) มารวมเข้าด้วยกัน
        
- **3. Configuration compliance (การตรวจสอบความสอดคล้องของการตั้งค่า):**
    
    - ทำหน้าที่เปรียบเทียบระหว่าง "การตั้งค่าจริง" (ดึงมาจาก Configuration backup) กับ "การตั้งค่าที่พึงประสงค์" (ดึงมาจาก Configuration rendering) เพื่อคำนวณหาความคลาดเคลื่อน (Drift) ที่เกิดขึ้นระหว่างสองส่วนนี้
        
- **4. Configuration deployment (การนำการตั้งค่าไปใช้งานจริง):**
    
    - ทำหน้าที่อัปเดตสถานะของโครงสร้างพื้นฐานเครือข่าย โดยใช้ไฟล์การตั้งค่าที่ถูกสร้างขึ้นจากขั้นตอน Configuration rendering
        
    - _อธิบายตามหนังสือ:_ ขั้นตอนนี้อาจรวมถึงกระบวนการประมวลผลเพื่อผลักดันสถานะการตั้งค่าจาก "จุดที่มันเป็นอยู่" ไปสู่ "จุดที่มันควรจะเป็น"
        

## 3. ตัวอย่างเครื่องมือและโซลูชันจากหนังสือ

- **ตัวอย่างโซลูชันแบบครบวงจร:** หนังสือระบุว่ามีโซลูชันแบบโอเพนซอร์ส (Open source solutions) เพียงไม่กี่ตัวเท่านั้นที่มีฟีเจอร์ครอบคลุมการจัดการทั้ง 4 ขั้นตอนนี้รวมไว้ด้วยกัน
    
- **ตัวอย่างเครื่องมือ Nautobot Golden Config:** หนังสือยกตัวอย่างปลั๊กอิน Nautobot Golden Config ว่าเป็นเฟรมเวิร์กที่สามารถรองรับการทำงานในกระบวนการนี้ได้เกือบทั้งหมด **ยกเว้นเพียงขั้นตอนเดียวคือ Configuration deployment** (โดยอ้างอิงจากความสามารถของเครื่องมือ ณ เวลาที่หนังสือเล่มนี้ถูกเขียนขึ้น)

เนื้อหาในหัวข้อย่อย **"Configuration backup" (การสำรองข้อมูลการตั้งค่า)** สามารถสรุปและอธิบายรายละเอียดโดยอิงตามข้อเท็จจริงในหนังสือได้ดังนี้

### 1. หัวข้อนี้พูดถึงอะไร?

หัวข้อนี้อธิบายถึง **การสำรองข้อมูลและการเก็บถาวรการตั้งค่าอุปกรณ์เครือข่าย (Configuration backup and archiving)** ซึ่งเป็นกระบวนการที่มีมานานแล้วก่อนที่ระบบอัตโนมัติจะกลายมาเป็นที่นิยม

วัตถุประสงค์หลักของกระบวนการนี้คือ การดึงข้อมูลและจัดเก็บไฟล์การตั้งค่าจากอุปกรณ์เครือข่าย เพื่อนำมาใช้เปรียบเทียบสถานะของระบบระหว่างช่วงเวลาต่างๆ ที่ระบุไว้ และใช้เพื่อย้อนกลับ (Roll back) การตั้งค่าไปยังจุดที่ระบบมีความเสถียร ในกรณีที่พบว่าเครือข่ายมีพฤติกรรมการทำงานที่ไม่พึงประสงค์

ปัจจุบัน วิธีที่ได้รับความนิยมที่สุดในการจัดเก็บไฟล์สำรองคือการใช้ **ระบบควบคุมเวอร์ชัน (Version control systems)** เนื่องจากมีฟีเจอร์ที่รองรับการจัดการเวอร์ชันของไฟล์และการเปรียบเทียบข้อมูลได้อย่างมีประสิทธิภาพ

### 2. ตัวอย่างในหนังสือและการอธิบายอย่างละเอียด

หนังสือได้ยกตัวอย่างเครื่องมือ, การทำงานของระบบเวอร์ชัน, และข้อควรระวังไว้ดังนี้:

- **ตัวอย่างเครื่องมือ RANCID:** หนังสือยกตัวอย่างเครื่องมือที่ชื่อว่า **RANCID** ซึ่งเป็นเครื่องมือยอดนิยมที่ใช้สำหรับดูแลรักษาไฟล์การตั้งค่าของเราเตอร์ โดยจัดเก็บไว้ในระบบควบคุมเวอร์ชันอย่าง Git หรือ Subversion
    
- **ตัวอย่างการเปรียบเทียบไฟล์สำรองด้วย Git (Example 14-5):** หนังสือแสดงตัวอย่างการเปรียบเทียบเอาต์พุตของการตั้งค่า 2 ไฟล์ เพื่อหาจุดแตกต่างโดยใช้ความสามารถของระบบเวอร์ชันผ่านคำสั่ง `git diff`
    
    Plaintext
    
    ```
    $ git diff
    diff --git a/nyc/nyc-leaf-02.infra.ntc.com.cfg b/nyc/nyc-leaf-02.infra.ntc.com.cfg
    index 0f3fa95..4e14e60 100644
    --- a/nyc/nyc-leaf-02.infra.ntc.com.cfg
    +++ b/nyc/nyc-leaf-02.infra.ntc.com.cfg
    @@ -189,9 +189,9 @@ ip route 0.0.0.0/0 10.0.0.2
     router bgp 65255
     router-id 10.0.20.7
     neighbor 10.11.11.17 remote-as 65253
    - neighbor 10.11.11.17 maximum-routes 12000
    + neighbor 10.11.11.17 maximum-routes 14000
     neighbor 10.11.11.25 remote-as 65253
    ```
    
    - _คำอธิบายผลลัพธ์:_ จากโค้ดตัวอย่าง ระบบตรวจพบความเปลี่ยนแปลงของพารามิเตอร์ `maximum-routes` ในโปรโตคอล BGP โดยค่าเดิมคือ `12000` (บรรทัดที่มีเครื่องหมายลบ) ถูกเปลี่ยนเป็น `14000` (บรรทัดที่มีเครื่องหมายบวก)
        
- **ตัวอย่างข้อมูลความลับที่ต้องระวัง (Secrets):** หนังสือระบุข้อควรระวังว่า หากจัดเก็บไฟล์สำรองในรูปแบบข้อความธรรมดา (Clear text) จะต้องลบข้อมูลความลับออกก่อนที่จะบันทึกลงระบบเสมอ โดยยกตัวอย่างข้อมูลที่ต้องลบ เช่น **คีย์ BGP MD5 (BGP MD5 keys)** หรือ **รหัสผ่านผู้ใช้ที่ผ่านการแฮชแล้ว (User hashed passwords)**
    

### 3. ข้อควรจำที่สำคัญจากหนังสือ

หนังสือได้เน้นย้ำในส่วนท้ายว่า แม้การเปรียบเทียบไฟล์การตั้งค่า (ซึ่งไม่จำกัดเฉพาะรูปแบบ CLI เท่านั้น) จะมีประโยชน์ในการทำความเข้าใจความเปลี่ยนแปลงที่เกิดขึ้น แต่ต้องตระหนักไว้เสมอว่า **"การตั้งค่าที่พึงประสงค์ (Intended configuration)"** จะต้องมาจากการเรนเดอร์ข้อมูลจากระบบ Source of Truth (SoT) เท่านั้น และต้องใช้ข้อมูลจาก SoT เป็นข้อมูลอ้างอิงหลักเสมอ


### 1. หัวข้อนี้พูดถึงอะไร?

หัวข้อนี้อธิบายถึงขั้นตอน **"การเรนเดอร์ไฟล์การตั้งค่า (Configuration rendering)"** ซึ่งทำหน้าที่แปลง "สถานะที่พึงประสงค์ (Intended state)" ที่กำหนดไว้ใน Source of Truth (SoT) ให้ออกมาเป็นการตั้งค่าจริง (Actual configurations) ที่เหมาะสมกับอุปกรณ์เครือข่ายแต่ละแพลตฟอร์ม

หนังสือระบุว่า เจตนาของการตั้งค่าจะไม่มีประโยชน์เลยหากไม่สามารถแปลงออกมาใช้งานจริงได้ กระบวนการนี้จึงทำงานโดยการนำ **"ข้อมูล (Data)"** มาประกอบเข้ากับ **"เทมเพลต (Templates)"** (ซึ่งทั้งสองส่วนนี้มาจาก SoT) เพื่อสร้างเป็นไฟล์การตั้งค่า (Configuration artifacts) ที่โครงสร้างพื้นฐานเครือข่ายต้องการ

### 2. รายละเอียดและกระบวนการทำงาน (อิงตามต้นฉบับอย่างเคร่งครัด)

- **จุดเริ่มต้นและการขยายข้อมูล:** กระบวนการเรนเดอร์จะใช้คลังข้อมูลอุปกรณ์ (Inventory) เป็นจุดเริ่มต้น จากนั้นจะขยายข้อมูลโดยดึงส่วนที่เกี่ยวข้องอื่นๆ เข้ามาประกอบ (เช่น หมายเลขไอพี, อินเทอร์เฟซ, วงจร และข้อมูลอื่นๆ ที่เทมเพลตต้องการ)
    
- **ลำดับความสำคัญในการรวมข้อมูล (Data Hierarchy):** กระบวนการจัดการข้อมูลมักจะมีการจัดลำดับชั้นเมื่อต้องนำข้อมูลมารวมกัน (Merging) โดยหนังสือระบุกฎหลัก (Rule of thumb) ว่า **"ข้อมูลที่เฉพาะเจาะจงกว่าจะเป็นฝ่ายชนะ (The more specific wins)"** แต่ในบางกรณีผู้ใช้อาจกำหนดน้ำหนัก (Weights) เพื่อควบคุมตรรกะการทำงานให้แม่นยำขึ้น
    
- **คำแนะนำก่อนทำระบบอัตโนมัติ (Standardized vs. Snowflake):** หนังสือเตือนว่าความพยายามและความซับซ้อนในการทำระบบอัตโนมัติระหว่าง "เครือข่ายที่เป็นมาตรฐาน" กับ "เครือข่ายที่ไม่มีรูปแบบชัดเจน (Snowflake)" นั้นแตกต่างกันมาก หนังสือแนะนำอย่างยิ่งว่าก่อนเริ่มทำระบบจัดการการตั้งค่า ควรพิจารณาทบทวนการออกแบบเครือข่ายให้เป็นมาตรฐาน และแก้ไขจุดยกเว้นต่างๆ ให้เรียบร้อย เพื่อให้ระบบอัตโนมัติมีประสิทธิภาพและแข็งแกร่งขึ้น
    
- **การนำไปใช้งานในสภาพแวดล้อมต่างๆ:**
    
    - **เครือข่ายที่มีอยู่เดิม (Brownfield):** ควรเริ่มต้นจากการเรนเดอร์การตั้งค่าเพียงบางส่วน (Subset) ก่อน เพื่อค่อยๆ สร้างความมั่นใจในระบบตามลำดับ
        
    - **เครือข่ายใหม่ (New deployments):** เป็นโอกาสในการสร้างการตั้งค่าแบบเต็มรูปแบบตั้งแต่เริ่มต้น (From scratch) เพื่อควบคุมเครือข่ายจาก SoT ตั้งแต่แรก
        

### 3. ตัวอย่างในหนังสือและการอธิบาย

หนังสือได้ยกตัวอย่างเพื่ออธิบายแนวคิดการทำงานและข้อควรระวังไว้ดังนี้:

- **ตัวอย่างที่ 1: การใช้ Ansible เป็นเครื่องมือเรนเดอร์**
    
    - _อธิบายตามหนังสือ:_ หนังสืออ้างอิงถึงเนื้อหาในบทที่ 12 เพื่อให้ผู้อ่านย้อนไปดูตัวอย่างของกระบวนการเรนเดอร์ไฟล์การตั้งค่าโดยใช้เครื่องมือ Ansible
        
- **ตัวอย่างที่ 2: การเลือกใช้เซิร์ฟเวอร์ NTP (อธิบายกฎ The more specific wins)**
    
    - _อธิบายตามหนังสือ:_ สมมติว่ามีการกำหนด "เซิร์ฟเวอร์ NTP ส่วนกลาง (Global NTP servers)" เอาไว้ แต่ในบางสถานที่ (Locations) อาจมีเซิร์ฟเวอร์ NTP ที่แตกต่างออกไป เมื่อระบบต้องดึงข้อมูลเซิร์ฟเวอร์ NTP ไปใส่ในข้อมูลอุปกรณ์ ระบบจะต้องเลือกดึงข้อมูลที่ "เฉพาะเจาะจงกว่า (More specific ones)" ไปใช้งาน ซึ่งก็คือเซิร์ฟเวอร์ของสถานที่นั้นๆ แทนที่จะเป็นเซิร์ฟเวอร์ส่วนกลาง
        
- **ตัวอย่างที่ 3: เครือข่ายแบบ Snowflake และโค้ดสปาเกตตี**
    
    - _อธิบายตามหนังสือ:_ หนังสือเปรียบเทียบเครือข่ายที่ไม่มีรูปแบบชัดเจนว่าเป็นเหมือน "เกล็ดหิมะ (Snowflake)" หากอุปกรณ์ทุกตัวมีการตั้งค่าเฉพาะตัวและการออกแบบที่ปรับแต่งเอง (Custom design) การสร้างคำสั่งอัตโนมัติจะทำให้เกิด **"โค้ดสปาเกตตี (Spaghetti code)"** ซึ่งเป็นโค้ดที่ยุ่งเหยิง บำรุงรักษายาก และขยายขีดความสามารถได้ยาก
## 1. หัวข้อนี้พูดถึงอะไร?

หัวข้อนี้พูดถึง 3 ส่วนสุดท้ายของการบริหารจัดการเครือข่ายอัตโนมัติ (Automation Engine) ได้แก่:

1. **Configuration compliance (การตรวจสอบความสอดคล้องของการตั้งค่า):** การเปรียบเทียบการตั้งค่าจริงกับสิ่งที่ควรจะเป็น เพื่อหาความคลาดเคลื่อน
    
2. **Configuration deployment (การนำการตั้งค่าไปใช้งานจริง):** การอัปเดตสถานะเครือข่ายให้ตรงกับที่ตั้งใจไว้ พร้อมเครื่องมือและวิธีป้องกันความเสี่ยง
    
3. **Operations (การปฏิบัติการ):** งานอื่นๆ บนเครือข่ายที่ไม่เกี่ยวข้องกับการเปลี่ยนการตั้งค่า เช่น การรีบูต หรือการอัปเกรดระบบปฏิบัติการ (NOS)
    

## 2. รายละเอียดและตัวอย่างในหนังสือ

### 2.1 Configuration compliance (การตรวจสอบความสอดคล้องของการตั้งค่า)

เมื่อมีข้อมูลตั้งค่าจริง (จาก Backup) และข้อมูลที่พึงประสงค์ (จาก Rendering) ขั้นตอนนี้จะทำหน้าที่เปรียบเทียบเพื่อหา "ความคลาดเคลื่อน (Deviation)" เป็นการเริ่มต้นทำระบบอัตโนมัติที่ง่ายที่สุด (Low-hanging fruit) เพราะเป็นการทำงานแบบอ่านอย่างเดียว (Read-only) โดยแนะนำให้ตรวจสอบเป็นประจำเพื่อตรวจจับความคลาดเคลื่อนที่อาจเกิดจาก "การตั้งค่าด้วยมือ (Manual intervention)"

- **ตัวอย่างรูปแบบข้อมูลและเครื่องมือ:** กระบวนการนี้รองรับทั้ง API payloads (JSON, XML, YANG) และ CLI แม้ว่า CLI จะจัดการยากกว่า (หนังสือยกตัวอย่างความแปลกประหลาดของการจัดรูปแบบในแต่ละ Vendor หรือการสลับบรรทัด) แต่ยังคงเป็นที่นิยมในปี 2023 โดยหนังสือยกตัวอย่างการใช้เครื่องมืออย่าง **Batfish, Cisco pyATS/Genie, หรือ NTC Templates** เพื่อใช้แปลงโครงสร้าง (Parsing) ข้อมูลแบบ CLI
    

### 2.2 Configuration deployment (การนำการตั้งค่าไปใช้งานจริง)

ขั้นตอนสุดท้ายคือการเปลี่ยนสถานะเครือข่ายให้ตรงกับความต้องการ สามารถทำแบบเต็มรูปแบบหรือทำแค่บางส่วนก็ได้ (Partial)

- **ตัวอย่างการทำบางส่วน (Partial deployment):** ในช่วงแรกอาจเลือกจัดการเฉพาะสถานะที่สำคัญ เช่น การจัดการ **สถานะ BGP บนเพื่อนบ้าน (Neighbor) เมื่อวงจรนั้นกำลังจะเข้าสู่ช่วงซ่อมบำรุง**
    
- **แนวทางการเปลี่ยนการตั้งค่า:** มีทั้งแบบสั่งงานตามลำดับขั้นตอน (Imperative mode) และแบบกำหนดเป้าหมายปลายทาง (Declarative approach)
    
- **ตัวอย่างการป้องกันความผิดพลาด (Rollback):** การเปลี่ยนการตั้งค่าต้องพร้อมย้อนกลับเสมอ หนังสือยกตัวอย่างการรองรับแต่กำเนิดใน **NETCONF** และฟีเจอร์อย่าง **commit-confirm** ที่ผู้ใช้ต้องยืนยันการทำงานหลังติดตั้งไปแล้ว เพื่อป้องกันการสูญเสียสิทธิ์เข้าถึงอุปกรณ์อย่างถาวร
    
- **ตัวอย่างเครื่องมือสำหรับ Deployment แบ่งตามประเภท:**
    
    1. **Custom applications:** ใช้ไลบรารีอย่าง **Netmiko, NAPALM, ncclient, Scrapli, gNMIc** หรือใช้ SDK ของ Vendor เช่น **Cisco Meraki SDK, Juniper Networks Junos PyEZ, AWS Boto3** รวมถึงการเรียกผ่าน APIs โดยตรง
        
    2. **Multipurpose open source tooling:** เครื่องมืออเนกประสงค์แบบโอเพนซอร์ส เช่น **Terraform, Ansible**
        
    3. **Vendor platforms:** แพลตฟอร์มเฉพาะค่าย เช่น **Cisco Crosswork NSO** และ **Juniper Apstra**
        
- **ตัวอย่างการลดความเสี่ยง:** หนังสือแนะนำให้ทดสอบด้วย **โหมด Dry-run**, รันใน **Lab environment** หรือโครงสร้างที่ไม่สำคัญก่อน รวมถึงการทำ Pre-deployment tests และตั้งกระบวนการอนุมัติ นอกจากนี้ยังแนะนำให้ทำ Post-validation หลังเปลี่ยนการตั้งค่า โดยยกตัวอย่างเครื่องมือทดสอบอย่าง **PyATS** หรือ **Robot Framework**
    
- **ตัวอย่าง Zero Touch Provisioning (ZTP):** การตั้งค่าอุปกรณ์อัตโนมัติตั้งแต่เริ่มต้นเมื่อเสียบสายเข้าเครือข่าย โดยอาศัยกลไกการค้นหาเช่น **DHCP** และระบุตัวตนด้วย **MAC address หรือ Serial number**
    

### 2.3 Operations (การปฏิบัติการ)

การปฏิบัติการบนเครือข่ายที่ไม่เกี่ยวข้องกับการเปลี่ยนคอนฟิก ในอดีตใช้ CLI แต่ปัจจุบันมีอินเทอร์เฟซโปรแกรมมิงให้ใช้แล้ว (หนังสือยกตัวอย่าง **gNOI หรือ NETCONF**)

- **ตัวอย่างการปฏิบัติการทั่วไป:** การรีบูตระบบ (System reboot), การทำ **ping** และ **traceroute**, การโอนไฟล์ (File transfer), การเปิดใช้งานระบบปฏิบัติการ (NOS activation) และการจัดการใบรับรอง (Certificate management)
    
- **ตัวอย่างกระบวนการอัปเกรด NOS (NOS upgrade solution):** หนังสือยกตัวอย่างการประกอบร่างงานเหล่านี้เป็น 5 ขั้นตอน ได้แก่:
    
    1. ตรวจสอบพื้นที่ว่างล่วงหน้า (Pre-validate) เพื่อเก็บไฟล์ NOS
        
    2. ทำสำเนาคอนฟิกเก็บไว้ในเครื่อง (Local copy) สำหรับใช้ Rollback
        
    3. ถ่ายโอนไฟล์ NOS ใหม่ (Transfer)
        
    4. เปิดใช้งาน (Activate) และรีบูต (Reboot)
        
    5. ตรวจสอบสถานะหลังติดตั้ง (Post-validate) ด้วย ping และ traceroute
