## 1. หัวข้อนี้พูดถึงอะไร?

หัวข้อนี้พูดถึง **"การเจาะลึกการใช้งานภาษาเทมเพลต Jinja"** ซึ่งเป็นภาษาเทมเพลตที่ได้รับความนิยมมากที่สุดในโลกของ Network Automation ณ ปัจจุบัน เนื่องจากได้รับการสนับสนุนอย่างกว้างขวางจากเครื่องมือและภาษาสำหรับระบบอัตโนมัติหลายประเภท รวมถึง Python โดยหนังสือได้นำเสนอตัวอย่างตั้งแต่การแปลงคำสั่ง CLI ของพอร์ตสวิตช์ (Switchport) ให้เป็นเทมเพลตพื้นฐาน ไปจนถึงการพัฒนาปรับปรุงโค้ดให้รองรับตัวแปรหลายตัว และการใช้งานร่วมกับโครงสร้างข้อมูลอย่างคลาส (Class) หรือดิกชันนารี (Dictionary) เพื่อความเหมาะสมในการจัดการข้อมูล (Namespace-friendly)

เนื้อหาหลักแบ่งออกเป็นประเด็นสำคัญพร้อมตัวอย่างตามลำดับที่หนังสือระบุไว้ดังนี้ครับ:

### จุดเริ่มต้นและการสร้างตัวแปรเดี่ยว (Example 9-2)

หนังสือเริ่มต้นด้วยการยกตัวอย่างคำสั่งคอนฟิกหน้าพอร์ตสวิตช์เดี่ยวๆ ที่ต้องการแปลงให้เป็นเทมเพลต เพื่อนำไปใช้ตั้งค่าพอร์ตสวิตช์อื่นๆ อีกหลายร้อยพอร์ตในระบบ:

Plaintext

```
interface GigabitEthernet0/1
description Server Port
switchport access vlan 10
switchport mode access
```

ในการเปลี่ยนสไนเป็ต (Snippet) นี้ให้เป็นเทมเพลต วิศวกรเพียงแค่ต้องตัดสินใจว่าส่วนใดที่ต้องคงเดิมไว้และส่วนใดที่ต้องปรับเปลี่ยนแบบไดนามิก

> **ตัวอย่างที่ 1 (Example 9-2):** หนังสือได้นำชื่ออินเทอร์เฟซที่ระบุเจาะจงออกไป แล้วแปลงให้เป็นตัวแปร (Variable) เพื่อนำไปเติมค่าในตอนที่เรนเดอร์เทมเพลตออกมาเป็นคอนฟิกจริง:
> 
> Plaintext
> ```
> interface {{ interface_name }}
> description Server Port
> switchport access vlan 10
> switchport mode access
> ```
> 
> เมื่อทำการเรนเดอร์เทมเพลตนี้ คุณสามารถส่งค่าตัวแปร `interface_name` เข้าไป และตำแหน่งดังกล่าวจะถูกเติมเต็มด้วยค่าที่เกี่ยวข้องกับตัวแปรนั้น

### การเพิ่มความยืดหยุ่นด้วยตัวแปรที่มากขึ้น (Example 9-3)

เนื่องจากเทมเพลตในตัวอย่างแรกมีข้อสมมติฐานว่าอินเทอร์เฟซของเครือข่ายทุกช่องจะมีการตั้งค่าที่เหมือนกันทั้งหมด หนังสือจึงตั้งคำถามว่า หากเราต้องการเปลี่ยนหมายเลข VLAN หรือเปลี่ยนคำอธิบายพอร์ต (Description) ในบางอินเทอร์เฟซจะทำอย่างไร?

> **ตัวอย่างที่ 2 (Example 9-3):** หนังสือระบุว่าในกรณีนี้ คุณควรแปลงส่วนอื่นๆ ของคอนฟิกให้เป็นตัวแปรเฉพาะของมันเองด้วย ดังนี้:
> 
> Plaintext
> 
> ```
> interface {{ interface_name }}
> description {{ interface_description }}
> switchport access vlan {{ interface_vlan }}
> switchport mode access
> ```

### การปรับปรุงโครงสร้างข้อมูลให้มีประสิทธิภาพ (Example 9-4)

หนังสือชี้ให้เห็นว่า แม้ตัวอย่างก่อนหน้านี้จะเป็นตัวอย่างที่เรียบง่าย แต่โครงสร้างแบบนั้นไม่ค่อยเป็นมิตรกับพื้นที่ชื่อข้อมูล (Not very namespace-friendly) ในการทำงานจริงเมื่อเรนเดอร์เทมเพลต จึงเป็นเรื่องปกติที่จะมีการใช้ประโยชน์จากแนวคิดเรื่อง **คลาส (Classes)** และ **ดิกชันนารี (Dictionaries)** ในภาษาอย่าง Python ซึ่งช่วยให้เราสามารถจัดเก็บข้อมูลหลายๆ ชุด (Multiple instances of data) เพื่อนำไปใช้วลลูป (Loop) และเขียนคอนฟิกซ้ำๆ ได้ในผลลัพธ์สุดท้าย

> **ตัวอย่างที่ 3 (Example 9-4):** หนังสือแสดงการเขียนเทมเพลตเดิมใหม่อีกครั้ง เพื่อใช้ประโยชน์จาก Python class หรือ dictionary:
> 
> Plaintext
> 
> ```
> interface {{ interface.name }}
> description {{ interface.description }}
> switchport access vlan {{ interface.vlan }}
> switchport mode access
> ```

**คำอธิบายการทำงานจากหนังสือ:** นี่เป็นการเปลี่ยนแปลงเพียงเล็กน้อยแต่มีความสำคัญ อ็อบเจกต์ (Object) ที่ชื่อ `interface` จะถูกส่งผ่านไปยังเทมเพลตทั้งหมดในคราวเดียว โดยมีเงื่อนไขตามลักษณะข้อมูลดังนี้:

- **หาก interface เป็น Python class:** ค่า `name`, `description`, และ `vlan` จะทำหน้าที่เป็นคุณสมบัติ (Properties) ของคลาสล่านั้น
    
- **หาก interface เป็น Dictionary:** ทั้งสามค่าจะเป็น คีย์ (Keys) ของดิกชันนารีนี้แทน ไม่ใช่คุณสมบัติ
    

ไม่ว่าจะเป็นรูปแบบใด เครื่องมือเรนเดอร์ (Rendering engine) จะทำหน้าที่แทนที่ค่าเหล่านั้นด้วยข้อมูลที่ตรงกับคีย์หรือคุณสมบัติให้โดยอัตโนมัติในขณะที่เรนเดอร์เทมเพลตครับ
